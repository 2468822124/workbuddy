#### 4个「参照完整性」缺口（代码级核实，全部实测真问题）

- **① 反向不同步** 🟡：选取周任务进日计划、后删/放弃，weekly那条卡在「已下沉`[x]`」回不到可选，须手改
- **② 文本匹配脆弱** 🟡：所有级联靠任务文字**精确匹配**，改名/同名多行/空白差异→匹配错
- **③ 出处链断裂** 🟡：todo最多追溯到「日规划·{date}」，**追不到周任务、更追不到月任务**
- **④ 删除不传播** 🟡：删周/月任务→日待办不消失；删日任务→weekly不回退

### 🔍 GLM 诊断（2026-08-10）

#### 方向抉择：重做 vs 增量

**光谱对比**：
- **L1 极轻增量**：任务行内联隐藏ID + todos加`parentTaskRef`列；Markdown仍唯一真相
- **L2 半规范化**（✅定稿）：新增轻量`tasks`表，`plans.content`保留为手帐真相，保存时双向sync
- **L3 全重做**：`base_task`实体 + `plan_schedule`外键树

**关键否决**：
- **L3否决**：代价（横扫全平台 + 推翻方案B + 手帐灵魂）远超收益；物理级联`ON DELETE CASCADE`是**红鲱鱼**
- **混合/双模型否决**：dual-model反模式——维护两套全栈 + 桥接，成本逼近L3而复杂度更高

**用户未来功能压力测试**（均验证L2够用）：
1. 交接流转：顺延机制已具雏形，L2不动todo核心模型 ✅
2. AI多轮问答生成复盘/计划：AI读现有数据，与数据模型无关 ✅
3. AI识别一周内低完成率任务并提问：按任务文字聚合统计即可 ✅
4. 项目任务池→今日总览新模块：数据已在，零新表 ✅

### 🔄 方向定稿（2026-08-10）

**载体定义（L2半规范化）**：
- `plans.content`（Markdown）**仍为手帐真相源**，手帐灵魂与"写计划"体验不变
- 新增轻量`tasks`表：`(tid PK, planId FK→plans, content, parentTaskId nullable, consumed, order)`
- `todos`加列`parentTaskRef`（= `parentPlanId + parentTaskId`，nullable）

**4缺口修法（L2下）**：
- **② 稳定身份**：`tasks.tid`给每条任务稳定编号；级联匹配键由"文字"改为"tid"
- **③ 出处链**：`todo.parentTaskRef`指向上级task→逐级溯源（todo→周任务→月任务→源头）
- **①④ 删除语义**：扩展`syncPlanTodos`的方案B open/done分流到**跨级**——检测上级task被删→按`parentTaskRef`查下游todo→open软删/done保留并标"来源失效"

**约束（一律不变）**：方案B、全软删除铁律、Markdown-as-truth、离线优先

## 经验总结

### 问题类型
- **类型**：数据模型/参照完整性/架构设计
- **根本原因**：v0.2架构采用Markdown-as-truth + 文本匹配，缺乏稳定身份标识

### 关键决策
- **L3否决原因**：文档的物理级联会推翻方案B（done历史保留），且横扫全平台代价过高
- **L2选择原因**：保留手帐灵魂，最小化冲击圈，仅升级"规划/级联"子系统

### 预防措施
- **数据模型设计**：在早期就应考虑稳定身份标识和参照完整性
- **架构决策**：重大架构变更需充分评估冲击范围和向后兼容性
