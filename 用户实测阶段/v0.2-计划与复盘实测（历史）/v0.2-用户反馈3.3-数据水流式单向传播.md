## 用户北极星（原话，不可改写）

> "核心问题不仅仅是周统筹改名不传播，我希望的状态是数据能像水流一样，源头的改动直接影响后面全部数据（例如：改名、删除），中游的改动只影响中下游，这样才是解决问题的真办法，而非遇到一个问题改一个问题，这样永远改不完，没有一个北极星目标，只能不断修改。"

**北极星一句话**：**数据像水流——单向下游传播（月→周→日→待办），源头改动（改名/删除/新增）影响全部下游，中游改动只影响中下游、不回传上游。**

---

## 背景（源自 3.2 第四轮问题1）

**现象**：周统筹（weekly_plan）改名周任务"做周报"→"做本周周报"后：
- ✅ todo tag 改名（"周任务·做本周周报"）—— tasks 表实时取值副作用
- ❌ 日规划子任务行文本不改名
- ❌ 今日待办 todo.content 不改名

**根因（GLM 经 Explore agent 代码追踪查实，既有设计缺口，非回归）**：
- `syncPlanTodos(weekly)`（`planRepo.ts`）仅 §3.3 更新 tasks 表 content + §3.6 删除传播，**无 parent→child 改名传播通道**。
- `findByParentTaskId` 全仓**仅用于删除 cascade**（`planRepo.ts:184`），不用于改名传播。
- weekly 早返回（`planRepo.ts:208-220` `!isDaily`）不碰 daily。
- todo.content 是日规划保存快照，weekly 保存从不更新。
- child→parent 不回传（单向，**已符合北极星**）。
- 无任何代码痕迹表明曾有传播通道后被破坏。

## 目标架构（单向下游传播）

```
monthly_plan → weekly_plan → daily_plan → todo
     ↓             ↓             ↓          (终端)
  源头改动 ──────→ 全下游传播（改名/删除/新增）
                   中游改动 ──→ 仅中下游，不回传上游
```

**传播规则**：
| 改动位置 | 改名 | 删除 | 新增 |
|---|---|---|---|
| 月任务（源头） | → 周/日子任务行 + todo 全改名 | → 周/日子任务行 + todo 全级联删 | （月任务新增无下游，天然无传播） |
| 周任务（中游） | → 日子任务行 + todo 改名（不回传月） | → 日子任务行 + todo 级联删（不回传月） | 同上 |
| 日任务（中游） | → todo 改名（不回传周/月） | → todo 删（不回传周/月） | 同上 |
| todo（终端） | — | — | 无下游 |

## 现状差距（GLM 诊断，供整体设计输入）

| 维度 | 当前实现 | 北极星目标 | 差距 |
|---|---|---|---|
| **改名传播** | 完全不传播（仅 tag 因 tasks 表实时取值副作用改） | parent→child 文本全下游传播 | 🔴 全缺 |
| **删除传播** | §3.6 cascade **部分**：todo 软删/失效，**不回写 daily/weekly markdown 子任务行** | parent→child 全下游（含 markdown 真相源 + todo） | 🟡 部分（todo 层有，markdown 层缺） |
| **新增传播** | 无（parent 新增任务不自动建 child） | 同删除，parent→child | 🔴 缺（但优先级低，新增无下游是常态） |
| **child→parent 回传** | 不回传 | 不回传 | ✅ 符合 |
| **tid 关联键** | 已就绪（`tasks.tid` + 行内 `parent:{tid}` 注释，扛改名） | 复用 | ✅ 基础在 |
| **consumed/完成态** | 方案C（跟随 todo 完成） | 应随传播重算（删下游 done → 上游 consumed 回退） | 🟡 部分（见 3.2 问题2b） |

## 实现方向（GLM 给方向，DS/整体设计定具体方案）

⚠️ **北极星是架构级改动，须整体设计，非单点 patch**。关键设计点：

1. **传播通道（parent→child 文本回写）**：
   - parent plan 保存时，按其任务 tid 找下游 child plan 的对应子任务行（`parent:{tid}` 注释）+ todo（`sourceTaskTid`/`parentTaskRef`）→ 回写新文本（改名）/删除（删除）/忽略（新增无下游）。
   - 复用现有 `tid` 关联键（已扛改名）+ `findByParentTaskId`（扩为改名/删除双用途）。

2. **markdown 真相源一致性**：
   - 改名/删除传播须回写下游 plan 的 **content（markdown）**，不止 todo。如周任务改名 → 回写本周各 daily_plan content 里 `parent:{周tid}` 子任务行文本。
   - 触发下游 plan 的 syncPlanTodos（保持 todo 与 markdown 一致）。

3. **循环检测 / 终止条件**：
   - 月→周→日 三级链，须有终止（避免无限传播）。日是终端（无 child plan，只有 todo）。

4. **性能**：
   - 一次源头改名可能触发多级、多 plan 回写 + 多 todo 更新。须批量化、避免 N+1。

5. **冲突 / 边界**：
   - 多源同名（同一日任务被多周任务下沉？当前 pick 限单父）。
   - 下游已手动改名（中游改名）——按北极星"中游改动只影响中下游"，下游手动改名应保留（不被上游覆盖）？还是上游优先？**须用户决策**。
   - 下游已删除（orphan）——上游改名不再回写它。

6. **与现有机制协同**：
   - 第二轮问题① `scheduledInPeriod`（rail 隐藏）——传播后 rail 应正确反映。
   - 第三轮问题乙 `sourceTaskTid` 复用——传播改名应触发复用而非新建。
   - 方案C consumed——删除传播应重算上游 consumed（见 3.2 问题2b）。
   - `reconcile`（编辑框隐藏注释）——回写下游 markdown 须保 tid 注释。
