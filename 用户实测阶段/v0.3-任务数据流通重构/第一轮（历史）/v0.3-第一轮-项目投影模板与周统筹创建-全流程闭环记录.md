## 3. GPT 诊断

### 3.1 UF1：周核心目标新增参数被父视图破坏（🔴阻断）

**裁定**：🐛 真实缺陷，已达到代码级确诊。

**用户可见现象**：选择月目标和手动输入两条创建路径都失败，IPC 返回 `weekStart/title 必填`。

**可能根因（按概率排序）**：

1. **父视图错误地把 Vue 多参数事件当成对象事件读取（约 95%，确诊）**。
   - `workbuddy/src/renderer/src/components/flow/FocusBlock.vue:16-20` 声明 `add: [title, monthGoalId]` 两个事件参数。
   - `FocusBlock.vue:35-42` 在提交时执行 `emit('add', t, gid)`，第一个参数是标题字符串，第二个参数是月目标 id。
   - `workbuddy/src/renderer/src/views/flow/FlowWeekView.vue:107-115` 却写成 `@add="addFocus($event.title, $event.monthGoalId)"`。
   - Vue 的 `$event` 在此处是第一个参数字符串，不是含 `title/monthGoalId` 的对象；因此父视图传给 `addFocus` 的两个值均为 `undefined`。
2. **周核心目标 IPC 校验拒绝缺失字段（约 5%，不是根因而是正确防线）**。
   - `workbuddy/src/main/ipc/flow.ipc.ts:185-190` 要求 `title` 和 `weekStart`，缺失时返回 `weekStart/title 必填`。
   - 该校验解释了用户看到的错误，但不应通过放宽后端校验来“修复”。

**中间链路证据**：

- `workbuddy/src/renderer/src/composables/useFlowWeek.ts:232-234` 原本会组装 `weekStart`、`title` 和 `monthGoalId`。
- `FlowWeekView.vue:27-54` 已将 `useFlowWeek()` 顶层解构，`weekStart` 本身可用；当前缺失发生在组件事件转发处。

**影响范围**：月目标选取、手动核心目标创建均不可用；完成、删除等既有目标动作不应随意改写。

### 3.2 UF2：本周任务新增参数被父视图破坏（🔴阻断）

**裁定**：🐛 真实缺陷，已达到代码级确诊。

**可能根因（按概率排序）**：

1. **父视图错误读取多参数事件的 `$event`（约 95%，确诊）**。
   - `workbuddy/src/renderer/src/components/flow/InstanceList.vue:19-29` 声明 `create: [title, kind, targetCount]`。
   - `InstanceList.vue:38-46` 执行 `emit('create', t, kind.value, n)`。
   - `workbuddy/src/renderer/src/views/flow/FlowWeekView.vue:125-140` 却写成 `@create="createTemp($event.title, $event.kind, $event.targetCount)"`。
   - 结果是 `title/kind/targetCount` 没有按事件参数传递；IPC 收到的 `weekStart/title/kind` 不完整。
2. **IPC 输入校验（约 5%，不是根因而是正确防线）**。
   - `workbuddy/src/main/ipc/flow.ipc.ts:76-80` 要求 `weekStart/title/kind`，所以错误会被明确拒绝而不是生成脏数据。

**中间链路证据**：

- `workbuddy/src/renderer/src/composables/useFlowWeek.ts:200-202` 原本会调用 `api.flow.instance.create({ weekStart, title, kind, targetCount })`。
- 组件事件在父视图处丢失参数，故后端错误文案与用户操作相符。

**影响范围**：一次型和场次型本周临时任务都不能新增；同时阻断场次型 `0/N → 1/N → N/N` 用户验收链路。

### 3.3 UF3：日规划模板状态未在视图顶层解包（🔴阻断）

**裁定**：🐛 真实缺陷，高度确定，结合 GPT 自主实测 F3/F5 已形成独立 GUI 交叉证据。

**可能根因（按概率排序）**：

1. **普通对象嵌套 ref 被直接用于模板表达式/组件 prop（约 90%，高度确定）**。
   - `workbuddy/src/renderer/src/composables/useFlowTemplates.ts:16-19` 创建 `templates/error/info/loading` 等 ref。
   - `useFlowTemplates.ts:74-85` 返回一个普通对象，该对象属性仍是 ref。
   - `workbuddy/src/renderer/src/views/flow/FlowDayView.vue:46` 使用 `const tpl = useFlowTemplates()`，没有将这些 ref 顶层解构，也没有显式 `unref`。

   - `useFlowTemplates.ts:52-63` 成功后会 `reload()`；若 UI 读取正确，创建结果应可见。当前“表单关闭但列表仍为 0 + 空错误条”更符合显示层 ref 解包错误。

**影响范围**：模板创建后的列表、成功/失败反馈、后续套用/编辑/删除验证都不可可靠进行。修复不得只隐藏红条，必须保证数据列表和反馈状态均真实可见。

### 3.4 UF4：项目任务计划日期与今日投影语义冲突（🟡待裁决）

**裁定**：❓ 当前不能直接判为代码缺陷；需要用户补测和产品语义定稿。

**高概率解释**：阶段4规格规定项目任务通过“加入今日”按钮生成今日投影，而不是由 `todos.planDate` 自动投影。

**关键证据**：

- 阶段4规格“项目投影链路”明确：项目页的某条 todo 通过“加入今日”按钮生成今日投影。
- `workbuddy/src/renderer/src/composables/useProjectDetail.ts:101-116` 的 `addToday()` 才调用 `api.flow.entry.add({ date: localToday(), title, source: 'project', projectId })`。
