## 2.2 E1 AI 配置 + 测试连接（错误网址误报成功）— 🐛 真实缺陷

### 用户报告（原文）
- **操作**：输入"存在但错误的网址"（一个真实可访问、但不是 LLM 端点的 URL）
- **预期**：URL 报错（连接失败）
- **实际**：显示"正常连接，并显示出延迟"
- **错误信息**：无

### 环境
- **模块**：设置 → AI 配置 → 测试连接
- **影响**：给用户**虚假信心**——配错的 AI 实际不可用，却提示"连接成功"，直到真正用 AI（对话搜索/引导/汇总）时才暴露。

### 复现步骤（GLM 整理）
1. 设置 → AI 配置，Base URL 填一个"真实存在但非 LLM"的网址（如 `https://www.baidu.com` 或任意普通网站根域名），Model/Key 随便填。
2. 点「测试连接」。
3. 预期：提示连接失败/非有效 AI 端点。实际：提示"连接成功，XXms"。

### GLM 诊断
**裁定：🐛 真实缺陷（HTTP 状态码单点校验，未校验响应体）。**

**根因（按概率，已锁定）：**
- **① 仅校验 HTTP 状态码，从不校验响应体（~95%）**
  - `src/main/services/llm.ts:70-77`（`testConnection`）：请求本身是对的——`POST {baseUrl}/chat/completions`，体 `{model, messages:[{role:'user',content:'ping'}], max_tokens:1}`，`Authorization: Bearer {apiKey}`（L51-65，符合规格-阶段4 §5.1）。**缺陷在响应判定**：
    ```ts
    if (!res.ok) {                                  // ← 仅看状态码
      return { ok: false, message: `服务器返回 ${res.status}…`, latencyMs }
    }
    return { ok: true, latencyMs }                  // ← 2xx 即判成功，零响应体校验
    ```
  - `res.ok` 对任何 2xx 为真。函数**从不解析 JSON、从不检查 `choices[0].message.content`、从不验证 Content-Type 是否 JSON、从不识别 error 形态的 body**。任何返回 HTTP 200 的响应都被判为"连接成功"。
- **为什么"错误但存在的网址"会误报成功**：大量真实网站/CDN/catch-all 前端对任意 POST 路径（如 `/chat/completions`）返回 **HTTP 200 + HTML 错误页/首页**（soft-404），而非干净的 4xx。因校验器只看 `res.ok`，这种响应被当成"可用 LLM 端点"。返回 `200 + {"error":"..."}` 的服务同理误判。
- **对比**：生产聊天路径（`requestChat`/`searchNews`，L219-241/278-283）至少会解析 `choices[0].message.content`；唯独测试连接函数跳过了这一步。

**关键判断证据**：
- 缺陷点：`src/main/services/llm.ts:70-77`（成功判定在 L77，无 body 校验）。
- IPC：`src/main/ipc/llm.ipc.ts:8-19`（`IPC.LLM_TEST`）。
- 渲染：`src/renderer/src/views/SettingsView.vue:32`（直接渲染"连接成功 · {latencyMs}ms"）。
- 规格差距：规格-阶段4 §5.1 写"200 → ok:true"——**规格本身过宽**，未要求校验响应体为有效 OpenAI 响应；用户测试流程 E1 期望"错误 URL → 失败"，要求比规格字面更严。

### 修复计划（交 DeepSeek，用 04 prompt）
- **修复项**：`src/main/services/llm.ts` `testConnection()`（L70-77 成功分支）。
  - 在 `res.ok` 之后，**解析并校验响应体为有效 OpenAI Chat Completion**：读 `await res.json()`（失败则读 text 判断是否 HTML），校验存在 `choices` 数组且 `choices[0].message.content` 为字符串。
  - 非 JSON / 无 `choices` / HTML 页 / error 形态 → 返回 `{ ok:false, message:'该地址未返回有效的 AI 响应，请确认 Base URL 指向 OpenAI 兼容的 /chat/completions 端点（如 https://api.deepseek.com）' }`。
  - 保留：`max_tokens:1`、10s 超时、apiKey 不入日志、401/403/429/5xx/网络错/超时的既有 message 映射不变。
- **验收点（GLM 复审 05 + 用户复测）**：
  - [ ] 错误但存在的网址（如 `https://www.baidu.com`）→ **提示失败**（非"连接成功"）。
  - [ ] 正确 LLM 端点 → 仍提示"连接成功 + 延迟"。
  - [ ] 错 Key → "API Key 无效或已过期"（401 路径不变）。
  - [ ] 不存在的域名 → ≤10s 内"连接失败/超时"。
  - [ ] logger 无 apiKey 明文（既有红线不回归）。
- **严重度裁定**：🟡 需修（不崩，但给虚假信心，属正确性缺陷；非 🔴 因不阻断且不发数据泄漏）。
- **指派**：DeepSeek（04-修复）。改动集中在一个函数的成功分支，低风险。

## 2.6 U6 无数据占位（无完成任务仍调 AI）— 🐛 真实缺陷

### 用户报告（原文）
- **操作**：选取了很早一日（无任何任务）
- **预期**：不调用 AI
- **实际**：依旧调用 AI，显示思考中并给出 AI 建议
- **错误信息**：无

### 环境
- **模块**：复盘 → AI 汇总（需已配 LLM）
- **影响**：违反"无数据应短路不调 LLM"的禁止边界式约定——浪费 token、给用户错误输出（AI 基于全局项目状态编造"当日进展"）。

### 复现步骤（GLM 整理）
1. 系统中存在 ≥1 个进行中项目（之前 T0/测试建的，与所选日期无关）。
2. 复盘页日期选一个**无任何完成任务**的很早日期。
3. 点「AI 汇总」。
4. 预期：立即出占位草稿、不转圈、不调 AI。实际：转"思考中"、调 AI、给 AI 建议。

### GLM 诊断
**裁定：🐛 真实缺陷（短路条件用 AND + `findActive()` 无日期过滤 → 短路永不触发）。**

**根因（已锁定）：**
- **① 短路条件过严且第二操作数恒非零（~95%）**
  - `src/main/services/llm.ts:371-390` `summarizeReview()`：
    ```ts
    const done = todoRepo.findCompletedOn(date).slice(0, LLM_TODO_LIMIT)        // 正确：按 date 过滤
    const projects = projectRepo.findActive().slice(0, LLM_PROJECT_LIMIT)        // ← 全局所有进行中项目，无日期过滤
    if (done.length === 0 && projects.length === 0) {                            // ← BUG：AND + 全局 projects
      return { draft: `# 日复盘草稿 · ${date}\n\n（当日暂无完成任务记录…）`, latencyMs: 0 }
    }
    ```
  - `projectRepo.findActive()`（`src/main/db/repositories/projectRepo.ts:65-76`）返回**全库** `isDeleted=0 AND status='active'` 的项目，**无 date/completedAt 过滤**。
  - 只要库里有任意进行中项目（任何真实用户的常态）→ `projects.length >= 1` → `done.length===0 && projects.length===0` 恒为 `false` → **短路永不触发 → 必调 LLM**。对任何非空库，该短路是死代码。
- **② 渲染层无兜底预检（放大项，~5%）**
  - `src/renderer/src/composables/useReviewSummary.ts:31-47`：渲染层**不做无数据预检**，仅以 `llmReady`（Key 是否存在）为守卫，L40 直接发 IPC `api.reviews.summarizeDraft({date})`。短路责任全在主进程，而主进程条件又永不成立。
- **机制复现**：用户有 ≥1 进行中项目 → `findActive()` 返回 → `projects.length>=1` → `true && false`=`false` → 跳过占位 → 调 LLM → AI 仅凭全局项目状态给"建议"（正是用户所见）。
- **`findCompletedOn` 本身没问题**：`todoRepo.ts:30-34` 正确按 `completedAt LIKE date+'%'` 过滤，早日期返回 0 行。✓

**规格缺陷（重要）**：本实现是**规格伪代码的逐字拷贝**——`规格-子阶段4-LLM增强.md` L229 的伪代码即 `if (done.length === 0 && projects.length === 0)`，L405/L436 验收文亦写"无完成任务**且无项目**"。**规格本身有设计缺陷**（把"全局存在进行中项目"误当"当日有项目活动"），被忠实转录成代码。需代码 + 规格同步修。

### 修复计划（交 DeepSeek，用 04 prompt）
- **修复项（代码）**：`src/main/services/llm.ts:374`——短路条件改为**仅看当日完成数**：
  ```ts
  if (done.length === 0) {        // 去掉 && projects.length === 0
    return { draft: `# 日复盘草稿 · ${date}\n\n（当日暂无完成任务记录，可手动补充今日收获与反思。）`, latencyMs: 0 }
  }
  ```
  理由：日复盘复盘的是"当日完成"，当日无完成即无可汇总；仅项目状态（无当日完成）会让 AI 编造（违反 system prompt 规则1"只使用真实任务"）。与用户测试流程 U6"无完成任务→不调 AI"一致。
  - （可选更稳）保留 projects 进上下文，但短路仍以 `done.length===0` 为准；不必改 `findActive`（爆炸半径小）。
- **修复项（规格同步，变更闭环）**：`计划与复盘体系实现项目计划/规格-子阶段4-LLM增强.md` 三处——L229 伪代码去 `&& projects.length === 0`；L405/L436 验收文"无完成任务且无项目"改为"当日无完成任务"。由 GLM 走变更闭环更新（或 DeepSeek 一并改）。
- **验收点（GLM 复审 05 + 用户复测）**：
  - [ ] 系统有进行中项目 + 选无完成任务的早日期 → 点 AI 汇总 → **立即出占位草稿、不转圈、DevTools Network 无 chat/completions 请求**。
  - [ ] 选有完成任务的日期 → 仍正常调 LLM 给草稿。
  - [ ] vitest 全绿不回归；build 绿。
- **严重度裁定**：🟡 需修（违反 spec'd 短路、浪费 token、错误输出；非 🔴 因不崩、不泄漏数据、单次不重试）。
