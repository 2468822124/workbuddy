# 07 - 修复用户实测事项（给 GLM+DS；文件名保留兼容）

> **用途**：GLM+DS 按某个 R 唯一全流程闭环文档中的统一 `FixN`，执行已批准的代码修复、替代或删除方案，并把执行事实追加到同一 R 文档。
>
> **入口边界**：用户实测问题统一使用 07。`04-deepseek修复.md` 只处理开发单元审查问题，不得用 04 处理 R 问题。07 不创建 R、测试计划或问题 ID，也不替用户作环境/产品决策。

> **阶段门禁卡**：开启条件 = `13` 已生成完整统一 `FixN`，所有事项有终态，覆盖缺口已转计划，且无待核实/环境/用户决策阻塞；完成状态 = 统一 Fix 执行证据齐全，完整源包已保存，`closureStatus=in-progress`、各点 `testPointStatus` 已记录、`nextAction=05`；失败回退 = 证据缺失回 `13`，环境/产品事项回 `16`，修复或复测失败留在 `07`。不能拆成多个 Fix，也不能把完成写成 Review/QA 通过。

## 发送给 GLM+DS 的输入

```text
R 唯一全流程闭环记录绝对路径：E:\workspace\用户实测阶段\<版本-功能名>\第<N>轮\<版本>-第<N>轮-问题概述-全流程闭环记录.md
修复批次：Fix<N>
多 R 批次标识：B<N>
本次 R 标识：R<N>
统一 Fix 状态：{{13 已标记可执行 / 不可执行}}
输入状态：planStatus={{}} · staticGate={{}} · closureStatus={{in-progress}}
允许范围/排除范围：{{}}
启动时间/实际执行者：{{}} / {{GLM / DS / GLM+DS}}
联合执行分工与 `当前代码状态.md` 唯一写入者：{{单人执行写“不适用”；联合执行写文件/命令分工和 GLM 或 DS}}
```

路径必须是当前问题来源轮次的唯一闭环文档，不能填写测试计划、GPT 报告、用户回传、旧版反馈文件或新问题文件。

## 一、开始前读取和停止条件

按顺序读取：

1. 输入的 R 唯一闭环文档，尤其是最新“事项处置总表”、诊断、统一 Fix 计划、覆盖补充项、环境/产品决策区、替代计划、删除计划和之前的 Fix/Review/QA/S 记录；
2. 该文档索引的原始测试计划、GPT 正式报告、用户 06 回传、用户证据、用户补充问题原文和独立 GPT 补充核验证据；
3. `当前代码状态.md`、相关开发单元闭环、`当前审查状态.md`、`规范类/项目代称.md`、技术栈规范和适用产品规格；
4. 原始失败场景涉及的代码、测试、构建配置和替代/删除范围。

在以下任一情况发生时，必须停止并在回复中列出“需补充信息”，不猜测、不缩小批次、不先修已确认的一半：

- R 闭环路径不存在、同一 R 有多个闭环文档、`FixN` 不存在或已经执行；
- 事项处置总表缺失，任何事项没有明确终态处置，或统一 Fix 的问题、范围、责任人、验收条件不完整；
- 仍存在 `📝待补证据/待核实`、`⏸️待环境/产品决策` 或待用户确认事项；
- 计划覆盖缺口未明确转为下一测试计划，或把未测试/未回传写成通过；
- 代码 Fix 缺少计划预期、用户原始事实/证据、GPT 正式或独立补充核验证据、同一 S/测试副本或原始失败场景；
- 替代/删除事项没有 `16` 记录的用户明确选择、批准范围和后续验收条件；
- 本 R 没有代码 Fix、替代或删除事项，仅有覆盖补充项；此时停止，不创建空 Fix，交给 14 的“覆盖补充计划”；
- 测试数据、正式入口、S 快照或真实数据隔离无法确认。

### 1.1 统一 Fix 门

07 只能执行 13 已标记为“可执行”的统一 `FixN`。可执行意味着：

1. 本 R 每一项都有明确处置结果；
2. 该批次一次覆盖本 R 中全部获准的代码 Fix、替代和删除事项；
3. 覆盖缺口已经作为下一测试计划纳入项，不进入代码改动；
4. 没有待核实、环境阻塞、待用户确认或未决冲突；
5. 每个执行事项都有允许范围、排除范围、原始失败场景、验收条件、证据路径和责任人。

如果 13 只完成了问题级证据门但仍有本 R 其他阻塞事项，不能调用 07。不能通过拆成 `Fix1a`、`Fix1b` 或“先修最容易的一个”绕过统一 Fix 门。

## 二、修复、替代和删除范围

只处理事项处置总表和统一 Fix 计划明确列出的项目：

- **代码修复**：按稳定问题 ID、预期、根因诊断、允许改动范围和验收条件实施最小必要改动；
- **替代方案**：只执行 16 已由用户选择并批准的替代方案，记录被替代对象、保留/迁移边界、功能影响和新的验收条件；
- **删除方案**：只执行 16 已批准的删除范围，记录删除对象、数据保留/软删除策略、不可逆风险、恢复条件和新的验收条件。

07 不得自行把环境阻塞改成产品缺陷，不得自行选择继续排障/替代/删除，不得把覆盖缺口补写成产品修复，不得将下一 R 的问题带入本 R。

允许修改产品代码及其必要的自动化测试、构建或配置；不允许修改用户测试计划原有结论、GPT 报告、用户回传、数据库以伪造结果、失败证据或历史 R 事实。不得修改治理 Prompt/模板，除非 Fix 计划明确把治理文件列为本批次改动。

## 三、执行和验证

对统一 Fix 中每个事项按以下顺序执行并记录：

1. 按原始 GUI/运行场景复现并记录实际失败；不能复现时标 `⚠️待复测`，不能把代码阅读当作复现；
2. 实施最小必要的修复、替代或删除；遵守现有技术栈、分层、软删除和数据保护规则；
3. 运行受影响的自动化测试、构建和静态检查，记录真实命令与结果；
4. **提交并推送代码**（如果项目已激活 CI）：
   ```bash
   git add .
   git commit -m "fix(R{{N}}): {{简短描述}} (#{{issue-id}})"
   git push origin <fix-branch>
   ```
   - 推送后等待 CI 运行完成（3-5 分钟）
   - 访问 GitHub Actions 查看 CI 状态
   - **CI ✅**：继续步骤 5
   - **CI ❌**：查看失败日志，修复问题后重新推送，重复此步骤
   - 在 Fix 回写中记录：CI run ID、CI 状态（✅/❌）、失败原因（如有）
   - **未激活 CI**：跳过此步骤
5. 按原用户动作链路复跑，覆盖计划要求的取消/确认、错误降级、刷新/离开重进、数据一致性和安全边界；
6. 对每项记录执行前后页面、数据、文件和证据；不安全或无法实际验证的项目标 `⚠️待用户实测`。

不得绕过 UI、直接调用业务 IPC/API、写数据库、脚本插入业务数据或通过隐藏 DOM 伪造通过。GUI 证据必须由后续 05 按复审规则重新取得；自动化测试不能替代用户实测。

若本批次代码、依赖或构建输入发生变化：

- 在 Fix 回写中记录候选 QA 编号、版本字段、来源提交号或完整工作树指纹、构建目录、构建物哈希、完整源包清单和待冻结的 S；
- 不自行宣称 QA/S 已冻结，不修改版本字段掩盖事实，不创建 C0/C1 Tag；
- 只有 05 复审通过后，才由 GPT 先使用 `15A-最终候选同步开发基线.md` 同步最终候选并核对 `source-sync-result.json`，再使用 `15-冻结QA-S.md` 冻结 QA/S。

若代码、依赖和构建输入均未变化，记录可复用的候选 S 及复用理由，仍须由 05 和 15 核对，不得跳过复审。

## 四、回写同一 R 闭环文档

在同一文档末尾追加 `FixN`，至少写明：

- 批次编号、日期、执行者、处理事项 ID和未处理/不适用项目；
- 每项改动文件/模块、改动目的、替代或删除对象及允许范围；
- 原始失败复现结果、根因与执行方案；
- 自动化测试、构建和静态检查命令/结果；
- 原始用户场景复跑步骤、页面稳定态、持久化核对和证据路径；
- 未验证项、剩余风险、阻塞项和下一步 `ReviewN`；
- 候选 QA 编号、版本字段、来源指纹、构建物哈希和待冻结 S 信息；
- `planStatus`、`staticGate`、各事项 `testPointStatus`、`closureStatus`、`updatedAt`、`updatedBy`、证据和 `nextAction=05`；
- 明确声明没有创建测试计划、没有创建新 R/问题文档、没有修改用户回传和 GPT 正式报告。

不得删除或覆盖原始测试事实、GPT 报告、用户 06、用户体验、问题分类、处置决策或之前的 Fix/Review。不得把修复执行写成 Review 通过、QA/S 冻结、用户验收通过或 R 闭环。

## 五、完成结论和交接

- 全部统一 Fix 事项按原始场景复跑且验收通过：报告“FixN 执行完成，待 GPT 使用 05 对整个批次复审”；05 通过后下一步是 15A，不是直接 15。
- 任一事项失败、未验证、证据缺失或环境阻塞：报告 `🟡待复测` 或 `⏸️需补充信息`，保持 R 阻塞，不生成可执行的下一计划；
- 只有 05 对整个批次复审通过后，才进入 `15-冻结QA-S.md`；15 冻结后才由 14 创建同一 R 的下一计划或覆盖补充计划。

07 的执行不等于 Review 通过、源代码同步完成、QA/S 冻结、用户实测闭环、G1、C1 或维护期。

## 六、Fix 机器交接与复审候选自动编排

统一 Fix 开始前，GLM+DS 必须先在代码开发区保存本次 Fix 的精确基线，并由 `begin-fix` 核对当前工作树等于 `current-development-pointer.json`。统一 Fix 完成并构建后，必须调用 E:\workspace\tools\r_fix_review.py 完成完整候选源包保存、候选生成和恢复；不能只把构建目录手工复制到复审目录，也不能用另一个 R 的混合工作树代替本次候选。

开始 Fix 前执行：

    python E:\workspace\tools\r_fix_review.py begin-fix --batch-id B<N> --r-id R<N> --fix-id Fix<M> --workspace-root E:\workspace --code-root E:\workspace\workbuddy --review-root "E:\workbuddy 复审" --snapshot-root E:\workbuddy-snapshots

完成修复、自动化验证和构建后执行：

    python E:\workspace\tools\r_fix_review.py complete-fix --batch-id B<N> --r-id R<N> --fix-id Fix<M> --build-dir <本次构建目录> --candidate-source E:\workspace\workbuddy --candidate-base-commit <C0或本次Fix基线提交> --allowed-source-file <批准文件相对路径> --allowed-worktree-file <允许的工作区文件相对路径>

其中 allowed-source-file 是本次候选允许携带的文件集合，allowed-worktree-file 是从 begin-fix 到 complete-fix 之间允许改变的开发区文件集合；`complete-fix` 在恢复开发工作树前保存 tracked/non-ignored 完整源树、`candidate-source-manifest.json` 和 `approved-source-diff.json`，包括新增源文件。任何未归属变化都会在复制候选前停止，且不会自动恢复工作区。重复调用同一 R/Fix 时只能返回同一已完成候选，不得覆盖候选、userData、证据或状态。

成功后，工具必须生成：

- E:\workbuddy 复审\<B<N>>\R<N>-Fix<M>-only\app\：只包含本 R、本 Fix 的独立构建物；
- 同目录的启动包装、独立 userData、evidence、review-meta.json 和 control/fix-complete.json；
- E:\workbuddy-snapshots\<B<N>-R<N>-Fix<M>-begin>\：Fix 前 tracked 与 non-ignored 文件、Git index、状态和清单；
- restore-result.json：Fix 后状态归档、恢复后文件树指纹、工作区指纹和 Git 状态。

只有 restoreStatus=verified、恢复前后基线指纹一致，完整源包可复核且候选变更集合完全落在统一 Fix 批准范围内，才可交给 05。该工具只处理 workbuddy 内 tracked/non-ignored 文件；node_modules、dist、out 等忽略目录不作为恢复证据，真实用户数据目录也不得作为候选或快照来源。

07 在同一 R 文档追加 FixN 时，除既有执行事实外，必须写入 batchId、rId、fixId、baselineHead、baselineWorkspaceFingerprint、candidateDir、candidateChangedFiles、candidateSourceManifestSha256、candidateSourceTreeFingerprint、approvedDiffFingerprint、build treeFingerprint、restoreStatus、restoreEvidencePath 和 nextAction=05。07 仍不能把候选生成写成 Review 通过、QA/S 冻结或用户验收。

## 六、下一次 Fix 的开发基线

开始下一次 Fix 前，必须先确认 `E:\workbuddy 复审\current-development-pointer.json` 存在、状态为 `verified`，且当前 `E:\workspace\workbuddy` 的完整工作区指纹与指针一致。指纹不一致时停止，不能从旧工作树、旧 QA/S 或旧复审候选继续修复。

只有 C0 初始基线或明确历史迁移才可调用 `register-development-baseline`，并记录 `registrationKind` 与原因；这不是普通 Fix 的静默绕过路径。完成 Fix 后若 05 通过，固定顺序为 `15A → 15 → 14`。
