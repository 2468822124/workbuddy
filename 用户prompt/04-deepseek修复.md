# 用户 Prompt · 04 GLM+DS 修复（兼容文件名）

> **用法**：GPT 对开发单元的审查结论为「需修复」时，把本文件复制粘贴给 **GLM、DS 或二者联合执行会话**。替换 `{{unit}}`、`{{计划目录}}`。
> **文件名兼容**：文件名保留 `deepseek` 以避免既有路径断链；正文现行执行角色为 GLM+DS。
> **GLM 前置**：GLM 第一次承担代码任务且尚未完成 02A 时，先执行 `用户prompt/02A-GLM代码熟悉.md`。
> **开发单元** = 子阶段。替换值见 `00-开发单元闭环Prompt使用说明.md`。
> **严格边界**：本 Prompt 只服务 `01 → 02 → 03 → 04 → 05` 的开发单元修复。用户实测 R 的问题、统一 `FixN`、替代或删除方案一律使用 `用户prompt/07-修复用户反馈.md`；04 不读取、创建或修改 R 闭环文档，不处理用户 06 回传，不自行决定用户实测问题范围。

> **阶段门禁卡**：开启条件 = `03` 明确给出当前审查问题、原失败场景、批准/排除范围和验收条件，且输入确为开发单元；完成状态 = 修复日志和复测证据完整，`closureStatus=in-progress`、`nextAction=05`；失败回退 = 审查要求不清回 `03`，修复失败留在 `04`；若发现是用户实测 R/`FixN`，立即转 `07`，不得越界修改。

**权威依据**：
1. `{{计划目录}}/{{unit}}-全流程闭环记录.md` 的「审查」环节（GPT 写的修复要求清单 —— **唯一修复依据**）
2. `当前代码状态.md`（当前任务状态）
3. `当前审查状态.md`（GPT 审查要求与重点）
4. `规范类/技术栈规范.md`（**修复代码同样强制遵守**：分层边界/数据层铁律/目录落位；修复方案若与规范冲突，停下提出 CR 而非违规实现）

**约束**：
- 只修审查指出的问题，**不得扩大范围、不得擅自重构**未要求的部分。
- **每条修复在 `{{计划目录}}/{{unit}}-全流程闭环记录.md` 内续写「修复」环节**（按 `模板/02_日志部分/项目日志部分编写模板.md` 格式）——写清：改了什么文件、为什么、对应审查问题 #。**不再使用 `项目日志/` 文件夹。**
- 更新 `当前代码状态.md` 的核心字段（当前状态/任务概要/自测结果/已知问题/下一步）。
- 重新自测所有受影响的验收点，结果写进「修复」环节的自测表。
- 偏差/取舍同样在 `当前代码状态.md` 记录原因。
- 回写 `closureStatus=in-progress`、各验收点 `testPointStatus`、`updatedAt`、`updatedBy`、证据路径和 `nextAction=05`；不得把修复完成直接写成审查通过。
