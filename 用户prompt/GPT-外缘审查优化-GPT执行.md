## 三、核心概念（5个必知）

### 3.1 闭环三态

每个任务都有明确状态：

- ✅ **通过**：验收点全部满足，可进入下一阶段
- 🟡 **需修复**：有明确问题，修复后复审
- 🔴 **驳回**：范围、安全、核心实现失效，先恢复条件

### 3.2 角色边界

| 角色 | 职责 | 禁止 |
|------|------|------|
| **GPT** | 规格、审查、治理 | 不写产品代码 |
| **GLM+DS** | 实现、自测、修复 | 不改治理文档、不直接审查通过 |
| **用户** | 需求决策、实测、最终验收 | - |

### 3.3 分层架构

```
src/
├─ main/          主进程（业务逻辑、数据库）
│  ├─ ipc/        IPC 通道（参数校验 + Result 包装）
│  ├─ services/   业务服务
│  ├─ db/         数据层
│  │  └─ repositories/  SQL 唯一属地
├─ preload/       桥接层（零业务逻辑）
├─ renderer/      渲染进程（UI）
└─ shared/        共享类型、常量
```

**红线**：
- **SQL 只能在 repositories**
- **renderer 禁止直连数据库**

### 3.4 数据层铁律

1. **唯一真相源**：任务真相只存结构化表，禁止从 Markdown 解析任务
2. **迁移只增不改**：已发布迁移禁止修改
3. **软删除**：业务数据删除用 `isDeleted=1`，禁止物理 DELETE
4. **凭据池派生**：完成态实时查询，禁止缓存完成状态字段

### 3.5 禁止事项

- ❌ 硬编码密钥、API Key
- ❌ renderer 直连数据库或执行 SQL
- ❌ 静默吞错（catch 后无日志无返回）
- ❌ console.log 提交到代码库
- ❌ 修改已发布迁移文件

## 四、03 - GPT 审查

**前置条件**：GLM+DS 报告"实现完成"

**必读**：
- 规格（全流程闭环记录）
- 实现日志（全流程闭环记录）
- `当前代码状态.md`
- `当前审查状态.md`

**审查步骤**：

1. **核对 GLM+DS 状态**
   - 读取 `当前代码状态.md`
   - 确认任务完成、自测通过、无遗漏

2. **运行门禁三件套**
   ```bash
   npm test                    # 必须 392/392 通过
   npm run build               # 必须成功
   npx tsc -p tsconfig.node.json --noEmit
   npx tsc -p tsconfig.web.json --noEmit
   ```

3. **逐项验证规格验收点**
   - 每个验收点写：预期、实际、证据、结论

4. **检查技术边界**
   ```bash
   # SQL 只在 repositories
   rg 'db\.prepare|db\.exec' --type ts --glob '!**/repositories/**'
   
   # renderer 不直连 DB
   rg 'better-sqlite3' workbuddy/src/renderer --type ts
   
   # 无硬编码密钥
   rg 'API_KEY|password.*=.*["\']' --type ts --glob '!tests/**'
   ```

5. **GUI 验证**（如涉及 UI）
   - 启动程序，实际操作
   - 验证空态、加载态、错误态、成功态
   - 验证确认/取消、刷新/重进

6. **错误降级**
   - 构造失败场景（非法输入、网络失败、数据库不可用）
   - 确认可读反馈、不崩溃、不清空、不泄露

**输出**：审查报告（写在全流程闭环记录）

**结论**（三态）：
- ✅ **通过（开发闭环）**：所有验收点通过，无 HIGH/CRITICAL 问题
- 🟡 **需修复**：有明确可修复问题，进入 04
- 🔴 **驳回**：范围、数据、安全、隔离失效，恢复条件

## 九、常见场景处理

### 场景 1：测试失败

**问题**：`npm test` 有失败

**处理**：
1. 查看失败原因（错误消息、堆栈）
2. 判断是**实现问题**还是**测试问题**
3. 修复对应代码
4. 重新运行测试
5. 更新 `当前代码状态.md`

---

### 场景 2：构建失败

**问题**：`npm run build` 失败

**处理**：
1. 查看构建日志
2. 常见原因：
   - TypeScript 类型错误
   - 导入路径错误
   - 缺少依赖
3. 修复后重新构建
4. 验证 `out/` 目录生成正常

---

### 场景 3：类型检查有新增错误

**问题**：`tsc` 报告新的类型错误

**处理**：
1. **存量诊断允许**（已记录在基线）
2. **新增错误必须修复**
3. 修复方式：
   - 补充类型标注
   - 修正类型推断
   - 避免 `any` 逃逸

---

### 场景 4：实现偏离规格

**问题**：实现时发现规格有问题

**处理**：
1. **不要先改后解释**
2. 在实现日志中记录：
   - 规格的问题
   - 偏离的内容
   - 原因和影响
   - 补充的验收条件
3. GPT 审查时会评估是否接受偏离

---

### 场景 5：审查发现越界改动

**问题**：GPT 发现修改了不在规格范围内的代码

**处理**：
1. GPT 给出 `🔴驳回` 结论
2. GLM+DS 回退越界改动
3. 只保留规格范围内的修改
4. 重新提交审查

## 版本号规则（语义化）

- **主版本（X.0.0）**：重大架构变更（如从单 R 改为多 R 并行）
- **次版本（1.X.0）**：新增流程或规则（如新增 G1 版本级整合）
- **修订版（1.1.X）**：错误修正、澄清说明（不改变流程）

## 治理原则

1. **向后兼容优先**：新规则不影响已闭环的历史项目

3. **可追溯**：所有变更记录在本日志中
4. **最小化原则**：不强化任何要素的流程应删除
