# 12 - GPT&Claude 自主 GUI 实测（给 GPT&Claude）

> **用途**：GPT&Claude 根据一份已经批准的项目测试计划，在真实可见窗口中执行客观实测、深度回归和证据采集。
>
> **最少输入**：只需提供下面两项；版本、功能、程序入口、启动方式、测试目录、数据隔离条件、测试点和报告落点都必须从测试计划读取，不要在本 Prompt 中重复填写。
>
> **重要边界**：GPT&Claude 自主实测不是用户验收。GPT&Claude 只写 `GPT实测记录/`，不创建用户反馈文档、不创建问题闭环文档、不修改产品代码、数据库、`当前代码状态.md` 或用户测试计划结论。用户反馈由 `06-用户反馈测试问题.md` 接收，再由 `13-生成用户实测全流程闭环.md` 合并。

> **阶段门禁卡**：开启条件 = 计划 `planStatus=ready`，适用静态 `staticGate/E0=passed`，版本/S/正式入口/测试副本/报告落点可核对；完成状态必须分开记录”静态 E0 已核对””动态 T01 结果””后续测试点结果””报告状态”；失败回退 = E0 失败补 `14` 前置，T01 失败只停止依赖它的后续点并交 `13/07`，T01 未测试只能写 `not-tested/待取证`，不能写成通过或启动阻塞。

> **用户补充问题边界**：首次 GPT&Claude 实测时不得猜测用户尚未提交的”用户补充问题”，也不得把代码阅读或历史截图当作用户已执行。用户提交 06 后，如 `13` 触发补充核验，GPT&Claude 必须在同一 `S` 快照、同一测试副本中完成可安全执行的独立可见 GUI 回放或只读持久化核对；结果写入 GPT&Claude 证据目录下独立的补充核验证据文件，不覆盖本正式报告，也不新建测试点/子用例 ID。无法安全执行时必须记录环境缺口，不得将未核验写成通过或 Fix。

## 已验证成功经验参考库

以下方法来自一次真实可见窗口 GUI 实测中的成功启动闭环，后续每次执行本 Prompt 时必须先参照。它是启动与状态捕获的方法基线，不替代测试计划的路径、快照、测试点和预期，也不扩大测试范围。示例中的版本、程序、脚本、环境变量和数据目录必须以当前测试计划为准，不得跨版本照搬。

### EXP-001：先用隔离启动入口，再选择唯一可见 WorkBuddy 窗口（R1-2 已验证）

**适用条件**：测试数据隔离依赖启动脚本、包装器或进程环境变量时，隔离启动入口是正式实测入口。环境变量只对启动它的进程及其子进程继承；在文件资源管理器中直接双击同一个 exe，不等价于执行该启动入口。

**R1-2 的实际成功方法**：

1. 只读核对计划指定的测试包、启动脚本、测试数据目录和真实用户数据禁止触碰边界；确认 WorkBuddy 已关闭，或从最新窗口列表重新选择并按计划安全关闭后再继续。
2. 执行计划指定的隔离启动入口。对于当前 B1 的 R1-3/R2-1，必须先运行 `E:\workbuddy-test\选择B1实测角色.bat`，再从 `E:\workbuddy-test\启动实测.bat` 启动；该入口按 `E:\workbuddy-test\R1-3&R2-1\B1-20260829\R1-3/R2-1\GPT/USER-YYYYMMDD\userData` 映射设置 `WORKBUDDY_USER_DATA`，再启动 `E:\workbuddy-test\app-v0.3\WorkBuddy.exe`。其他计划必须以其计划正文登记的入口和数据目录为准，后续测试动作只在这个启动进程树中进行。
3. 等待窗口出现并稳定；重新调用 `list_apps()`/`list_windows()`，按计划程序路径和窗口标题筛选 WorkBuddy，必须得到唯一目标窗口。不要凭旧句柄、旧坐标或文件管理器中选中的 exe 继续操作。
4. 对唯一目标窗口获取一次新的截图和可访问性/文本状态，确认页面已进入 WorkBuddy，且能看到本轮测试前缀、首次启动状态或计划规定的初始标记。若显示另一数据源、非本轮前缀任务或疑似真实用户内容，立即停止业务实测，记录为隔离/启动阻断，不要继续点击业务控件。
5. 每次动作严格执行“最新观察 → 只发一个动作 → 立即重新观察 → 等待页面稳定”的闭环。动作成功返回只说明输入已发送，不能作为页面完成的证据。
6. 实测结束后通过可见窗口关闭 WorkBuddy，等待稳定，再用 `list_windows()` 和允许的只读进程核对确认目标窗口/进程为 `0`；只有在确认程序关闭后，才能执行计划允许的测试副本重置或其他环境操作。

**本次经验的反例和诊断结论**：R1-2 中用隔离启动入口启动时，BOOT1、I2、D1 等测试前缀数据能够恢复；关闭后从文件资源管理器直接双击同一 `WorkBuddy.exe`，窗口加载了另一数据源（可见“v0.3日规划手动任务-已改名”、顺延任务和热点内容）。因此，只要隔离依赖进程环境变量，就不得把“直接双击 exe”作为正式 GUI 实测启动方式；如计划同时列出 exe 和启动脚本，优先使用能建立隔离环境的启动脚本，并把直接 exe 仅作为计划明确要求的独立隔离边界检查。该结论已由 `GPT实测记录\v0.3实测内容\第1轮\证据\R1-2-T01-C05-直接启动隔离.png` 复核。

**启动失败时的最小恢复动作**：不要重复双击或反复发送同一动作。先重新枚举窗口和进程，确认是否存在 WorkBuddy、启动器、模态框或失效句柄；重新执行当前计划指定的隔离入口，重新选择唯一窗口并重新获取状态。若仍无法证明使用测试数据目录，写入报告的“需补充信息/阻断”并停止依赖该环境的业务测试，不得临时改用当前工作树、直接 exe、真实用户目录或内部 API。

## 一、先读取并校验

从输入取得测试计划绝对路径和测试标识后，按以下顺序只读读取：

1. 测试计划本身；
2. 测试计划列出的 `当前审查状态.md`、`当前代码状态.md`、开发单元闭环记录、版本/技术栈规范和相关用户测试流程；
3. 测试计划指定的测试专用程序入口、启动方式、测试目录、数据目录、报告路径、证据路径和本次测试点。

如果测试计划不存在、路径不是文档根下的治理文档、测试标识不匹配或字段缺失，立即停止业务实测，在报告的「需补充信息」中列出具体缺口。发现不同文档互相矛盾时，先按下方「冲突分级与 SSOT 解析」处理；只有无法解析、影响测试基线/数据安全，或直接影响当前测试点预期的冲突才停止对应测试。不得猜测、临时替换启动命令或扩大测试范围。

### 冲突分级与 SSOT 解析

1. **先判定冲突范围**：区分产品语义、当前实现状态、测试计划步骤和历史记录；一个测试点的预期不一致，不自动阻断没有依赖它的测试点。
2. **按治理总纲的真相源优先级解析产品语义**：`开发阶段项目计划/项目计划.md` > 对应阶段规格 > 适用 CR 全流程记录 > `当前代码状态.md`。`当前审查状态.md` 和闭环记录用于核对最新审查/决策状态；它们不能用历史摘要覆盖更高优先级的现行规格。
3. **低优先级旧文案冲突**：若高优先级规格、最新有日期的决策记录和当前实现状态能够形成唯一口径，则把低优先级内容标记为“待同步/过时文案”，在报告中记录冲突，但继续执行不依赖该冲突的测试点；不得在实测过程中改写文档。
4. **测试计划自身与权威规格冲突**：只阻断受影响的测试点，除非计划已有明确分支或补充说明；不得默默替换该测试点的操作/预期。其他独立测试点可以继续，并在报告中列出被阻断测试点及恢复条件。
5. **全局停止条件**：同层权威来源仍无法形成唯一口径，或冲突涉及 S 快照、程序入口、测试数据隔离、真实数据边界、损坏恢复或其他安全条件时，停止全部相关业务实测并写 `⏸️停止（需补充信息）` 或 `🔴驳回`。

1. R 计划对应功能的所有开发单元均为 `✅开发闭环`；G1 计划列出的所有纳入功能均已完成各自 R 轮次闭环；

3. 被测程序来自该 S 快照的独立构建目录，不是从可变工作树临时启动；
4. 如果这是当前目标版本第一份 R 测试计划，计划还必须能核对 `C0` 提交、Tag、版本字段和当时工作树已归档；G1 计划必须核对所有活跃 R 已关闭、双方证据齐全以及版本级整合快照；

8. 若计划要求重置数据，重置方式明确指向测试数据副本，并已确认程序关闭。
9. 测试点 ID 与计划类型一致：R 计划只能使用 `R<N>-<n>-T<NN>`，G1 计划只能使用 `G1-T<NN>`。

### 3.1 13 触发的补充核验

补充核验不属于首次 GPT 报告的预先通过项。收到 `13` 的明确触发后，应立即按问题级门禁执行：

## 四、可见窗口和证据规则

必须使用用户能看到的 WorkBuddy 窗口完成点击、键盘输入、菜单/下拉选择、页面导航、确认/取消、拖动和滚动。操作期间保持窗口可见；每个测试点执行后等待页面稳定，并记录等待条件或超时。

### 动作后的稳定反馈

- 工具调用返回成功只证明输入已发送，不证明页面已经完成路由、渲染或数据刷新。
- 每次点击、输入、选择、导航、刷新或滚动后，先立即获取一次新状态；如果没有错误但页面仍保持动作前状态，按约 `300ms` 的间隔继续观察，最多等待 `2s`，直到标题、选中态、关键文本或页面结构发生预期变化。
- 在稳定窗口出现前不得重复发送同一动作；等待上限后仍无变化，记录为“动作已发送但反馈未出现”，重新选择当前真实窗口并再诊断，不得把旧截图直接写成最终结果。
- 每次 GUI 动作只允许使用产生该动作前一份观察中的窗口、截图 ID、坐标或元素索引；页面变化后必须以最新状态继续。
- 如果状态捕获报告窗口已最小化、窗口句柄失效或没有截图，先从 `list_apps()`/`list_windows()` 重新选择唯一目标并激活，再获取新状态；不得对最小化窗口或旧句柄继续发送动作。

允许的环境核对仅限与本次测试有关的只读操作，例如进程状态、窗口信息、Git 状态、测试目录是否产生文件、测试专用数据库是否存在。严禁：

- 直接调用业务 IPC、预加载 API、HTTP 接口、数据库 SQL、SQLite 文件或内部函数代替用户操作；
- 用脚本插入、修改或删除业务数据，再把结果写成页面操作通过；
- 使用隐藏 DOM 事件、`evaluate` 调业务函数、伪造 IPC 参数或改写 `userData` 绕过 UI；
- 修改产品代码、测试程序、数据库、`当前代码状态.md`、`当前审查状态.md` 或用户实测计划；
- 用单元测试、代码阅读、历史截图、开发者自测或“工具无法操作”替代 GUI 证据。

如果原生文件对话框、日期选择器、系统确认框、安装环境或窗口操作无法在当前桌面工具中完成，写 `⚠️待用户实测`，给出用户可照做的步骤，不得伪造结果。

## 五、测试范围

严格按测试计划顺序执行：启动/恢复、计划列出的共同核心链路、GPT 客观测试项、指定回归项、错误降级和安全边界。不得自行添加测试点，不得把用户主观体验测试写成 GPT 已通过。

每个测试点都使用计划中的稳定 ID，例如 `R1-1-T01`，并在报告中完整记录：

1. **操作**：实际点击、输入、选择、确认/取消、刷新、离开后重进的步骤和非敏感输入值；
2. **预期反馈**：逐字或准确引用计划中的预期；
3. **实际反馈**：页面文本、状态、数量、跳转、持久化结果、错误信息、等待时间和异常；
4. **证据**：截图绝对路径或相对文档根路径，以及必要的只读核对输出；
5. **结论**：`✅通过`、`❌缺陷`、`⚠️待用户实测` 或 `ℹ️非本轮范围`，并标注严重度。

每个改变数据的链路至少验证一次刷新或离开后重进。涉及取消、二次确认、删除、导入覆盖或错误回退的链路，必须分别验证取消路径和确认路径。出现 `🔴阻断` 或 `🟡需修复` 后，停止所有依赖该结果的后续测试；彼此独立的安全项可继续，但必须说明依赖关系。

## 六、已知问题回归与错误降级

从测试计划的回归清单、最近 GPT 报告和开发/审查记录逐条建立回归项，记录原始复现步骤、修复后预期、本轮真实操作、实际反馈、证据和状态。只有本轮有 GUI 证据才能写“已关闭”。

只在计划明确的范围内构造失败场景，例如空输入、非法输入、无效 Key、不可达地址、取消确认、非法导入文件或缺少必填字段。每次失败都核对：有可读反馈、不崩溃/不白屏/无无限重试、原有数据未被错误清空或重复写入、非相关功能仍可用，且不泄露密钥、用户数据或内部堆栈。涉及数据库损坏、文件删除/覆盖而没有测试副本和恢复步骤时，标记 `⚠️待用户实测`，不得操作。

## 七、报告必须区分的结果

报告中分别列出：

- **已通过项**：本轮有真实 GUI 证据且符合计划的项目；
- **发现问题**：本轮真实复现的问题，包含稳定 ID、严重度、复现条件、影响和证据；
- **待用户实测项**：因主观体验、原生控件、安装环境、硬件或当前桌面工具限制而未完成的项目；
- **未测试项**：不属于本轮范围、缺少前置或因依赖问题停止的项目。

问题严重度按实际影响标注：`🔴阻断`、`🟡需修复`、`🔵一般`、`ℹ️待用户确认`。`ℹ️待用户确认` 不能写成缺陷，也不能写成通过。

### G1 专用边界

当测试标识为 `G1` 时：

- 只执行 G1 计划列出的版本级整合测试点，使用 `G1-T<NN>`，不创建或改写 R 轮次文档；
- 必须核对所有纳入的活跃 R 已关闭、双方正式证据齐全，并使用计划绑定的统一 `S` 快照；
- G1 通过只能作为形成 `C1` 的必要条件，不能在 GPT 报告中写成 `C1`、用户验收通过或项目进入维护期；
- G1 发现问题时，报告中记录客观事实和证据，后续由 `13` 判断回写现有 R 还是新建下一 R。

## 八、结论和后续

结论只能从本轮证据得出：

- `✅通过（GPT自主实测）`：本轮计划范围全部有证据通过，无未关闭的 `🔴`/`🟡` 问题；同时列出仍需用户完成的项目，并声明不等于用户验收闭环；
- `🟡需修复`：存在可复现的 `🟡` 或 `🔴` 问题，列出编号、严重度、复现步骤、证据和建议回到 `07` 修复；
- `🔴驳回`：程序无法启动、数据隔离/安全边界失效、发生数据损坏，或核心范围无法真实验证；说明停止原因和恢复条件；
- `⏸️停止（需补充信息）`：前置资料或隔离条件无法确认，列出补充清单。

不要在 GPT 报告中宣称“用户实测闭环”“用户验收通过”或“项目进入维护期”。完成后只向用户报告：测试标识、报告路径、证据目录、结论、已通过项、发现问题、待用户实测项，以及尚未由用户亲自完成验收的声明。用户完成同一测试计划后，使用 `06-用户反馈测试问题.md` 回传；双方证据由 `13-生成用户实测全流程闭环.md` 合并。
