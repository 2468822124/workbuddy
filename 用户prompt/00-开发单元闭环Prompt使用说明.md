# 00 开发单元闭环 Prompt 使用说明

> **维护方**：GPT　**作用**：01–11 prompt 的总索引 + 占位符替换查表 + **全流程文档落点规则**。
> **上位**：`规范类/文档治理总纲.md`、`规范类/变更闭环规则.md`、`规范类/阶段闭环门禁规则.md`。
> **建立日期**：2026-08-07（随「计划与复盘体系」立项增补；2026-08-12 文档结构改革后全面适配）。

---

## 一、四套闭环 + 立项/归档 prompt

| 闭环 | 适用期 | 单位 | 链路 | Prompt |
|---|---|---|---|---|
| **功能立项** | 全新功能开工前（一次） | 功能 | 需求 → 功能级项目计划 | **10** 启动 |
| **构建期** | 阶段 0–6（已完工）**及新功能子阶段开发** | 开发单元（子阶段） | 规格 → 全流程闭环记录 → 🟡? → ✅ | **01** 启动 · **02** 执行 · **03** 审查 · **04** 修复 · **05** 复审 |
| **用户实测** | 功能开发闭环后（实测撞问题） | 用户反馈N | 反馈 → 诊断 → 修复 → 复测 → 闭环 | **06** 报问题 · **07** 修反馈 |
| **维护期 CR** | 阶段 6「✅ 全部关闭（含用户实跑 E2E）」后 | CR-NNN | 变更请求 → 全流程闭环记录 → CHANGELOG | **08** 执行 · **09** 审查 |
| **Git 归档** | 某开发单元 / CR 已正式闭环、准备把当前状态写入 git 快照 | 闭环后的归档动作 | 闭环文档终态 → 状态文档同步 → git 提交 | **11** 在 git 中归档 |

> **判定用哪套**：构建期开发单元是否闭环，以该单元全流程记录的最新 GPT 复审结论、顶部当前门禁状态和 `当前审查状态.md` 为准；`当前代码状态.md` 是 DeepSeek 的实现事实和自测快照，用于真实性核对，不裁决闭环。新功能先 **10**（立项）再循环 **01–05**（子阶段）；功能开发闭环后进 **06/07**（用户实测）；阶段 6 全部关闭（含用户实跑 E2E）后改 **08/09**（维护期 CR）；某个开发单元或 CR 已达到本层级终态、需要把最新状态固化进 git 时，用 **11**。

> **11 的使用条件**：只在对应归档层级已经达到终态、相关闭环记录与 GPT 状态看板已同步、且不再需要回到适用的修复/审查流程时使用。`当前代码状态.md` 中的“实现完成，待 GPT 审查”“修复完成，待 GPT 复审”“待 GPT 复审”是允许的 DeepSeek 交审前置状态，不阻断 GPT 已判定通过的归档；只有实现/修复仍未完成、失败，或其事实与复审证据矛盾时才停止。历史章节中的旧 `🔴/🟡` 修复项在后续复审已关闭的，不算当前残留。

## 二、什么是「开发单元」与「功能级项目计划」

文档分两层：

- **功能级项目计划**（10 prompt 产出，一份功能一份）：`开发阶段/vX-{功能名}/项目计划.md`。规划整个功能——子阶段划分、功能级验收/边界、版本。**常驻活跃区，功能全部闭环后才随功能归档。**
- **开发单元 = 子阶段**（01–05 循环，每次一个子阶段）：是构建期的工作单位。原 `阶段0`…`阶段6` 已完工归档；新功能按其 `项目计划.md` 的子阶段划分推进。

## 三、占位符替换查表

01–05 用三个占位符适配任意开发单元：`{{计划目录}}`、`{{unit}}`、`{{unit名}}`（01 另用 `{{prev}}`）。

**新结构下 `{{计划目录}}` 的含义已变**：它指**功能目录**（功能级项目计划 + 各子阶段全流程文档所在），即 `开发阶段/vX-{功能名}`。

### 示例：计划与复盘体系（历史功能，已归档）

| 占位符 | 替换值 |
|---|---|
| `{{计划目录}}` | `开发阶段/v0.2-计划与复盘体系` |
| `{{unit}}` | `子阶段1` / `子阶段2` / `子阶段3` / `子阶段4` / `子阶段5` |
| `{{unit名}}` | `基建` / `计划核心` / `复盘核心` / `LLM增强` / `规划体系` |
| `{{prev}}`（仅 01） | 上一子阶段标识；`子阶段1` 填「无（首发）」 |

> 历史功能级计划（真相源，已归档）：`项目管理改革前文档记录/计划与复盘体系实现项目计划/项目计划.md`。

**下一个新功能**立项时：先用 **10 prompt** 产出 `开发阶段/vX-{功能名}/项目计划.md`，再在本 §三 旁追加该功能的占位符替换表，01–05 即可复用。

## 四、全流程单文档落点规则（核心 —— 改革后统一）

**改革铁律：一个开发单元/CR/用户反馈 = 一份全流程闭环记录文档。** 浏览这一份即可知所有过程及记录。**不再使用** `项目日志/`、`审查日志/`、`变更请求/` 等分散文件夹。

| 闭环 | 全流程文档落点 | 文档内环节（按模板续写） |
|---|---|---|
| **构建期**（子阶段） | `开发阶段/vX-{功能名}/vX-{unit}-{名}-全流程闭环记录.md` | 规格(01) → 实现日志(02) → 审查(03) → 修复(04) → 复审(05) → 闭环 |
| **用户实测**（反馈） | `用户实测阶段/vX-{功能名}-实测/vX-用户反馈{N}-{简述}-全流程闭环记录.md` | 报告(06) → 诊断(06) → 修复(07) → 复审(07) → 复测 → 闭环 |
| **维护期 CR** | `变更开发/vX-{功能名}/CR-{NNN}-{简述}-全流程闭环记录.md` | 变更请求(08起) → 变更日志(08) → 审查(09) → 复审 → 闭环 |

**环节书写规则**：
- **历史已有内容** → 旧文档**原样粘贴**入对应环节（不修改/润色），GPT 只加结构元信息（环节标题、来源文件、日期）。
- **后续新增内容** → 按 `模板/` 对应部分编写模板，在文档内**追加续写**一节：
  - 规格 / 功能级项目计划 → `模板/01_计划部分/项目计划部分编写模板.md`
  - 实现日志 → `模板/02_日志部分/项目日志部分编写模板.md`
  - CR 实现日志 → `模板/02_日志部分/变更日志部分编写模板.md`
  - 审查 / 复审 → `模板/03_审查部分/审查部分编写模板.md`
  - 用户反馈记录 → `模板/04_反馈部分/用户实测反馈部分编写模板.md`
  - CR 变更请求（规格环节）→ `模板/04_反馈部分/变更请求部分编写模板.md`

## 五、构建期闭环图（一个功能）

```
10 GPT 立项 → 产出 开发阶段/vX-{功能名}/项目计划.md（功能级，划分子阶段）
  └─ 循环每个子阶段：
     01 GPT 起 规格 → 写进 vX-{unit}-全流程闭环记录.md 的「规格」环节
       → 02 DeepSeek 实现 → 同文档续写「实现日志」环节
       → 03 GPT 审查 → 同文档续写「审查」环节
       → 🟡?  04 DeepSeek 修复 → 05 GPT 复审（仍 🟡 回 04）/ ✅ 子阶段开发闭环
     → 回 01 进下一子阶段
  └─ 全部子阶段 ✅ → 功能闭环 → 进 用户实测阶段（06/07）
```

四个子阶段全部 ✅ 后：版本 bump（按 `规范类/变更闭环规则.md §5`）+ `变更记录/CHANGELOG.md` 追加一行。

## 六、固定基准（项目级，不随开发单元变化，已归档但仍是权威）

- **总规划上位**：`项目管理改革前文档记录/开发阶段项目计划/项目计划.md`（§7 验收 / 禁止边界 / 错误降级三表）
- **视觉基准**：`项目管理改革前文档记录/开发阶段项目计划/规格-阶段0-视觉.md` + 代码根 `workbuddy/.../token.css`
- **门禁规则**：`规范类/阶段闭环门禁规则.md`（三层门禁：开发部分闭环[GPT] → 功能闭环 → 实测闭环[用户]）

> 这些基准文件虽在归档区，但仍是**活权威**——引用时用上述完整路径，不得擅自修改其内容（记录性文件一字不改）。

## 七、路径订正备忘（本次改革已统一）

- `项目规范/` → **`规范类/**
- `当前状态.md` → **`当前代码状态.md`**（DS 维护）+ **`当前审查状态.md`**（GPT 维护）
- `用户最终测试反馈/` → **`用户实测阶段/`**
- `增量开发/` → **`变更开发/`**
- `项目日志/`、`审查日志/`、`变更请求/`（分散文件夹）→ **取消**，改为全流程闭环记录文档内续写环节
- 模板：`项目计划模板.md` 等 → **`模板/0X_{部分}/{部分}编写模板.md`**
