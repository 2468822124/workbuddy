# 00 - 开发与用户实测 Prompt 使用说明

> **维护方**：GPT&Claude
> **作用**：01-16 Prompt 总索引、角色边界、最少输入和文档落点规则。
> **上位规范**：
> - L1 快速入门：`规范类/00-快速开始.md`（10分钟核心概念）
> - L2 日常流程：`规范类/01-日常开发流程.md`（1小时掌握开发流程）
> - L3 完整规范：`规范类/文档治理总纲.md`、`规范类/阶段闭环门禁规则.md`、`规范类/变更闭环规则.md`、`规范类/技术栈规范.md`
> 
> **文档根**：`E:\workspace\`。代码根通常为 `E:\workspace\workbuddy\`；治理 Markdown 不得写入代码根。

### 角色边界

- **GPT**：规格、计划、审查、复审、客观 GUI 实测、证据治理、问题分类和项目管理；不修改产品代码或 `当前代码状态.md`。
- **GLM+DS**：产品代码、自动化测试、构建/配置、开发实现/用户实测 Fix、自测、版本字段、`当前代码状态.md` 和 `规范类/命名规则.md`；开发单元用 04，用户实测 R 用 07；不修改 `当前审查状态.md` 或审查结论。
- **实际执行者记录**：每个 02/04/07/08 开始卡和日志填写 `GLM`、`DS` 或 `GLM+DS`；联合执行时写文件/命令分工，并指定当前状态文件唯一写入者。两者均不得自判 GPT 门禁通过。
- **用户**：亲自完成用户范围和共同核心链路，裁决主观体验与最终用户验收；通过 06 回传，不建立独立用户实测报告。用户可以只回传发现问题的用例；未列出的用例只表示“本次暂未发现问题”，不等于通过。

## 二、构建期闭环

新功能先用 10 产出功能级项目计划，再针对每个开发单元循环：

```text
01 规格 → 02 实现 → 03 审查 → 04 修复（如有）→ 05 复审 → ✅开发单元闭环
```

开发单元全流程记录落点：

```text
开发阶段\vX-功能名\vX-<unit>-<名称>-全流程闭环记录.md
```

构建期 `05` 以文档内容自动识别模式；构建期通过后，当前目标版本先通过 `C0` 进入功能实测前置。`当前代码状态.md` 只是真实实现快照，不裁决开发单元是否闭环；裁决以 GPT 复审和 `当前审查状态.md` 为准。代称完整定义见 `规范类/项目代称.md`。

## 三、用户实测四层编号模型

### 轮次和批次

- **`C0`**：当前目标版本全部开发单元闭环后的唯一实测基线提交；只作为开发阶段进入功能实测的门锁。
- **`S0`**：由 C0 构建的首个不可变实测快照；后续每个被测候选都必须绑定一个 S 快照。
- **`QA1/QA2`**：实测阶段 Fix/Review 后形成的候选代码状态，按当前目标版本全局递增；不强制产生 Git 提交，不代表通过或发布。
- **`S1/S2`**：分别绑定 QA1/QA2 的不可变构建快照，记录来源指纹、构建目录、构建物哈希和测试数据目录。
- **`R1/R2`**：实测处置来源轮次。可承接独立产品问题、覆盖缺口和环境/产品处置事项；同一 R 只有一份闭环文档。
- **`R1-1/R1-2`**：同一问题来源轮次内的测试计划序号。首次功能实测计划在 C0/S0 后由 `14` 创建；后续计划只在 Fix/Review 后形成 QA/S 时由 `14` 创建。“第一轮计划（2）”表示 `R1-2`，不是第二轮。
- **`Fix1/Fix2`**：GLM+DS 对同一 R 全部已批准代码修复、替代和删除事项的统一批次，始终回写轮次唯一闭环文档。
- **`Review1/Review2`**：GPT 对整个统一处理批次的复审批次，始终回写同一轮次文档；通过后交 15 冻结 QA/S。
- **`15`**：05 整批复审通过后的 QA/S 候选快照冻结，不改代码。
- **`16`**：环境/产品事项的证据和用户决策记录，不改代码、不替用户决策。
- **`G1`**：所有活跃轮次关闭后的版本级整合回归，不创建新问题轮次。
- **`G1-T<NN>`**：G1 计划内稳定测试点 ID；G1 不使用 `R` 编号。
- **`C1`**：当前版本所有活跃功能/问题轮次关闭、G1 通过、双方证据齐全且用户完成当前目标版本验收后的正式版本节点。
- **测试点 ID**：R 计划使用 `R<N>-<n>-T<NN>`，G1 计划使用 `G1-T<NN>`；必须贯穿计划、GPT 报告、用户回传和证据。

### 新规则路径

```text
用户实测阶段\vX-功能名\第N轮\vX第N轮用户实测计划（n）.md
用户实测阶段\vX-功能名\第N轮\vX-第N轮-问题概述-全流程闭环记录.md
用户实测阶段\vX-功能名\第N轮\R<N>-<n>相关证据\
GPT实测记录\vX实测内容\第N轮\vX-R<N>-<n>-GPT实测.md
GPT实测记录\vX实测内容\第N轮\证据\R<N>-<n>-<测试点>-<场景>.png
用户实测阶段\vX-版本级整合\G1\vX-G1版本级整合测试计划.md
用户实测阶段\vX-版本级整合\G1\用户证据\G1-T<NN>-<场景>.<扩展名>
GPT实测记录\vX实测内容\G1\vX-G1-GPT实测.md
GPT实测记录\vX实测内容\G1\证据\G1-T<NN>-<场景>.png
```

同一 `R<N>` 始终只有一份全流程闭环文档。R 初始化由 13 在 C0/S0 后创建骨架；首次测试计划由 14 创建。旧 v0.3 文件和旧路径原样保留；新规则只向前生效，不迁移、不重写历史审计线。

### 测试计划创建门与实测快照门

GPT 创建当前目标版本第一份可执行计划前必须只读确认并形成 `C0`：所有开发单元 `✅开发闭环`、整个工作区的非忽略变更已明确归属并提交、C0 提交号/Tag/版本字段可定位、程序入口和测试数据隔离条件明确，并由 C0 生成 `S0`。

同一版本的后续计划不以新的 Git 提交或干净工作树为门锁。Fix/Review 后如果代码、依赖或构建输入发生变化，GLM+DS 形成新的 `QA` 候选；GPT 在计划中绑定对应 `S` 快照。未提交代码允许进入候选快照，但必须记录完整工作树指纹、构建物哈希和独立构建目录。无法冻结或复核 S 时，计划只能保持 `🟡待补前置`，不能启动实测。

### 双方分工

- **GPT**：客观运行事实、深度回归、数据持久化、刷新/重进、错误降级、隔离、安全和可复现 UI/文案事实。
- **用户**：亲自完成核心链路，并评价理解成本、自然性、文案、信任感和确认/取消是否敢操作；也可报告客观缺陷。
- 共同核心链路必须由双方各自执行，GPT 通过不等于用户验收通过。

## 四、用户实测调用顺序

```text
开发单元全部闭环 → C0 → S0 → 14 创建 R<N>-1 首次功能实测计划
  → 12 GPT 自主 GUI 实测（报告/证据写 GPT实测记录）
  → 用户按同一计划执行（06 三态回传）
  → 13 合并双方证据到 R<N> 唯一闭环文档
  → 13 合并后写事项处置总表；覆盖缺口/环境/替代/删除/待核实分别分流
  → 所有事项处置完成且无阻塞：07 统一 FixN（修复/替代/删除）
  → 05 对整个 FixN Review → 15 冻结 QA/S → 14 创建同 R 下一份计划
  → 独立新增：13 续写当前 R，并新建 R<N+1> 唯一闭环；不创建 R<N+1>-1 计划
  → 新 R 统一 Fix → 05 Review → 15 QA/S 后，14 创建 R<N+1>-1 首份计划
  → 覆盖补充 R：14 可复用有效 S 创建覆盖补充计划，不伪造 QA/S
  → 无回归/无新增：关闭当前 R，等待 G1
  → 所有活跃轮次关闭后创建 G1 计划 → 12 + 用户 06 → 13 合并 G1 证据 → 用户最终验收 → C1
```

### 06 的三态

1. **发现问题**：逐条回传测试点 ID、操作、预期、实际、数据影响和证据；用户无需先判断回归/新增。可以只列出发现问题的用例；未列出的用例记为“本次暂未发现问题”，不补写通过事实。
2. **全部完成且无问题**：列出实际执行的全部测试点、共同核心链路、刷新/重进/错误场景和证据；不能只写“通过”。
3. **无法完成/环境阻塞**：记录最后可确认步骤、可见阻塞、影响范围和证据；不能写成产品通过或缺陷已确认。

### 13 的证据门

缺少 GPT 正式报告、用户正式回传、测试标识匹配或某个事项的关键事实/预期/证据时，只能停止或建立 `📝待补证据/待核实`，不得进入 Fix。问题级证据齐全仍必须等待本 R 所有事项都有终态处置；只有无待核实、环境/产品决策或用户确认阻塞，且代码/替代/删除计划完整时，才能生成统一 `FixN`。用户补充问题由 `13` 保留来源标签、建立稳定问题 ID；对可客观复核的事项必须在同一 S/测试副本中触发独立 GPT 补充核验，补充核验不得代替用户主观验收。

## 五、最少输入规则

### 12

只填：测试计划绝对路径、`R<N>-<n>` 或 `G1`。其余均从计划读取。无法确认的版本、提交、程序入口、目录、隔离、窗口或报告落点必须停止。

### 06

只需引用测试计划绝对路径和 `R<N>-<n>` 或 `G1`，再提交三态之一及实际反馈。用户可以只回传问题用例，并以 `用户补充问题 1/2/3…` 报告计划覆盖缺口或额外发现；用户证据归档到计划指定目录，不建立独立报告。

### 07

只填：轮次唯一全流程闭环文档绝对路径、`FixN`。只修复该文档修复计划明确的项目，回写同一文档；不新建问题文档、不修改测试计划结论。

### 02A

只由 GLM 首次代码执行前使用一次。固定读取文档根、代码根和当前指针，输出只读熟悉报告；不填写任务占位符，不改文件，不运行会写入工作树或数据目录的命令。

### 05

只填：权威全流程文档绝对路径、`ReviewN`。自动识别构建期或用户反馈模式；用户反馈模式通过后只进入同轮下一测试计划，不直接宣称用户验收闭环。

### 13

支持 `R 初始化`、`R 测试合并`、`G1 合并` 三种模式。R 初始化只在 C0/S0 后创建骨架，不要求计划、报告或 06；R 测试合并只读取已有计划并合并事实、事项处置和分流；G1 只回写 G1 计划。若同时有回归和新增，续写原 R 并新建下一 R 唯一闭环文档。13 不创建、续写或修改任何测试计划；收到用户补充问题后，对可客观复核事项必须在同一 S/测试副本中触发独立 GPT 客观补证并单独归档。

### 14

只填：计划创建类型、版本/功能、目标计划路径，以及首次的 C0/S0、修复后的 Fix/Review/QA/S 或覆盖补充的原 R/缺口/有效 S。14 支持首次功能实测、修复后复测、覆盖补充计划和 G1；不创建 R 闭环文档、不改写已有计划结论，也不预写 GPT 或用户实测结果。

### 15 / 16

15 只在 05 整个统一 Fix 复审通过后冻结 QA/S；16 只记录环境/产品处置证据和用户明确选择。两者都不修改代码、数据库、测试计划或原始实测报告。

## 六、模板与治理文件

- GPT 报告唯一模板：`模板\GPT实测记录模板.md`。
- 测试计划：`模板\05_实测部分\项目测试计划模板.md`。
- 测试计划创建 Prompt：`用户prompt\14-生成用户实测计划.md`。
- 用户实测轮次闭环：`模板\05_实测部分\用户实测问题全流程闭环模板.md`。
- 项目代称与版本节点：`规范类\项目代称.md`。
- 历史/反馈内容模板：`模板\04_反馈部分\用户实测反馈部分编写模板.md`，新轮次优先使用 05 实测模板。
- 构建期复审续写：`模板\03_审查部分\审查部分编写模板.md`。

### 六-A、多 R Fix 批次的自动交接

用户实测 R 的统一 Fix 使用 E:\workspace\tools\r_fix_review.py 作为机器入口：07 在 Fix 前 begin-fix，完成构建后 complete-fix；候选复制完成后仅在变化归属明确且恢复指纹一致时恢复 E:\workspace\workbuddy。批次由 finalize-batch 固定预期 R/Fix，05/13/15 通过 scan-batch 动态枚举 E:\workbuddy 复审\<B>；全部 R-only Review passed 后才 prepare-merge/complete-merge。13 创建或验证唯一 B<N>-merge 闭环，05 完成集成复审，15 只冻结最终 merge 包。

机器状态不得取代 R 文档、Review、用户 06 或 QA/S 冻结；所有步骤幂等，终态不可覆盖，真实用户数据不得进入快照、候选、userData 或证据目录。新批次闭环模板为 模板\05_实测部分\多R批次合并复审闭环模板.md。

## 七、功能闭环与维护期边界

- **功能开发闭环**：所有开发单元达到 `✅开发闭环`，仅表示可以进入实测。
- **功能用户实测闭环**：当前功能所有活跃 `R` 轮次关闭、G1 通过、GPT 客观范围和用户核心链路/主观验收均有证据；用户拥有最终验收裁决权。满足后只关闭该功能，当前版本仍须等待其他活跃功能和版本级 C1 条件。
- 单个功能闭环不等于项目进入维护期。只有全部功能和阶段 6 用户 E2E 完成后，才按 `规范类/变更闭环规则.md` 进入维护期并使用 CR。

## 八、文档写入禁区

- GPT 不编辑产品代码、数据库、`当前代码状态.md`，也不把 GPT 报告直接改写成用户反馈。
