# 15A - 最终候选同步开发基线（给 GPT）

> **用途**：在 `05` 对单 R 或多 R 批次的最终候选复审通过后，建立下一阶段可复核的开发工作树基线。15A 只负责机器同步和凭证核对，不负责代码审查、用户实测、QA/S 编号或测试计划。
>
> **固定顺序**：`05 Review 通过 → 15A 保存完整源包并受控同步 E:\workspace\workbuddy → GPT 核对同步凭证 → 15 冻结 QA/S → 14 创建后续计划`。

## 发送给 GPT 的输入

```text
批次：B<N>
候选策略：direct / merge
最终候选目录：E:\workbuddy 复审\<B>\<R>-Fix<M>-only 或 merge
Review 状态文件：<最终候选 control\review-status*.json>
产品代码根：E:\workspace\workbuddy
复审根：E:\workbuddy 复审
源包根：E:\workbuddy-snapshots
唯一权威 B/R 全流程文档：E:\workspace\用户实测阶段\<...>.md
```

路径必须指向当前批次最终候选和最新 Review 状态文件。不得把 R-only 中间候选作为多 R `merge` 候选，不得使用旧 QA/S 快照、`app.asar`、`out`、构建物或 Review 文字恢复源码。

## 一、职责边界

15A 必须：

1. 核对最新 Review 状态为 `passed`，且 Review 身份、证据、候选类型和候选构建一致；
2. 核对 B 状态、候选策略、R/Fix 集合、构建清单、完整候选源清单和批准差异指纹；
3. 调用唯一机器同步入口，将完整源树和批准差异保存到 `E:\workbuddy-snapshots\<B>-<candidate>-source-sync\`；
4. 逐文件核对当前 `E:\workspace\workbuddy` 是否仍等于候选同步前基线，只写入批准差异；
5. 核对新增文件、删除文件、同一批准文件的外部改动和 Git index/staged 冲突；
6. 核对同步后的工作树指纹、逐文件结果、只读源包、清单哈希和 `source-sync-result.json`；
7. 成功后在唯一权威 B/R 全流程文档追加“最终候选源代码同步记录”。

15A 不得代码审查、重写 Review、修改产品代码以外的无关文件、覆盖无关工作区改动、创建 Git commit/Tag/C1、冻结 QA/S、创建测试计划或把失败写成 `QA/S 已冻结`、用户通过或 `🟢等待下一轮测试`。

## 二、单 R 与多 R 规则

- 单 R：`candidateStrategy=direct`，且批次只能有一个预期 R/Fix；该 R-only 最终候选可作为 B 候选。
- 多 R：`candidateStrategy=merge`，且批次至少有两个预期 R/Fix；只有 `E:\workbuddy 复审\<B>\merge` 可同步进入 15。
- 多 R 的 R-only 候选只用于各 R 复审和 merge 集成，不得冻结 QA/S，也不得作为最终同步对象。
- `complete-merge` 必须已经生成最终 merge 候选，`developmentWorktreePreserved=true`；15A 不替代 merge 集成或 B merge Review。

## 三、固定机器命令

```text
python E:\workspace\tools\r_fix_review.py sync-final-candidate ^
  --batch-id B<N> ^
  --candidate-strategy direct|merge ^
  --candidate-dir <最终候选目录> ^
  --review-status <Review 状态文件> ^
  --code-root E:\workspace\workbuddy ^
  --review-root "E:\workbuddy 复审" ^
  --snapshot-root E:\workbuddy-snapshots
```

只允许使用此命令完成最终候选同步。命令必须先完成所有门禁，再进行任何批准差异写入；成功后重新计算工作树指纹并逐文件核验。

历史候选若没有新式 `control\source-tree`，标准命令会且只会自动发现同一批次、同一候选的 `E:\workbuddy-snapshots\<B>-<candidate>-source-recovery\`。恢复包必须已经由 `recover-history-source-package` 验证、整体只读，且候选源清单、完整源树、批准差异和候选冻结指纹全部一致；不得为标准同步命令手工拼接未登记的临时源码参数。候选元数据若显式声明了源树或批准差异路径但对应文件缺失，按篡改/缺失阻断，不得回退到恢复包。

机器结果唯一写入：

```text
E:\workbuddy 复审\<B>\control\source-sync-result.json
```

状态只能是：

- `sourceSyncStatus=verified`：同步完成、结果和指针均已核对；可交给 15；
- `sourceSyncStatus=blocked`：Review、身份、清单、基线、冲突或批准范围缺口；留在 15A；
- `sourceSyncStatus=failed`：同步写入或回滚未能完成；留在 15A，若有残留文件必须记录。

成功时同时更新：

```text
E:\workbuddy 复审\current-development-pointer.json
```

指针至少记录最新 B、候选目录、候选策略、源包路径、`HEAD`、状态、Git index 哈希、工作树指纹、候选源清单哈希、批准差异指纹和 `source-sync-result.json` 路径。

## 四、同步前后硬门禁

同步前必须逐项核对：

1. Review 状态文件是候选目录内最新终态记录，状态为 `passed`，证据路径在候选 `evidence` 内且文件哈希可复核；
2. `review-meta.json`、Review 状态、`batch-state.json` 和命令输入的 B、候选类型、候选策略、R/Fix 身份一致；
3. B 状态为 `frozen`；单 R 只有一个预期 R/Fix，多 R 只有最终 `merge` 候选；
4. 候选程序和 `build-manifest.json` 存在，构建清单内容、文件数、清单哈希和构建树指纹一致；
5. `candidate-source-manifest.json`、`review-meta.json` 以及候选原生源工件或已验证历史恢复包中的 `approved-source-diff.json`、完整源树，其清单哈希与批准差异指纹一致；
6. 候选源包完整，包括新增源文件；源包与源清单逐文件一致且不可写；
7. 当前开发树 `HEAD`、候选基线、Git index 和同步前逐文件内容仍匹配；
8. 新增文件必须确认当前目标不存在；删除文件必须确认当前目标仍是候选基线文件；Git staged/index 冲突必须单列并阻断；
9. 当前批准文件被其他修改占用时停止，不覆盖、不自动合并；无关文件必须保留。

同步只写 `approved-source-diff.json` 中列出的批准文件。同步中途失败时工具回滚已经写入的文件，并重新核对回滚指纹；回滚失败时保持 `failed`，记录残留路径，不继续 15。

## 五、完成和失败处理

### 成功

GPT 核对 `source-sync-result.json` 的 `sourceSyncStatus=verified`，确认：

- `sourcePackageReadOnly=true`；
- `candidateSourceManifestSha256`、`approvedDiffFingerprint`、同步前/后工作树指纹可复核；
- `appliedFiles` 只有批准差异；`preservedFiles` 中的无关改动仍在；
- `current-development-pointer.json` 与同步后工作树完全一致；
- 没有冲突、回滚异常、未批准文件变化或清单缺失。

然后在唯一权威文档追加“最终候选源代码同步记录”，只引用机器结果路径和其中的哈希，不另建第二套哈希事实；下一步固定为 `15`。

### 阻断或失败

保留 `source-sync-result.json`，明确缺口、冲突文件、责任人、补证路径和恢复条件。同步失败时不得修改无关工作区文件，不得继续 `15`，不得写 QA/S 冻结或后续计划状态。

## 六、下一次 Fix 的开发基线

下一次调用 `begin-fix` 前，当前 `workbuddy` 的完整工作区指纹必须等于 `current-development-pointer.json`。指针缺失、状态不是 `verified` 或指纹不一致时，工具拒绝开始 Fix。

只有 C0 初始基线或明确历史迁移才允许使用独立的 `register-development-baseline` 操作，并必须写明 `registrationKind` 和原因；不得通过删除指针、旧 QA/S 或旧快照静默绕过。

## 七、历史 S2 补证

历史 S2 不能由旧 QA/S 快照、`app.asar`、`out`、构建物或 Review 文字反向冒充源码。需要补证时，使用：

```text
python E:\workspace\tools\r_fix_review.py recover-history-source-package ^
  --batch-id B2 ^
  --candidate-dir "E:\workbuddy 复审\B2\R1-Fix2-only" ^
  --source-dir <独立恢复的完整源树> ^
  --required-source-file tests/r1Fix2.spec.ts
```

恢复源树必须逐文件匹配既有 `candidate-source-manifest.json` 和冻结的批准差异指纹。若旧候选本身已有 `approved-source-diff.json`，必须同时核对其路径、文件哈希、基线/候选清单和 changed 集合；若旧候选像 B2 一样没有该文件及其声明字段，工具只能从同一 R/Fix 的已验证 `begin-fix`/begin 快照重建，且重建结果必须匹配 `review-meta.json` 中已经冻结的 `approvedDiffFingerprint`。重建的源树和差异只写入新的只读 `source-recovery` 包，不补写或改写历史候选目录。

可审计恢复日志可用重复的 `--source-evidence <文件>` 登记路径、SHA-256 和大小，并用 `--reconstruction-note <限定说明>` 记录工具调用范围。缺少任一源文件、begin 快照不一致、冻结指纹不匹配或来源不可审计时只记录阻断，S2 保持不可使用；补证成功后，标准 `sync-final-candidate` 自动核对并采用该恢复包，仍须完成 15A/15 的新门禁，不创建 R1-5，不改写既有 QA2/S2 冻结记录或 R1-4 计划正文。
