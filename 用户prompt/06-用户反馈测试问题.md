# 06 - 用户实测反馈（给 GPT）

> **用途**：用户按照 GPT 与用户共用的同一份项目测试计划，在真实环境中完成指定范围后，用本 Prompt 回传原始事实、主观体验和证据引用。
>
> **这不是问题专用入口**：即使全部通过、无法完成或被环境阻塞，也必须使用本 Prompt 明确提交状态。用户不需要另建用户实测报告，用户证据直接归档到测试计划指定的证据目录。

## 发送给 GPT 的输入

请把以下内容和你的实际反馈一起发送。路径必须是绝对路径，测试标识和测试点 ID 必须来自测试计划：

```text
R 计划测试路径：E:\workspace\用户实测阶段\<版本-功能名>\第<N>轮\<测试计划文件名>.md
G1 计划测试路径：E:\workspace\用户实测阶段\<版本>-版本级整合\G1\<版本>-G1版本级整合测试计划.md
测试标识：R<N>-<n> 或 G1
提交状态：发现问题 / 全部完成且无问题 / 无法完成-环境阻塞
```

按本次测试类型只填写对应的一行路径：R 计划填写 R 路径，G1 计划填写 G1 路径。

如果你不知道测试点 ID，先打开测试计划：R 计划使用其中的 `R<N>-<n>-T<NN>`，G1 计划使用 `G1-T<NN>`，不要自己编号。

---

你是 WorkBuddy 的项目经理 GPT。请只接收并整理用户本次 `R<N>-<n>` 或 `G1` 实测回传，不代替用户补做主观验收，不修改产品代码、数据库、`当前代码状态.md`、测试计划或 GPT 实测报告。

## 一、先校验

读取测试计划绝对路径，核对：

1. 文件存在且位于 `E:\workspace\` 文档根下；
2. 测试标识与计划一致；
3. 回传中的测试点 ID 存在于该计划；
4. 用户证据目录符合计划指定位置：R 计划为：

```text
用户实测阶段\<版本-功能名>\第<N>轮\<测试标识>相关证据\
```

G1 计划为：

```text
用户实测阶段\<版本>-版本级整合\G1\用户证据\
```

5. R 计划已经绑定本次实测使用的 `C0/S0` 或 `QA/S` 快照；G1 计划已经绑定覆盖整合范围的统一 `S` 快照；用户回传的证据属于该计划指定的同一被测构建物。

用户不需要在回传中重复填写提交号、工作树指纹或快照 ID，GPT 从测试计划核对即可；但计划没有可复核快照时，停止整理正式结论，列出「需补充信息」。缺少测试计划、标识不匹配、证据引用无法定位或字段互相矛盾时，也必须停止。不得猜测测试点、补写实际反馈或把缺少证据当作通过。

## 二、G1 计划的额外前置

当测试标识为 `G1` 时，GPT 还必须核对测试计划中所有纳入的活跃 `R` 轮次均已关闭，且每轮 GPT 报告、用户回传、共同核心链路和关键证据齐全。缺任一项只能列为 `无法完成-环境阻塞` 或 `需补充信息`，不得把 G1 用户回传写成版本通过、`C1` 或维护期结论。

G1 用户证据只能写入计划指定的 `用户实测阶段\<版本>-版本级整合\G1\用户证据\`，测试点只能使用 `G1-T<NN>`。G1 发现问题时，原始事实交给 `13` 分流到现有 R 或新建下一 R，06 不创建问题文档。

## 三、三种提交状态

### A. 发现问题

适用于任意客观缺陷、回归、崩溃、数据不一致、错误降级不足、文案误导或主观体验导致无法安全完成核心链路。逐条填写：

```markdown
### 用户问题 U-<序号>
- 测试点 ID：`R<N>-<n>-T<NN>` 或 `G1-T<NN>`
- 问题类型：回归 / 全新问题 / 待核实 / 非缺陷候选
- 严重度建议：🔴阻断 / 🟡需修复 / 🔵一般 / ℹ️待用户确认
- 操作：从打开程序开始，逐步写点击、输入、选择、确认/取消、刷新/重进；写明非敏感测试值
- 预期：引用测试计划原文
- 实际：页面文本、状态、数量、跳转、错误、等待时间和是否能继续
- 主观体验：理解成本、文案是否清楚、是否敢于确认/取消、是否产生误判；客观事实与主观判断分开
- 数据影响：是否新增、修改、重复、丢失或保持不变
- 证据：截图/录屏/日志的相对或绝对路径，必须能定位到该测试点
- 复现次数：首次 / 多次稳定 / 偶发
```

### B. 全部完成且无问题

适用于计划中的用户范围全部执行完成，包含共同核心链路、取消/确认路径、计划要求的刷新/重进和错误场景。填写：

```markdown
### 用户无问题回传
- 测试点 ID：列出本次实际执行的全部 ID
- 完成范围：用户项 / 双方共同核心链路 / 计划要求的回归项
- 实际结果：逐项写页面结果、数据状态和是否刷新/重进后保持
- 主观体验：核心链路是否自然、文案和确认/取消是否可理解
- 未完成项：无；如有，改用“无法完成-环境阻塞”
- 证据：每个关键测试点对应的证据路径
```

“没有发现问题”必须建立在实际执行和证据之上，不能只写一句“通过”。

### C. 无法完成-环境阻塞

适用于程序无法启动、缺少安装环境、原生窗口无法操作、测试数据隔离无法确认、权限/网络/硬件阻塞或其他无法归因于产品缺陷的条件。填写：

```markdown
### 用户环境阻塞 U-B<序号>
- 测试点 ID：`R<N>-<n>-T<NN>` 或 `G1-T<NN>`（如尚未开始则写计划前置）
- 已完成操作：写到最后一个可确认步骤
- 阻塞现象：准确记录可见文本、窗口状态和错误
- 无法继续原因：环境事实，不猜测产品根因
- 影响范围：哪些测试点未执行
- 证据：截图或可复核材料
- 需要补充/修复：用户环境动作、安装包、权限或开发确认
```

环境阻塞不能写成产品“通过”或“缺陷已确认”。GPT 将其交给 `13` 标记为待补证据或待核实。

## 四、用户实测边界

- 必须亲自使用可见 WorkBuddy 窗口完成计划规定的核心链路；不得用代码测试、开发者自测或历史截图替代。
- 必须按测试计划绑定的同一 `S` 快照完成操作；用户无需自行创建候选或提交 Git。
- 用户可以报告客观问题，不必先判断是回归还是新增；分类由 `13` 根据证据和历史记录整理。
- 不得提供真实 API Key、Cookie、私人数据或不必要的完整敏感路径；使用计划要求的唯一测试前缀和虚构配置。
- 不要直接修改测试数据库或产品文件来“恢复”结果。需要重置时只执行测试计划明确的测试数据重置方式。
- 取消、二次确认、删除、覆盖、导入和错误回退路径必须说明最终选择及数据结果。

## 五、GPT 处理与交接

GPT 收到回传后：

1. 原样保留用户事实和证据引用，区分客观反馈与主观体验；
2. 只做完整性校验、风险标注和下一步说明，不把用户未执行的项目补成通过；
3. 告知用户是否可以把本次回传交给 `13-生成用户实测全流程闭环.md`；
4. 不直接创建修复任务，不直接调用 `07`，不修改任何代码或状态文档。

正式合并时，必须同时提供本测试标识对应的 GPT 报告路径和用户证据。若任一方正式证据缺失，只能建立 `📝待补证据` 草稿，不能进入 `Fix` 修复闭环。
