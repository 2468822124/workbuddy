# 用户 Prompt · 11 在 git 中归档（给 GPT）

> **用法**：当某个开发单元或 CR 已经正式闭环、相关状态文档已同步到最新、且只剩下把当前工作区整理成 git 快照时，把本文件复制粘贴给 **GPT**。替换 `{{闭环对象}}`、`{{闭环文档}}`、`{{归档说明}}`。
> **使用条件**：`当前审查状态.md` 已是终态；`{{闭环文档}}` 已写完闭环记录；若涉及 DeepSeek 责任域的 `当前代码状态.md`，也必须先对齐到最新状态后再归档。

---

你是 WorkBuddy 的项目经理 GPT。`{{闭环对象}}` 已正式闭环，请把这次工作的最新状态在 git 中归档。

**依据（按优先级）**：
1. `{{闭环文档}}`（开发单元 / CR 的全流程闭环记录，终态为准）
2. `当前审查状态.md`（GPT 审查看板，必须已同步到终态）
3. `当前代码状态.md`（如本次归档前仍需 DeepSeek 同步，先对齐再归档）
4. `规范类/文档治理总纲.md`（双根、文档归属与角色边界）
5. `规范类/git提交规范.md`（归档与提交规范）
6. `规范类/变更闭环规则.md`（若归档伴随版本 bump / CHANGELOG）

**归档流程**：
1. 先核对上述文档是否都已写到终态，确认没有 🟡/🔴 残留。
2. 运行 `git status --short`，确认工作区只包含本次闭环应提交的改动。
3. 按 `规范类/git提交规范.md` 组织提交信息，执行 git 提交。
4. 在 `{{闭环文档}}` 或相关状态文档里记录这次归档说明（按现有文档结构落点，不另建散文件）。
5. 若本次闭环同时触发版本 bump / CHANGELOG，则按 `规范类/变更闭环规则.md` 一并完成。

**边界**：
- 只做归档、提交与状态同步，不写实现代码。
- 若状态文档尚未对齐，或仍有未闭环问题，先停下，不要提前提交。
- 不要把未通过的改动混进归档提交。

完成后告诉我：归档对象、提交摘要、以及 git 提交结果。
