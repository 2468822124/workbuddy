# 用户 Prompt · 11 在 git 中归档（给 GPT）

> **用法**：仅在闭环对象已达到本次归档层级的终态、相关证据已记录完成，且需要把当前工作区固化为 git 快照时使用。替换 `{{闭环对象}}`、`{{闭环层级}}`、`{{闭环文档}}` 和 `{{归档说明}}`。
> **角色边界**：本 Prompt 只执行归档、提交和当前状态同步，不实现功能、不代替审查/复审、不代替用户实测。`当前代码状态.md` 由 DeepSeek 维护，GPT 只读。

---

你是 WorkBuddy 的项目经理 GPT。请将 `{{闭环对象}}` 的最新闭环状态归档到 git。

本次归档说明：`{{归档说明}}`

## 归档层级

本次归档层级为：`{{闭环层级}}`

可选值：

- `开发单元`
- `功能开发闭环`
- `用户实测闭环`
- `维护期 CR`

只能按本次归档层级判断门禁，不得把开发闭环、功能闭环和用户实测闭环混为一谈。

## 权威依据与状态职责

按以下顺序读取并判断：

1. `{{闭环文档}}`：以顶部「当前门禁状态」、`## 当前门禁状态` 下的当前门禁层级，以及最后一个正式「复审」或「闭环」结论为准。
2. `当前审查状态.md`：GPT 的当前审查/门禁裁决。
3. `当前代码状态.md`：DeepSeek 的实现事实、自测和代码真实性快照，仅用于核对，不裁决闭环。
4. 功能级 `项目计划.md`：范围、功能级验收、版本和用户实测边界。
5. `规范类/文档治理总纲.md`：双根、文档归属和角色边界。
6. `规范类/git提交规范.md`：归档与提交规则。
7. `规范类/变更闭环规则.md`：仅在涉及功能验收、版本 bump、CHANGELOG 或维护期 CR 时读取和执行。

明确遵守以下状态权威顺序：

| 状态 | 权威文档 | 作用 |
|---|---|---|
| 开发单元最终结论 | 全流程记录的最新正式「复审/闭环」结论及当前门禁状态 | 判断开发单元是否 `✅开发闭环` |
| GPT 门禁裁决 | `当前审查状态.md` | 确认 GPT 是否通过 |
| 实现事实快照 | `当前代码状态.md` | 核对 DeepSeek 实现、自测和代码真实性，不裁决闭环 |
| 功能/版本状态 | 功能级计划、用户实测记录、变更闭环规则 | 判断是否进入用户实测、是否 bump 版本 |

## 一、终态检查

### A. 归档层级为「开发单元」

必须同时满足：

- 全流程记录最后一个正式复审结论为 `✅通过（本子阶段开发闭环）`，或文档现行模板明确等价的 `✅开发闭环` 结论。
- 全流程记录顶部「当前门禁状态」为 `✅开发闭环`。
- 全流程记录 `## 当前门禁状态` 下的当前门禁层级为 `✅开发闭环`。
- 全流程记录「文档元信息」中的当前阶段状态为 `✅开发闭环`，或与顶部状态明确等价。
- `当前审查状态.md` 的当前审查状态为 `✅通过（本子阶段开发闭环）`，或明确等价的 GPT 通过结论。
- 当前有效的验收、复审和门禁信息中不存在未关闭的 HIGH/CRITICAL 问题。
- 当前没有要求回到 04/05 的修复或复审动作。

历史首审、复审1、修复要求或其他审计章节中已经被后续复审明确关闭的 `🔴/🟡`，不算当前残留问题；不得通过全文搜索历史徽标来否定最新终态。

### B. 归档层级为「功能开发闭环」

必须确认功能级 `项目计划.md` 所列该功能的全部开发单元均已达到 `✅开发闭环`，并按功能级计划确认范围和验收已完成。仅有单个开发单元通过时，不得宣称功能开发闭环。

### C. 归档层级为「用户实测闭环」

必须确认用户实测记录存在明确的 `✅验收闭环` 结论，并且用户实测发现的问题已经完成修复和复测。GPT 的开发通过结论不能替代用户实测裁决。

### D. 归档层级为「维护期 CR」

必须确认对应 CR 的全流程记录已由适用的 GPT 审查/复审流程关闭，并核对 CR 范围、回归证据、版本和 CHANGELOG 要求。若 CR 触发用户实测或版本闭环，按对应规范一并满足。

### E. `当前代码状态.md` 的特殊规则

`当前代码状态.md` 是 DeepSeek 的审查前置快照，不是 GPT 终态看板。以下状态本身不阻断已经由 GPT 判定通过的归档：

- `实现完成，待 GPT 审查`
- `修复完成，待 GPT 复审`
- `待 GPT 审查`
- `待 GPT 复审`

只要全流程记录的最新正式结论和 `当前审查状态.md` 均已由 GPT 判定通过，上述交审标记仍可作为审查前置快照保留。

以下情况必须停止归档，并说明证据：

- 快照仍写着实现中、修复中、失败、未完成或其他明确未完成状态。
- 快照中的自测结果与代码、测试或复审证据不符。
- 快照所述实现范围与全流程记录、工作区代码不一致。
- 快照记录了尚未交给 GPT 审查/复审的阻断问题。

GPT 不得修改 `当前代码状态.md`。需要 DeepSeek 对齐时，停止归档并要求 DeepSeek 更新；不得用 GPT 修改代替责任域同步。

## 二、当前元信息一致性

检查 `{{闭环文档}}` 中 GPT 维护的当前字段：

- 文档顶部「当前门禁状态」
- `## 当前门禁状态` 下的当前门禁层级和状态说明
- `文档元信息`中的本阶段/当前阶段状态
- 最后一个正式「复审」或「闭环」结论

若当前元信息互相矛盾，例如顶部为 `✅开发闭环`、文档元信息仍为 `🔴驳回`：

- 只修正当前字段，使其与最新 GPT 裁决一致；
- 保留历史审查、修复和复审段落原文，不重写历史证据；
- 在归档说明中记录修正了哪些当前字段及原因。

## 三、功能和版本边界

- `✅开发闭环` 只表示代码开发阶段完成，不自动表示功能开发闭环或用户实测闭环。
- 开发单元归档不自动 bump 版本、不自动修改 CHANGELOG。
- 只有功能级计划和 `规范类/变更闭环规则.md` 明确要求，且对应用户实测结论达到 `✅验收闭环` 时，才执行版本 bump 和 CHANGELOG 更新。
- 若本次仅达到 `✅开发闭环`，归档说明必须写明：`用户实测闭环另行进行`。

## 四、工作区范围检查

先运行并记录：

```text
git status --short
git diff --name-only
git diff --stat
```

将变更分为：

1. `{{闭环对象}}` 的代码和测试；
2. `{{闭环对象}}` 的全流程记录、`当前审查状态.md` 和必要的治理/版本文档；
3. 与本次闭环对象无关的既有改动。

只允许提交第 1、2 类。发现第 3 类时：

- 不得使用 `git add -A`；
- 不得删除、还原、覆盖或清理用户已有改动；
- 先列出越界文件和归属判断，停止提交，等待用户确定提交范围。

若工作区包含本次对象在最后一次 GPT 复审之后新增的代码或测试改动，不能直接归档；必须回到适用的审查/复审流程重新验证。

## 五、提交前检查

- 确认所有待提交代码和测试都能在全流程记录的实现日志、修复日志或文件清单中找到依据。
- 确认没有代码改动发生在最后一次 GPT 复审之后；若有，停止并回到 03/05。
- 运行 `git diff --check`。
- 不重复执行审查；归档只固化已经形成的证据和裁决。
- 遵守双根规则：治理文档写在文档根，产品代码写在代码根，不在代码根创建治理文档副本。

## 六、提交方式

若本次同时包含已通过的代码/测试和闭环文档：

1. 先提交主体快照，提交信息使用 Conventional Commit，例如：

   ```text
   feat(stage6): close legacy module cutover
   ```

2. 在 `{{闭环文档}}` 末尾追加以下小节，不另建散文件：

   ```md
   #### Git 归档记录
   - 归档对象：{{闭环对象}}
   - 归档层级：{{闭环层级}}
   - 归档日期：YYYY-MM-DD
   - GPT 最终裁决来源：{{闭环文档}} 最新复审/闭环结论；当前审查状态.md
   - DeepSeek 状态文件：当前代码状态.md 作为审查前置快照保留，未由 GPT 修改
   - 主体提交 hash：<填写主体提交 hash>
   - 工作区结果：<填写 git status --short 结果>
   ```

3. 再提交归档记录，提交信息例如：

   ```text
   docs(archive): record stage6 git archive
   ```

若只有文档状态同步，使用：

```text
docs(archive): record `{{闭环对象}}` closure
```

若本次确实达到功能/用户实测/CR 的版本闭环，按 `规范类/变更闭环规则.md` 完成版本和 CHANGELOG 后再归档；不得因开发单元归档自行 bump 版本。

## 七、完成报告

完成后必须报告：

- 归档对象和归档层级；
- GPT 最终裁决来源；
- `当前代码状态.md` 是否仅作为 DeepSeek 前置证据保留；
- 主体提交和归档记录提交的 hash、提交摘要及 git 结果；
- 是否执行版本 bump / CHANGELOG，以及原因；
- 最终 `git status --short` 是否为空。

若门禁未通过、当前状态文档存在无法修正的矛盾、工作区包含无法归属的改动、复审后有未验证代码改动，必须停止提交并说明具体阻断项。
