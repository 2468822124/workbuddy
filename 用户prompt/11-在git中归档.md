# 用户 Prompt · 11 在 git 中归档（给 GPT）

> **用法**：仅在闭环对象已达到本次归档层级的终态、相关证据已记录完成，且需要把当前工作区固化为 git 快照时使用。替换 `{{闭环对象}}`、`{{闭环层级}}`、`{{闭环文档}}` 和 `{{归档说明}}`。项目节点定义见 `规范类/项目代称.md`。
> **角色边界**：本 Prompt 只执行归档、提交和当前状态同步，不实现功能、不代替审查/复审、不代替用户实测。`当前代码状态.md` 由 GLM+DS 维护，GPT 只读。

> **阶段门禁卡**：开启条件 = 目标对象已达到本次归档层级的正式终态，且能从当前指针和权威文档定位最新结论；完成状态 = 归属检查、提交/Tag（如适用）、归档记录和当前快照同步完成；失败回退 = 回到产生该终态的业务阶段，不能修改冻结历史、覆盖旧结论或把历史顶部状态当作当前状态。

---

你是 WorkBuddy 的项目经理 GPT。请将 `{{闭环对象}}` 的最新闭环状态归档到 git。

本次归档说明：`{{归档说明}}`

## 归档层级

本次归档层级为：`{{闭环层级}}`

可选值：

- `开发单元`
- `C0 实测基线`
- `QA 候选归档（可选）`
- `功能开发闭环`
- `用户实测闭环`
- `C1 正式版本`
- `维护期 CR`

只能按本次归档层级判断门禁，不得把开发闭环、功能闭环和用户实测闭环混为一谈。

## 权威依据与状态职责

按以下顺序读取并判断：

1. `{{闭环文档}}`：读取文档底部最新正式「复审」或「闭环」结论，并核对当前元信息和 `当前审查状态.md` 指针；顶部「当前门禁状态」只作历史/元信息，不能单独覆盖底部结论。
2. `当前审查状态.md`：GPT 的当前审查/门禁裁决。
3. `当前代码状态.md`：GLM+DS 的实现事实、自测和代码真实性快照，仅用于核对，不裁决闭环。
4. 功能级 `项目计划.md`：范围、功能级验收、版本和用户实测边界。
5. `规范类/文档治理总纲.md`：双根、文档归属和角色边界。
6. `规范类/git提交规范.md`：归档与提交规则。
7. `规范类/变更闭环规则.md`：仅在涉及功能验收、版本 bump、CHANGELOG 或维护期 CR 时读取和执行。
8. `规范类/项目代称.md`：核对 C0、QA、S、G1、C1 的节点和版本口径。

明确遵守以下状态权威顺序：

| 状态 | 权威文档 | 作用 |
|---|---|---|
| 开发单元最终结论 | 全流程记录的最新正式「复审/闭环」结论及当前门禁状态 | 判断开发单元是否 `✅开发闭环` |
| GPT 门禁裁决 | `当前审查状态.md` | 确认 GPT 是否通过 |
| 实现事实快照 | `当前代码状态.md` | 核对 GLM+DS 实现、自测和代码真实性，不裁决闭环 |
| 功能/版本状态 | 功能级计划、用户实测记录、变更闭环规则 | 判断是否进入用户实测、是否 bump 版本 |

## 一、终态检查

### A. 归档层级为「开发单元」

必须同时满足：

- 全流程记录最后一个正式复审结论为 `✅通过（本子阶段开发闭环）`，或文档现行模板明确等价的 `✅开发闭环` 结论。
- 全流程记录当前元信息与底部最新正式结论均为 `✅开发闭环`；顶部旧状态不能单独裁决。
- 全流程记录 `## 当前门禁状态` 下的当前门禁层级为 `✅开发闭环`。
- 全流程记录「文档元信息」中的当前阶段状态为 `✅开发闭环`，或与顶部状态明确等价。
- `当前审查状态.md` 的当前审查状态为 `✅通过（本子阶段开发闭环）`，或明确等价的 GPT 通过结论。
- 当前有效的验收、复审和门禁信息中不存在未关闭的 HIGH/CRITICAL 问题。
- 当前没有要求回到 04/05 的修复或复审动作。

历史首审、复审1、修复要求或其他审计章节中已经被后续复审明确关闭的 `🔴/🟡`，不算当前残留问题；不得通过全文搜索历史徽标来否定最新终态。

### B. 归档层级为「功能开发闭环」

必须确认功能级 `项目计划.md` 所列该功能的全部开发单元均已达到 `✅开发闭环`，并按功能级计划确认范围和验收已完成。仅有单个开发单元通过时，不得宣称功能开发闭环。

### C. 归档层级为「用户实测闭环」

必须确认用户实测记录存在明确的 `✅验收闭环` 结论，并且用户实测发现的问题已经完成修复和复测。GPT 的开发通过结论不能替代用户实测裁决。

问题级 Fix 或“本次暂未发现问题”不构成用户实测闭环；未列用户用例、待核实项、计划覆盖缺口或未完成的共同核心链路仍阻止该归档层级。

### D. 归档层级为「维护期 CR」

必须确认对应 CR 的全流程记录已由适用的 GPT 审查/复审流程关闭，并核对 CR 范围、回归证据、版本和 CHANGELOG 要求。若 CR 触发用户实测或版本闭环，按对应规范一并满足。

### E. 归档层级为「C0 实测基线」

必须同时确认：

- 当前目标版本范围内所有开发单元均为 `✅开发闭环`；
- 整个 `E:\workspace` 工作区的所有非忽略变更均已明确归属；无法归属的变更必须停止，不能擅自提交、删除或还原；
- GLM+DS 已将代码版本字段更新为对应预发布号，例如 `0.3.0-c0`；GPT 只读核验；
- C0 主体提交内容、提交号、构建标识和 C0 Tag 可定位；
- C0 已生成 `S0`，并记录构建物哈希、独立构建目录和测试数据隔离；
- 本次归档只表示“开发进入功能实测”，不表示 GPT 实测通过、用户验收通过或正式发布。

C0 通过后，GPT 通过 `用户prompt/14-生成用户实测计划.md` 创建当前目标版本第一份 `R<N>-1` 可执行测试计划。后续 Fix/Review 不回到 C0，也不因创建下一份测试计划强制提交 Git；后续计划同样必须由 `14` 在新的 QA/S 形成后创建。

### F. 归档层级为「QA 候选归档（可选）」

- QA 不是实测下一次的强制 Git 门锁，默认由测试计划和 GPT 报告记录 `QA` 状态及其对应 `S` 快照。
- 只有需要把候选状态固化为可定位提交时才使用本 Prompt；未提交候选不得伪造 QA Tag，必须记录完整工作树指纹。
- QA 归档不执行正式版本 bump，不修改 CHANGELOG，不得宣称通过或可发布。

### G. 归档层级为「C1 正式版本」

必须同时确认：

- 当前目标版本的所有活跃 `R` 轮次均已关闭；
- GPT 客观报告、用户共同核心链路和用户范围证据均已齐全并合并；
- `G1` 版本级整合回归通过，且没有未关闭的阻断/需修复问题；
- 用户已作出当前目标版本的最终验收裁决；
- GLM+DS 已将版本字段更新为正式版本，例如 `0.3.0`；
- `CHANGELOG` 已写完，C1 正式 Tag 和主体提交可定位。

C1 才是当前目标版本的正式节点。单个功能用户实测闭环、GPT 自主实测通过或 QA Tag 都不能替代 C1。

### H. `当前代码状态.md` 的特殊规则

`当前代码状态.md` 是 GLM+DS 的审查前置快照，不是 GPT 终态看板。以下状态本身不阻断已经由 GPT 判定通过的归档：

- `实现完成，待 GPT 审查`
- `修复完成，待 GPT 复审`
- `待 GPT 审查`
- `待 GPT 复审`

只要全流程记录的最新正式结论和 `当前审查状态.md` 均已由 GPT 判定通过，上述交审标记仍可作为审查前置快照保留。

以下情况必须停止归档，并说明证据：

- 快照仍写着实现中、修复中、失败、未完成或其他明确未完成状态。
- 快照中的自测结果与代码、测试或复审证据不符。
- 快照所述实现范围与全流程记录、工作区代码不一致。
- 快照记录了尚未交给 GPT 审查/复审的阻断问题。

GPT 不得修改 `当前代码状态.md`。需要 GLM+DS 对齐时，停止归档并要求 GLM+DS 更新；不得用 GPT 修改代替责任域同步。

## 二、当前元信息一致性

检查 `{{闭环文档}}` 中 GPT 维护的当前字段：

- 文档顶部「当前门禁状态」
- `## 当前门禁状态` 下的当前门禁层级和状态说明
- `文档元信息`中的本阶段/当前阶段状态
- 最后一个正式「复审」或「闭环」结论

若当前元信息互相矛盾，例如顶部为 `✅开发闭环`、文档元信息仍为 `🔴驳回`：

- 只修正当前字段，使其与最新 GPT 裁决一致；
- 保留历史审查、修复和复审段落原文，不重写历史证据；
- 在归档说明中记录修正了哪些当前字段及原因。

若全流程文档存在多份历史状态，归档前必须在记录中写明：读取的底部最新正式结论位置、当前指针路径、适用的 `planStatus/staticGate/testPointStatus/closureStatus`、`updatedAt`、证据和下一步。冻结文档、历史计划、历史报告、冻结 QA/S、历史证据和数据库不得修改；本 Prompt 只能处理现行归档元信息和新增归档记录。

## 三、功能和版本边界

- `✅开发闭环` 只表示代码开发阶段完成，不自动表示功能开发闭环或用户实测闭环。
- 开发单元和 C0 归档不创建正式版本，不把 `0.3.0-c0` 当作正式发布；C0 的预发布字段由 GLM+DS 先同步。
- QA 归档不 bump 正式版本、不修改 CHANGELOG。
- 只有当前目标版本达到 C1，或 `规范类/变更闭环规则.md` 对维护期 CR 明确要求时，才执行正式版本 bump 和 CHANGELOG 更新。
- 若本次仅达到 `✅开发闭环`，归档说明必须写明：`用户实测闭环另行进行`。

## 四、工作区范围检查

先运行并记录：

```text
git status --short
git diff --name-only
git diff --stat
```

将变更分为：

1. `{{闭环对象}}` 的代码和测试；
2. `{{闭环对象}}` 的全流程记录、`当前审查状态.md` 和必要的治理/版本文档；
3. 与本次闭环对象无关的既有改动。

只允许提交第 1、2 类。发现第 3 类时：

- 不得使用 `git add -A`；
- 不得删除、还原、覆盖或清理用户已有改动；
- 先列出越界文件和归属判断，停止提交，等待用户确定提交范围。

若工作区包含本次对象在最后一次 GPT 复审之后新增的代码或测试改动，不能直接归档；必须回到适用的审查/复审流程重新验证。

## 五、提交前检查

- 确认所有待提交代码和测试都能在全流程记录的实现日志、修复日志或文件清单中找到依据。
- 确认没有代码改动发生在最后一次 GPT 复审之后；若有，停止并回到 03/05。
- 运行 `git diff --check`。
- 不重复执行审查；归档只固化已经形成的证据和裁决。
- 遵守双根规则：治理文档写在文档根，产品代码写在代码根，不在代码根创建治理文档副本。

## 六、提交方式

若本次同时包含已通过的代码/测试和闭环文档：

1. 先提交主体快照，提交信息使用 Conventional Commit，例如：

   ```text
   feat(stage6): close legacy module cutover
   ```

2. 在 `{{闭环文档}}` 末尾追加以下小节，不另建散文件：

   ```md
   #### Git 归档记录
   - 归档对象：{{闭环对象}}
   - 归档层级：{{闭环层级}}
   - 归档日期：YYYY-MM-DD
   - GPT 最终裁决来源：{{闭环文档}} 最新复审/闭环结论；当前审查状态.md
   - GLM+DS 状态文件：当前代码状态.md 作为审查前置快照保留，未由 GPT 修改
   - 主体提交 hash：<填写主体提交 hash>
   - 工作区结果：<填写 git status --short 结果>
   ```

3. 再提交归档记录，提交信息例如：

   ```text
   docs(archive): record stage6 git archive
   ```

若只有文档状态同步，使用：

```text
docs(archive): record `{{闭环对象}}` closure
```

若本次确实达到 C1、功能用户实测闭环或 CR 的版本闭环，按适用规范完成版本和 CHANGELOG 后再归档；不得因开发单元、C0 或 QA 归档自行宣布正式发布。

## 七、完成报告

完成后必须报告：

- 归档对象和归档层级；
- GPT 最终裁决来源；
- `当前代码状态.md` 是否仅作为 GLM+DS 前置证据保留；
- 主体提交和归档记录提交的 hash、提交摘要及 git 结果；
- 是否执行版本 bump / CHANGELOG，以及原因；
- 最终 `git status --short` 是否为空。

若门禁未通过、当前状态文档存在无法修正的矛盾、工作区包含无法归属的改动、复审后有未验证代码改动，必须停止提交并说明具体阻断项。
