# git 提交规范

> **维护方**：GPT（项目经理）
> **作用**：定义 WorkBuddy 在 git 中同步最新状态、形成归档快照、以及提交消息的基本规则。
> **生效日期**：2026-08-16
> **配套**：`用户prompt/11-在git中归档.md`、`规范类/文档治理总纲.md`、`规范类/变更闭环规则.md`

---

## 1. 适用场景

- 开发单元已通过，准备把当前闭环状态写入 git。
- 维护期 CR 已关闭，准备记录版本 bump / CHANGELOG / 归档快照。
- 需要把 GPT 维护的状态文档与 DeepSeek 交付结果一起同步到仓库历史。

## 2. 使用条件

满足以下条件后，才可使用 `用户prompt/11-在git中归档.md`：

1. 对应开发单元或 CR 已正式闭环，结论为 ✅。
2. `{{闭环文档}}` 的终态已写完。
3. `当前审查状态.md` 已同步到终态。
4. `当前代码状态.md` 的实现事实与代码、测试及闭环证据一致；其“待 GPT 审查/复审”标记不覆盖 GPT 的最终裁决。
5. 工作区中没有当前仍需回到 04/05/08/09 处理的阻断项。

### 2.4 DeepSeek 状态快照与 GPT 终态裁决

- `当前代码状态.md` 是 DeepSeek 维护的实现事实、自测和代码状态快照，属于 GPT 审查前置输入，不是 GPT 的终态看板。
- `实现完成，待 GPT 审查`、`修复完成，待 GPT 复审`、`待 GPT 审查`、`待 GPT 复审` 是允许的交审状态；只要全流程记录的最新 GPT 复审结论和 `当前审查状态.md` 均已通过，就不单独阻断归档。
- 开发单元是否达到 `✅开发闭环`，以全流程记录最新正式复审/闭环结论、顶部当前门禁状态及 `当前审查状态.md` 为准。
- 只有 `当前代码状态.md` 明确写着实现中、修复中、失败、未完成，或其自测/实现范围与代码和 GPT 复审证据矛盾时，才构成归档阻断；此时要求 DeepSeek 对齐，不由 GPT 修改该文件。
- 全流程记录历史审查、复审和修复章节中的 `🔴/🟡` 是审计证据，不得脱离最后正式结论作为当前残留问题。

## 3. 不得使用

- 本次归档层级仍在实现、审查、复审或修复中。
- 对应层级仍需要额外的 GPT 审查/复审确认，或存在当前有效的阻断级问题。
- 工作区存在越界改动，或状态文档的当前元信息无法与最终裁决对齐。
- 仅达到 `✅开发闭环` 却把本次操作宣称为用户实测闭环；用户 GUI E2E 仍属于用户实测层级，除非本次归档层级明确为用户实测闭环且已有用户裁决。

## 4. 提交前检查

- 运行 `git status --short`，确认只保留应提交项。
- 确认变更都能在闭环文档、状态文档或版本文档里找到依据。
- 若有版本 bump / CHANGELOG，先把相关文档写完，再提交。

## 5. 提交消息

- 采用 Conventional Commit 风格：`type(scope): summary`
- 归档提交优先使用 `docs(archive): ...` 或 `chore(archive): ...`
- 若提交主要是闭环后的文档与状态同步，`scope` 可写 `stage3`、`cr-xxx`、`archive`
- 如果本次提交同时包含代码与文档，提交摘要要先说明闭环对象，再说明归档结果

## 6. 边界

- 不要用归档提交替代审查、复审或用户实测。
- 不要把未通过的内容混进归档提交。
- 不要擅自改动 DeepSeek 责任域的状态文件。
