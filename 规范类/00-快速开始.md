# WorkBuddy 快速开始（10分钟入门）

> **版本**：v1.2.0  
> **目标受众**：新接手的开发者、AI 协作者  
> **学习时间**：10 分钟  
> **下一步**：[日常开发流程](./01-日常开发流程.md)（1小时掌握）

---

## 一、项目概览

WorkBuddy 是一个 **Electron + Vue 3 + TypeScript** 的桌面应用，采用 **多 AI 协作**的 vibe coding 模式：

- **GPT**：项目经理、规格编写、审查
- **GLM+DS**：编码实现、自动化测试
- **用户**：需求决策、真实窗口实测

当前版本：**v0.3 任务数据流通重构**

---

## 二、双根规则（最重要）

项目有两个根目录，**必须区分**：

| 根 | 路径 | 存放内容 |
|---|---|---|
| **文档根** | `E:\workspace\` | 所有 `.md` 治理文档、规格、测试计划 |
| **代码根** | `E:\workspace\workbuddy\` | 代码（`src/`、`tests/`）、构建配置 |

**铁律**：
- 所有文档路径相对**文档根**
- GLM+DS 在代码根工作时，写文档必须回到文档根
- 代码根下不得存放治理文档副本

## 三、核心概念（5个必知）

### 3.1 闭环三态

每个任务都有明确状态：

- ✅ **通过**：验收点全部满足，可进入下一阶段
- 🟡 **需修复**：有明确问题，修复后复审
- 🔴 **驳回**：范围、安全、核心实现失效，先恢复条件

### 3.2 角色边界

| 角色 | 职责 | 禁止 |
|------|------|------|
| **GPT** | 规格、审查、治理 | 不写产品代码 |
| **GLM+DS** | 实现、自测、修复 | 不改治理文档、不直接审查通过 |
| **用户** | 需求决策、实测、最终验收 | - |

### 3.3 分层架构

```
src/
├─ main/          主进程（业务逻辑、数据库）
│  ├─ ipc/        IPC 通道（参数校验 + Result 包装）
│  ├─ services/   业务服务
│  ├─ db/         数据层
│  │  └─ repositories/  SQL 唯一属地
├─ preload/       桥接层（零业务逻辑）
├─ renderer/      渲染进程（UI）
└─ shared/        共享类型、常量
```

**红线**：
- **SQL 只能在 repositories**
- **renderer 禁止直连数据库**

### 3.4 数据层铁律

1. **唯一真相源**：任务真相只存结构化表，禁止从 Markdown 解析任务
2. **迁移只增不改**：已发布迁移禁止修改
3. **软删除**：业务数据删除用 `isDeleted=1`，禁止物理 DELETE
4. **凭据池派生**：完成态实时查询，禁止缓存完成状态字段

### 3.5 禁止事项

- ❌ 硬编码密钥、API Key
- ❌ renderer 直连数据库或执行 SQL
- ❌ 静默吞错（catch 后无日志无返回）
- ❌ console.log 提交到代码库
- ❌ 修改已发布迁移文件

## 四、常用命令

```bash
# 开发
cd E:\workspace\workbuddy
npm run dev                    # 启动开发服务器

# 测试
npm test                       # 运行全量测试
npm run test:coverage          # 测试 + 覆盖率报告

# 构建
npm run build                  # 构建（main + preload + renderer）
npm run pack:win               # 打包 Windows 未安装目录包

# 类型检查
npx tsc -p tsconfig.node.json --noEmit   # Node 侧
npx tsc -p tsconfig.web.json --noEmit    # Web 侧

# 重建原生模块（better-sqlite3 与 Electron 版本不匹配时）
npm run rebuild
```

## 七、快速问答

**Q：我修改了代码，接下来做什么？**

A：GLM+DS 流程：
1. 自测（运行测试、构建、类型检查）
2. 更新 `当前代码状态.md`
3. 报告"实现完成，待 GPT 审查"

GPT 流程：
1. 读取 `当前代码状态.md` 和 `当前审查状态.md`
2. 审查代码（03 流程）
3. 给出三态结论

---

**Q：我想添加新依赖，可以吗？**

A：不能随意添加。新依赖必须：
1. 在规格中明确需求
2. 评估替代方案（是否有现有工具可用）
3. GPT 审查批准
4. 记录包名、版本、用途、体积影响

---

**Q：测试失败了，怎么办？**

A：
1. 先看失败原因（错误消息、堆栈）
2. 如果是业务逻辑问题：修复实现代码
3. 如果是测试本身错误：修复测试代码
4. 重新运行测试验证
5. 更新 `当前代码状态.md`

---

**Q：我不清楚某个概念，去哪里查？**
