> **维护方**：GPT（项目经理）
> **用途**：集中定义 WorkBuddy 项目治理、实测、修复、复审、Git 节点和版本状态的代称。
> **适用范围**：新规则生效后的全部治理文档、Prompt、模板和实测记录。
> **上位规范**：`规范类/文档治理总纲.md`、`规范类/阶段闭环门禁规则.md`、`规范类/git提交规范.md`。
> **历史规则**：现有历史文件保持原样；本词典不改写历史文档中的同名编号。

## 入口阶段判定

> **当前入口阶段：B1 当前批次业务实测。**
> B1 尚未形成完整业务实测结论，但这只是当前结果状态，不是入口阻塞原因。
> 在 B1 当前批次结束前，R1-3 与 R2-1 的唯一实际操作入口是 `E:\workbuddy-test\启动实测.bat`，角色选择器是 `E:\workbuddy-test\选择B1实测角色.bat`。
> `E:\workbuddy-test\长期入口\` 仅为 B1 完成后的后续长期实测入口，当前为“已预建、未启用”，不得用于本次 B1 实测。
> B1 结束后，旧入口保留为历史资产；“切换入口”仅表示后续运行改用长期入口，不表示覆盖、迁移、重命名或删除旧入口。

本轮 R1-3、R2-1 计划状态保持 `🟡待补前置`，后续由独立复核判断是否可执行；该状态不是“B1 业务实测未完成”导致的入口阻塞。

## 一、使用原则

1. 本文件是代称词典，不替代门禁、Git、技术栈或用户实测操作规则。
2. 代称必须在计划、报告、回传、闭环记录和证据路径中保持一致。
3. `C0`、`QA`、`S`、`C1` 是版本/候选节点；`R`、`Fix`、`Review`、`G1` 是实测流程节点。它们不能互相替代。
4. `C0` 只负责把开发阶段交给功能实测阶段；实测阶段的下一次测试由不可变 `S` 快照控制，不因每次 Fix/Review 强制产生新的 Git 提交。
5. 所有编号默认使用 ASCII 字母和数字。`N`、`n`、`NN` 等大写占位符只能在模板中使用，实际记录必须替换为具体数字。

## 二、版本和候选节点

### 2.1 节点总表

| 代称 | 全称/含义 | 作用 | 是否正式版本 | 编号作用域 |
|---|---|---|---|---|
| `C0` | 开发完成基线提交 | 当前目标版本全部开发单元闭环后，锁定进入功能实测的代码基线 | 否；实测基线 | 当前目标版本唯一一个 |
| `S0` | C0 实测构建快照 | 由 C0 构建的首个不可变被测构建物 | 否 | 当前目标版本全局 |
| `QA1/QA2...` | Quality Assurance candidate，实测候选状态 | Fix/Review 后形成的待测代码状态；记录当前候选是否来自提交或工作树 | 否 | 当前目标版本全局递增 |
| `S1/S2...` | QA 实测构建快照 | 分别绑定 `QA1/QA2...` 的不可变被测构建物 | 否 | 当前目标版本全局递增 |
| `C1` | 版本完成节点 | 当前版本所有活跃功能/问题轮次关闭、双方证据齐全、G1 通过且用户完成最终验收后的正式版本节点 | 是 | 当前目标版本唯一一个 |

### 2.2 C0、QA、S、C1 的关系

```text
开发单元全部闭环
        │
        ▼
C0（唯一开发→实测基线提交，v0.3.0-c0）
        │
        ▼
S0（C0 的不可变实测构建快照）
        │
        ├─ R1-n 实测 → 13 合并 → Fix/Review
        │                         │
        │                         ▼
        │                  QA1 → S1 → 同轮下一份 R1-n 计划
        │                  QA2 → S2 → 继续复测
        │
        ▼
所有活跃 R 轮次关闭 → G1 版本级整合回归 → 用户最终验收
        │
        ▼
C1（正式版本 v0.3.0）
```

- `C0` 必须是可定位的 Git 提交，且创建前必须完成开发闭环、变更归属确认和工作树清理。
- `S0` 绑定 C0；代码、依赖或构建输入没有变化时可以复用同一 S 快照。
- `QA1` 表示候选代码状态，不强制要求 Git 提交。未提交修复也可以形成 QA 状态，但必须记录完整工作树指纹、构建物哈希和独立构建目录。
- `S1` 必须在实际测试前冻结，并且只能从对应 `QA1` 状态构建。GPT 和用户使用同一 S 构建物，但使用独立测试数据目录。
- Fix/Review 后，下一份 `R<N>-<n+1>` 测试计划不以新的 Git 提交或干净工作树作为门锁；它以已冻结、可复核的 S 快照为运行基准。
- `C1` 只有在当前目标版本所有活跃功能/问题轮次关闭、双方证据齐全、G1 通过且用户完成最终验收后成立。单个功能闭环不直接形成 C1，也不等于项目进入维护期。

### 2.3 版本号和 Git Tag

以下以当前目标版本 `v0.3` 为例；后续版本按同样结构替换版本号：

| 节点 | Git/展示版本 | `workbuddy/package.json` | Git Tag |
|---|---|---|---|
| `C0` | `v0.3.0-c0` | `0.3.0-c0` | 必须：`v0.3.0-c0` |
| `QA1/S1` | `v0.3.0-qa.1` | `0.3.0-qa.1` | 可选：`v0.3.0-qa.1` |
| `QA2/S2` | `v0.3.0-qa.2` | `0.3.0-qa.2` | 可选：`v0.3.0-qa.2` |
| `C1` | `v0.3.0` | `0.3.0` | 必须：`v0.3.0` |

- `package.json` 的版本字段属于代码状态，由 GLM+DS 修改；每次填写实际执行者，GPT 只读核验，不直接编辑。
- QA Tag 只有在存在可定位的提交时才创建；未提交 QA 状态只记录工作树指纹和构建物哈希，不伪造 Tag。
- `C0`/`C1` 的 Tag 表示可定位节点，不表示用户验收自动通过；QA Tag 表示内部候选，不表示发布。
- 当前 `package.json` 的实际值不得由本词典推断。形成 C0/QA/C1 时必须按当时状态由 GLM+DS 更新并由 GPT 核验。

## 三、用户实测流程代称

| 代称 | 含义 | 规则 |
|---|---|---|
| `R<N>` | 实测处置来源轮次 | 可承接独立产品问题、覆盖缺口和环境/产品处置事项；同一轮始终只有一份全流程闭环文档 |
| `R<N>-<n>` | 同一问题来源轮次中的第 n 份测试计划 | 只在 C0 首次进入实测或对应问题完成 `Fix → Review → QA/S` 后由 `14` 创建；`R1-1` 和 `R1-2` 属于同一个 R1 |
| `R<N>-<n>-T<NN>` | 稳定测试点 ID | 贯穿测试计划、GPT 报告、用户回传、闭环文档和证据 |
| `FixN` | GLM+DS 用户反馈统一处理批次 | 同一 R 一次处理全部已批准代码修复、替代和删除事项，并回写该文档；覆盖缺口不进 Fix；实现/修复日志必须标真实执行者 |
| `ReviewN` | GPT 统一处理批次复审批次 | 实地核对整个 Fix 的修复、替代、删除、原始失败场景、回归、越界和技术栈边界，回写同一文档 |
| `15` | QA/S 候选快照冻结 | 05 整批 Review 通过后由 GPT 核对并冻结候选 QA/S；不修改代码或测试计划 |
| `16` | 环境与产品处置决策 | GPT 记录同一 S/副本的环境证据、影响和用户明确的继续排障/替代/删除选择；不替用户决策、不修改代码 |
| `G1` | 版本级整合回归 | 所有活跃 R 轮次关闭后执行；使用独立的 G1 测试计划和 `G1-T<NN>` 测试点，不创建新的 R 轮次，发现问题时回写现有轮次或新开下一轮 |
| `U<N>` | 用户实测轮次闭环中的问题 ID | 由 13 在该轮文档内保持稳定；不是全局缺陷编号 |
| `F<N>` | GPT 报告内的问题 ID | 只在对应 GPT 报告内定位；合并到轮次文档时由 13 建立问题映射 |

G1 测试点使用 `G1-T<NN>`，不属于任何 `R` 轮次。

### 3.1 结果状态

| 状态 | 含义 |
|---|---|
| `🟡待实测` | 13 已建立 R 初始化骨架，尚无首份测试计划结果 |
| `📝待补证据/待核实` | 关键事实、证据、复核或用户确认缺失/冲突；不能进入 Fix |
| `⏸️待环境/产品决策` | 环境事项或替代/删除选择等待用户/PM 决策；不能进入 Fix |
| `🟡待修复` | 本 R 所有事项已有终态处置，且统一 Fix 可执行；不表示修复完成 |
| `🟢等待下一轮测试` | 05 整批 Review 通过且 15 已冻结 QA/S，等待 14 创建下一计划 |
| `✅当前轮次闭环` | 本 R 所有事项完成并重新验证，无未关闭回归、覆盖、环境、核实或用户决策缺口；仍须 G1 |
| `维护期` | 全部功能和阶段 6 用户 E2E 完成后，才按 CR 规则进入项目维护期 |

### 3.2 统一 Fix 门

部分问题回传不要求用户为未列出的用例虚构详细通过记录。单个代码问题只有同时具备以下材料，才可列入统一 `Fix`：

1. 测试计划中的预期、测试点/子用例或“计划覆盖缺口”定位；
2. 用户原始事实和用户证据（问题由用户回传时）；
3. GPT 正式报告或 `13` 触发的独立 GPT 补充 GUI/只读核验证据；
4. 同一 `S` 快照、测试副本、入口和数据前缀可复核；
5. 问题分类、允许改动范围、验收条件和下一步已明确。

用户事实与 GPT 补充回放冲突时，该问题保持 `待核实`，不得仅凭代码阅读或一次不同结果进入 `Fix`。以上只是单项证据门；真正生成 `FixN` 还必须满足本 R 所有事项都有终态处置，覆盖缺口已转下一计划，批准的替代/删除已有 16 决策，且没有待核实、环境阻塞或待用户确认。`用户补充问题 1/2/3…` 只是来源标签，不是测试点、子用例或稳定问题 ID。

### 3.3 环境和产品处置门

每个环境事项必须使用同一 S/测试副本按正式入口重复启动，核对进程参数、环境变量、实际数据目录和 GUI 结果；存在候选替代入口时至少验证一个。必须登记责任人、独立排障期限、用户/PM 复评点及“继续排障/替代/删除”选项。16 记录用户明确选择；决定前事项持续阻断统一 Fix。

## 七、编号作用域和唯一性

- `C0`、`C1`、`S0`、`S1`、`QA1` 等版本节点在同一目标版本内全局唯一；多个功能不得各自重新使用同一版本级编号。
- `R<N>` 在功能实测处置来源范围内唯一；同一 `R<N>` 只能有一个轮次闭环文档。
- `R<N>-<n>` 在所属 R 轮次内唯一；每次实际测试必须创建新的 n。
- `R<N>-<n>-T<NN>` 在所属测试计划内唯一；测试计划变更测试语义时不得复用旧测试点 ID。
- `FixN`、`ReviewN` 在所属 R 轮次闭环文档内递增；不得覆盖历史批次。
- `CR-NNN` 在项目维护期全局唯一，不因功能或版本重置。

## 八、历史同名兼容

历史文档中的同名编号不自动套用当前词典：

| 历史形式 | 历史语境 | 当前解释 |
|---|---|---|
| `C1/C2...` | 旧版用户流程中的测试场景编号或子项编号 | 不是当前 `C1` 正式版本节点 |
| `S/S1/S2...` | 旧版用户流程中的 LLM 未配置降级场景及其子步骤 | 不是当前 `S0/S1` 构建快照 |
| `G1/G2...` | 历史治理要素、审查编号或其他章节编号 | 只有新规则文档中的 `G1` 才表示版本级整合回归 |
| `U/F` | 历史用户反馈或 GPT 报告中的测试项/问题编号 | 只有新规则模板语境中的 `U<N>`/`F<N>` 才按本词典解释 |

历史目录、历史计划、历史 GPT 报告和历史全流程记录必须保留原样。新文档只使用当前规则，并在引用历史证据时注明其原始语境。

## 九、已确认的治理决策

- `C0` 是开发阶段进入功能实测阶段的唯一 Git 门锁，不是每次实测或每个修复批次的门锁。
- 实测阶段 Fix/Review 后可以在未提交工作树上形成 QA 候选，但实际运行前必须冻结对应 S 快照并记录指纹、构建物哈希和独立构建目录。
- `13` 支持 `R 初始化 / R 测试合并 / G1 合并`；初始化不要求测试计划、GPT 报告或用户 06，测试合并不创建测试计划，G1 只回写 G1 计划。
- 同一 R 使用整轮统一 Fix：代码修复、批准替代和批准删除合并为一个 FixN；覆盖缺口进入 14 覆盖补充计划，待核实/环境/用户决策未完成时不得生成可执行 Fix。
- `05` 只复审整个 Fix 批次；通过后交 `15` 冻结 QA/S，再由 `14` 创建后续计划。`16` 只记录用户明确的继续排障、替代或删除决定。
- `G1` 使用独立的版本级整合测试计划、GPT 报告和用户回传；G1 失败时按证据回写现有 R 或新建下一 R，G1 本身不变成 R。
- C0/QA/C1 的版本字段由 GLM+DS 更新，GPT 核验；C0/C1 必须 Tag，QA Tag 可选。
- `C1` 是当前目标版本级节点，必须等待所有活跃功能/轮次、双方证据、G1 和用户最终验收；单个功能闭环不直接等于 C1 或项目维护期。
- 历史结构保持不变，新规则向前生效。

## 十、同一修复批次的多 R 合并复审

当多个已经完成 Fix 的活跃 R 被用户明确归入同一修复批次时，使用批次代称 `B<N>`，不改变各 R 原有的唯一闭环和 `FixN/ReviewN` 编号。批次规则如下：

- 批次共同基线必须是同一个 `C0/S0`。每个 R 先从该基线独立生成自己的 `R-only` 候选，只包含该 R 统一 Fix、批准替代和批准删除的差异；混合工作树或已经包含其他 R 的候选不能直接冒充 `R-only`。
- 初始复审次数为“本批次 R 数 + 1”：每个 `R-only` 各一次整批 05 复审，最后一次是所有已通过 `R-only` 的合并包复审。合并包复审失败后的修复/复审是同一 `B<N>-merge` 闭环的追加轮次，不创建新的 R 或新的 R `FixN`。
- 已经存在的前置停止 `Review` 是历史事实，不得覆盖；后续按所属 R 的下一个 `ReviewN` 继续。B1 中 R2 的前置停止 `Review1` 后，R2-only 使用 `Review2`。
- `B<N>-merge` 必须有独立的批次级全流程闭环文档，记录合并来源、完整清单、指纹、构建物、复审、合并阶段修复和最终冻结；它不是 GPT 报告、测试计划或 `审查日志/`。
- 单 R 复审可以并行，但各候选必须使用独立程序目录、启动包装和 `userData`；涉及代码的合并阶段修复仍串行执行。B1-merge 失败时只在 B1-merge 文档追加“`B1-merge 修复记录N`”，不回流 R1/R2。
- 只有全部 `R-only` 复审和最终 B1-merge 复审通过，才能调用一次 `15`。15 只冻结最终合并包为全局下一个 `QA/S`（B1 预计为 `QA1/S1`），不冻结中间候选；冻结后才能将该 S 覆盖部署到正式测试入口并由 `14` 创建后续计划。
