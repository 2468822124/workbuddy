## 2. 分层架构边界（四层，越界即违规）

```
src/
├─ main/       主进程：一切业务逻辑与数据访问的唯一属地
│  ├─ index.ts / window.ts     生命周期与窗口
│  ├─ ipc/      IPC 通道层（薄壳：参数校验 + 调 service/repo + Result 包装）
│  ├─ services/ 业务服务（纯业务规则，可依赖 repo，禁依赖 IPC）
│  ├─ db/       数据层
│  │  ├─ connection.ts / migrate.ts   连接与迁移
│  │  ├─ migrations/   迁移脚本（编号递增，见 §5 铁律 2）
│  │  └─ repositories/ 仓储（SQL 唯一属地）
│  └─ lib/     主进程工具（result.ts / logger.ts / crypto.ts）
├─ preload/    桥接层：仅做 contextBridge 暴露，零业务逻辑
├─ renderer/   渲染进程
│  └─ src/
│     ├─ views/       路由页面
│     ├─ components/  组件（含 planning/ project/ settings/ 子域）
│     ├─ composables/ 组合式函数（useApi 之上的状态编排）
│     ├─ lib/         渲染端纯函数（如 planTid.ts 一类，随重构清理）
│     └─ router/ styles/
└─ shared/     双进程共享：types.ts / constants.ts / ipc.ts（通道名）/ period.ts 等纯类型与纯函数
tests/         vitest 测试（与 src 同构命名 xxx.spec.ts）
```

### 各层允许与禁止事项

| 层 | 允许 | 禁止 |
|---|---|---|
| **main/ipc** | 校验入参、调用 service/repo、`Result<T>` 包装返回、通道名引用 `shared/ipc.ts` | 禁写业务规则；禁直拼 SQL；禁操作 DOM |
| **main/services** | 业务规则、调用 repositories、调用其它 service | 禁直连 SQLite（SQL 只能在 repositories）；禁 import electron UI API |
| **main/db/repositories** | 全部 SQL、行↔对象映射 | 禁业务判断（如"何时算完成"属 service/派生查询）；禁 IPC |
| **main/lib** | 无副作用或有明确契约的工具函数 | 禁依赖 db/services |
| **preload** | contextBridge 暴露白名单 API | 禁 nodeIntegration 直通；禁业务逻辑 |
| **renderer** | UI、composable 状态编排、经 preload 桥调用 IPC | **禁直连数据库**；禁 node API；禁 SQL 字符串；禁在渲染层写业务真相规则（展示性派生除外，须注明） |
| **shared** | 类型、常量、纯函数（无 IO、无 electron/vue 依赖） | 禁 import main/renderer 任何模块；禁副作用 |

**跨层调用规则**：renderer →(preload桥)→ ipc → service → repository，单向依赖；任何反向依赖（如 main import renderer）违规。

## 3. IPC 契约规范

1. **通道命名**：`域:动作` 小驼峰域（沿用现状，如 `plans:listByPeriod`、`todos:toggle`）；通道名常量统一放 `shared/ipc.ts`，**禁止字面量散落**。
2. **返回包装**：所有 IPC 返回 `Result<T>`（`src/main/lib/result.ts` 既有模式：`{ok:true,data}|{ok:false,error}`）；禁止裸抛到渲染层。
3. **preload 桥**：每个新通道须在 preload 同步暴露，入参出参类型引用 `shared/types.ts`。
4. **入参校验**：ipc 层首行校验（类型/必填/边界），非法即返回 `{ok:false,error}`，禁静默容错。
5. **渲染端调用**：统一走 `useApi` composable，组件内禁直接 `window.api.*` 裸调（除 useApi 内部）。

## 4. 数据层铁律（本轮重构核心，源自 3.2 六轮失败教训）

1. **唯一真相源**：任务域真相只存结构化表。任何"从文本解析任务"的代码（planParser 类）不得再新增；旧计划与复盘模块的解析/同步路径（planRepo.syncPlanTodos、planParser、planTid、todoSource 推断链等）标记为**待删除，禁止复用、禁止扩写**。
2. **迁移只增不改**：新表/新列走 `migrations/00NN_xxx.ts` 编号递增、`addColumnIfMissing` 幂等模式；**禁止**修改已发布迁移脚本内容；禁止 DELETE/UPDATE 存量数据的"回填式迁移"进入正式迁移（一次性数据操作须单独脚本并留档）。
3. **软删除约定**：业务数据删除一律 `isDeleted=1 + deletedAt`；物理 DELETE 仅允许出现在显式数据清理脚本。
4. **任务域/叙述域隔离**：任务行永不存于 Markdown/自由文本；感想/复盘长文（叙述域）独立表存储，两域无外键、无同步逻辑。
5. **凭据池派生原则**：完成态/消耗态/统计一律实时查询派生，**禁止落任何"完成状态缓存字段"**（consumed、sourceInvalid 类字段是 3.2 幽灵残留的物种，不得复活）。
6. **出处元数据直存**：任务来源（周任务/项目/提醒/手动/模板）在创建时显式写 source 元数据字段，**禁止事后按内容推断**（labelTodoSource 五规则推断链模式禁止再现）。

## 5. 代码规范与错误处理

1. **命名**：文件 kebab-case 或沿用现状 PascalCase（.vue 组件 PascalCase、.ts 模块小驼峰）；TS 接口 PascalCase；IPC 通道见 §3；迁移文件 `00NN_蛇形名.ts`。
2. **函数/文件尺寸**：函数 <50 行，文件 <800 行（超限拆分）。
3. **错误处理**：ipc/service 层显式处理一切失败路径，日志走 `main/lib/logger.ts`；**禁止静默吞错**（catch 后无日志无返回）；渲染层用户可见错误须有 UI 反馈（3.2「点选取无反应」教训）。
4. **不可变优先**：数据变换返回新对象；确需原地修改须注释说明。
5. **禁止事项**：console.log 提交前清除（logger 除外）；禁硬编码密钥/魔法数；禁 any 扩散（确需须注释）。

## 6. 测试要求（3.2「假绿」教训制度化）

1. **门禁三件套**：vitest 全绿 + `electron-vite build` 绿 + `tsc -p tsconfig.node.json` 无新增错误（news.ts:22 为存量基线）。
2. **门禁全绿 ≠ 功能可用**：凡新功能须有测试真实触达主逻辑路径；**纯函数必须直测**（不允许"只测 repo 不测渲染端消费的纯函数"）。
3. **正则捕获组规则**：凡新增/修改正则捕获组索引的代码，实现者必须以 node 实跑验证组数与取值，并在 PR/日志中附验证输出（复审1 m[4] 事故的永久防再犯条款）。
4. **渲染端路径**：composable/渲染端 lib 的新增纯函数必须导出并单测（usePlanning.spec 模式）。
5. **回归清单**：任务数据流通重构的每阶段验收须覆盖对应阶段的用户实测场景（源自 3.2 六轮）。

## 7. 目录落位规则（新增代码）

| 新增物 | 落位 |
|---|---|
| 新业务域表 + 仓储 | `src/main/db/migrations/00NN_*.ts` + `src/main/db/repositories/xxxRepo.ts` |
| 新业务服务 | `src/main/services/xxx.ts` |
| 新 IPC 通道 | `src/main/ipc/xxx.ipc.ts` + `shared/ipc.ts` 通道名 + preload 桥 |
| 新页面 | `src/renderer/src/views/XxxView.vue` + router 注册 |
| 新组件 | `src/renderer/src/components/{域}/Xxx.vue` |
| 新 composable | `src/renderer/src/composables/useXxx.ts` |
| 双端共享类型/纯函数 | `src/shared/` |
| 测试 | `tests/xxx.spec.ts` |

**禁止**：视图里写 SQL/仓储逻辑；service 里写组件；shared 里进程特定 API。

## 8. 新依赖引入流程（评审制）

1. 提出方（DS 或 GLM）在阶段规格 §3 或 CR 中列明：包名、版本、用途、体积影响、替代方案评估。
2. GLM 审查必要性（是否可用现有依赖/手写 20 行内解决）。
3. 用户确认后写入 package.json，并在《技术栈规范》§1 清单同步登记。
4. **未经此流程的依赖引入视为违规**（含 devDependencies）。

## 9. 重构专用边界（任务数据流通重构期间附加）

1. **旧模块冻结区**：`planRepo.ts` / `planParser.ts` / `taskRepo.ts` / `todoRepo.ts`（旧任务部分）/ `todoSource.ts` / `parentRef.ts` / `usePlanning.ts` / `planTid.ts` / `plans.ipc.ts` / `todos.ipc.ts`（旧通道）——**只读不改不扩**，待阶段⑥统一删除替换；新功能禁止 import 冻结区。
2. **项目/提醒模块边界**：projects / reminders 模块**不重写**；新任务域经适配层接入——对项目模块**只读其任务 + 唯一写通道（完成态回写）**；提醒任务按打卡型语义生成当日任务行。适配层落 `src/main/services/`。
3. **新任务域代码前缀**：新仓储/服务/通道以新域命名（如 `taskV2` / `flow` 等在规格-阶段1 定名），与冻结区文件物理隔离，禁止同文件混写新旧逻辑。
4. **数据不迁移**：旧 plans/todos/tasks 数据不迁移入新模型；新表新起，旧表保留至阶段⑥归档清理。
