# 日常开发流程（1小时掌握）

> **版本**：v1.2.0  
> **前置**：已阅读 [快速开始](./00-快速开始.md)  
> **目标受众**：需要编写代码或审查代码的 AI  
> **学习时间**：1 小时  
> **下一步**：[完整治理手册](./文档治理总纲.md)（按需查阅）

---

## 一、开发阶段流程（01-05）

```
01 GPT 写规格
  ↓
02 GLM+DS 实现
  ↓
03 GPT 审查
  ↓
若有问题：04 GLM+DS 修复
  ↓
05 GPT 复审
  ↓
✅ 开发单元闭环
```

---

## 二、01 - GPT 写规格

**输入**：功能需求、项目计划

**输出**：规格（写在全流程闭环记录中）

**规格必须包含**：
1. 单元目标、用户可见成果
2. 包含范围和不包含范围
3. 技术设计、数据模型
4. IPC 通道、参数、返回类型
5. 文件落位、模块边界
6. GLM+DS 的有序任务拆解
7. 可逐条验证的验收点
8. 禁止边界、错误降级

**状态**：初始为 `🟡实现中`

---

## 三、02 - GLM+DS 实现

**前置条件**：规格已就绪

**执行顺序**（典型）：
```
数据模型
  → SQLite migration
  → shared types / IPC 常量
  → db repositories（SQL 唯一属地）
  → main services（业务逻辑）
  → main IPC handlers
  → preload 安全桥
  → renderer composables
  → views/components
  → Vitest 单测与组件测试
  → 门禁三件套
```

**自测清单**：
- [ ] 运行 `npm test`（全部通过）
- [ ] 运行 `npm run build`（成功）
- [ ] 运行 `npx tsc` 两套（零新增错误）
- [ ] 逐项验证规格验收点
- [ ] 测试正常路径、边界、错误降级

**输出**：
1. 实现代码
2. 测试代码
3. 实现日志（写在全流程闭环记录）
4. 更新 `当前代码状态.md`

**报告**："实现完成，待 GPT 审查"

---

## 四、03 - GPT 审查

**前置条件**：GLM+DS 报告"实现完成"

**必读**：
- 规格（全流程闭环记录）
- 实现日志（全流程闭环记录）
- `当前代码状态.md`
- `当前审查状态.md`

**审查步骤**：

1. **核对 GLM+DS 状态**
   - 读取 `当前代码状态.md`
   - 确认任务完成、自测通过、无遗漏

2. **运行门禁三件套**
   ```bash
   npm test                    # 必须 404/404 通过
   npm run build               # 必须成功
   npx tsc -p tsconfig.node.json --noEmit
   npx tsc -p tsconfig.web.json --noEmit
   ```

3. **逐项验证规格验收点**
   - 每个验收点写：预期、实际、证据、结论

4. **检查技术边界**
   ```bash
   # SQL 只在 repositories
   rg 'db\.prepare|db\.exec' --type ts --glob '!**/repositories/**'
   
   # renderer 不直连 DB
   rg 'better-sqlite3' workbuddy/src/renderer --type ts
   
   # 无硬编码密钥
   rg 'API_KEY|password.*=.*["\']' --type ts --glob '!tests/**'
   ```

5. **GUI 验证**（如涉及 UI）
   - 启动程序，实际操作
   - 验证空态、加载态、错误态、成功态
   - 验证确认/取消、刷新/重进

6. **错误降级**
   - 构造失败场景（非法输入、网络失败、数据库不可用）
   - 确认可读反馈、不崩溃、不清空、不泄露

**输出**：审查报告（写在全流程闭环记录）

**结论**（三态）：
- ✅ **通过（开发闭环）**：所有验收点通过，无 HIGH/CRITICAL 问题
- 🟡 **需修复**：有明确可修复问题，进入 04
- 🔴 **驳回**：范围、数据、安全、隔离失效，恢复条件

---

## 五、04 - GLM+DS 修复

**前置条件**：GPT 03 审查结论为 `🟡需修复`

**输入**：GPT 审查报告中的问题清单

**执行原则**：
1. **只修复 GPT 列出的问题**，不扩大范围
2. **先复现失败场景**，再改最小必要代码
3. **逐个问题记录**：修改文件、原因、修复方式、验收点
4. **重新运行受影响测试**和门禁三件套
5. **重新验证原失败场景**

**输出**：
1. 修复代码
2. 修复日志（追加到全流程闭环记录）
3. 更新 `当前代码状态.md`

**报告**："修复完成，待 GPT 复审"

---

## 六、05 - GPT 复审

**前置条件**：GLM+DS 04 修复完成

**复审步骤**：
1. **读取修复日志**（全流程闭环记录）
2. **逐项复跑原失败场景**
3. **检查新引入问题**（回归测试）
4. **验证边界和降级**

**结论**（三态）：
- ✅ **通过（开发闭环）**：所有问题已修复，可进入下一单元
- 🟡 **仍需修复**：追加 Review2，再次进入 04
- 🔴 **驳回**：根本性问题未解决

---

## 七、用户实测流程（C0 → R → Fix → Review → QA/S）

**触发**：所有开发单元闭环后

**流程**：

```
C0（开发基线）
  ↓
S0（不可变快照）
  ↓
12 GPT 实测 + 用户实测
  ↓
06 用户三态回传
  ↓
13 合并双方证据
  ↓
07 GLM+DS 统一 Fix
  ↓
05 GPT 复审
  ↓
15 冻结 QA/S
  ↓
14 创建下一轮测试计划
```

**关键点**：
- **C0**：开发进入实测的代码基线，不是正式发布
- **S0**：从 C0 构建的不可变快照，测试专用
- **R**：实测处置来源轮次（R1、R2、R3...）
- **QA/S**：待测候选 + 快照，冻结后不可变
- **G1**：版本级整合回归（所有 R 关闭后）
- **C1**：正式版本（用户最终验收后）

## 八、维护期 CR 流程

**触发**：阶段 6 + G1 + C1 完成后

**流程**：

```
用户反馈 / GPT 发现缺陷
  ↓
GPT 创建 CR-NNN 全流程记录
  ↓
08 GLM+DS 复现并实现
  ↓
09 GPT 审查
  ↓
若有问题：08 → 09 循环
  ↓
✅ CR 关闭
  ↓
11 Git 归档
```

**CR 编号**：从 CR-001 起全局递增，不复用、不跳号

## 九、常见场景处理

### 场景 1：测试失败

**问题**：`npm test` 有失败

**处理**：
1. 查看失败原因（错误消息、堆栈）
2. 判断是**实现问题**还是**测试问题**
3. 修复对应代码
4. 重新运行测试
5. 更新 `当前代码状态.md`

---

### 场景 2：构建失败

**问题**：`npm run build` 失败

**处理**：
1. 查看构建日志
2. 常见原因：
   - TypeScript 类型错误
   - 导入路径错误
   - 缺少依赖
3. 修复后重新构建
4. 验证 `out/` 目录生成正常

---

### 场景 3：类型检查有新增错误

**问题**：`tsc` 报告新的类型错误

**处理**：
1. **存量诊断允许**（已记录在基线）
2. **新增错误必须修复**
3. 修复方式：
   - 补充类型标注
   - 修正类型推断
   - 避免 `any` 逃逸

---

### 场景 4：实现偏离规格

**问题**：实现时发现规格有问题

**处理**：
1. **不要先改后解释**
2. 在实现日志中记录：
   - 规格的问题
   - 偏离的内容
   - 原因和影响
   - 补充的验收条件
3. GPT 审查时会评估是否接受偏离

---

### 场景 5：审查发现越界改动

**问题**：GPT 发现修改了不在规格范围内的代码

**处理**：
1. GPT 给出 `🔴驳回` 结论
2. GLM+DS 回退越界改动
3. 只保留规格范围内的修改
4. 重新提交审查
