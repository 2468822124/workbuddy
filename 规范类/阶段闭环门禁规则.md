### 矩阵执行规则

1. `planStatus` 只表示计划生命周期，不表示业务结果；`staticGate` 只表示静态前置，不表示动态测试通过。
2. 台账缺失先标为“待补台账/待核对”；只有它影响入口安全、版本身份、数据隔离或无法定位测试范围时，才升级为业务启动阻塞。
3. `E0=passed` 只允许开始 `T01`；`T01=not-tested` 允许开始取证，不能写成 `passed`，也不能反过来阻止 T01 启动。
4. 动态测试点失败才停止依赖它的后续点；独立点按计划继续。环境阻塞和产品选择必须走 `16`，不能由 GPT 猜测结论。
5. 失败回退是业务类型的回退，不是把所有问题退回同一个 Prompt：开发审查回 `04`，R 修复回 `07`，维护期 CR 回 `08 → 09`，计划门禁回 `14`，环境/产品事项回 `16`；`15A` 同步失败留在 `15A`，不得进入 `15`。

## 一-B、统一四层状态模型

所有新建或更新的阶段计划、R 闭环、G1 计划、GPT 报告和入口记录必须能够分别给出以下四层状态。旧历史文档不强行迁移；需要引用旧文档时在现行文件中建立映射。

| 字段 | 允许值 | 负责更新方 | 含义 |
|---|---|---|---|
| `planStatus` | `not-created` / `created` / `needs-prerequisite` / `ready` / `superseded` | GPT（计划） | 计划是否存在、前置是否齐全、是否允许进入静态门；不表示测试结果 |
| `staticGate` | `not-applicable` / `pending` / `passed` / `failed` | GPT/入口预检 | C0、S、入口、版本、隔离等静态条件；`passed` 只开放动态取证 |
| `testPointStatus` | `not-tested` / `in-progress` / `passed` / `failed` / `blocked` / `not-applicable` | GPT/用户按各自证据 | 单个动态测试点的实际结果；未测试不能推断为通过 |
| `closureStatus` | `not-started` / `in-progress` / `blocked` / `closed` / `not-applicable` | 对应闭环维护方 | 当前轮次/CR/开发单元是否关闭；不覆盖历史事实 |

状态更新必须同时写 `updatedAt`、`updatedBy`、`evidence` 或 `nextAction`。状态层级不允许互相代替：例如 `staticGate=passed` 不能自动把 `planStatus` 改为 `ready`，`testPointStatus=not-tested` 不能自动把 `staticGate` 改为 `failed`。

## 二、角色与状态看板权限

| 文档 | 唯一维护方 | 其他角色 |
|---|---|---|
| `当前代码状态.md` | GLM+DS（同一时刻单写者） | GPT 只读，核对实现真实性 |
| `当前审查状态.md` | GPT | GLM+DS 只读，读取审查要求 |
| 开发单元全流程记录 | GPT/GLM+DS 按环节追加 | 不删除、不覆盖历史；实现/修复段标真实执行者 |
| 用户实测轮次全流程记录 | GPT 通过 13 创建/续写；GLM+DS 通过 07 写 Fix | 用户原始回传和双方证据只引用，不改写事实 |

GPT 不得修改产品代码、数据库或 `当前代码状态.md`；GLM+DS 不得修改 `当前审查状态.md`。状态看板的当前结论必须与对应全流程文档最新正式结论一致。

### 当前审查状态.md 的快照写入规则

- `当前审查状态.md` 只保存最新审查任务、当前门禁、活跃 R 状态和证据边界；它是快照，不是时间线或审计日志。
- GPT 每次产生新的审查、复审或门禁结论时，必须直接覆盖当前字段和活跃 R 状态表；不得在文件末尾追加按日期命名的“当前状态”章节。
- 历史审查、修复、复审和时间线必须保留在对应开发单元或 R 唯一全流程闭环记录中。当前看板只引用其最新正式结论，不通过全文统计历史 `🔴/🟡` 判断当前状态。
- 如果看板旧字段与权威全流程文档最新正式结论冲突，先覆盖看板当前字段使其一致，再在权威全流程文档保留历史事实；不得用新追加段落掩盖旧当前字段。

## 三、开发单元闭环

### 判定条件

- 规格、实现、审查、修复（如有）和复审记录齐全；
- 所有开发单元验收点有实际证据通过；
- 无未关闭的 `HIGH/CRITICAL`、技术栈红线或越界改动；
- GPT 复审明确写出 `✅通过（开发单元闭环）`。

### 状态流转

```text
🟡实现中 → 🟡待审 → 03 审查 → 04 修复（如有）→ 05 复审 → ✅开发闭环
```

`当前代码状态.md` 中“待 GPT 审查/待 GPT 复审”是 GLM+DS 交审前置状态，不覆盖 GPT 已有的正式通过；但实现/修复失败或事实与证据矛盾时，必须重新处理。

## 四、进入功能实测的硬门：C0

GPT 创建当前目标版本第一份 `R<N>-1` 测试计划前，只读核对并形成 `C0`：

1. 所有开发单元均为 `✅开发闭环`；
2. 整个 `E:\workspace` 工作区内所有非忽略变更均已明确归属；无法归属的变更必须停止，不能擅自提交、删除或还原；
3. C0 基线已提交 Git，能锁定提交号、构建标识和对应版本字段；
4. C0 Tag 已创建，且提交内容与待测代码一致；
5. 程序入口、启动方式、操作系统和窗口环境明确；
6. 测试专用目录、测试数据目录和真实用户数据隔离边界明确；
7. 需要重置时，命令只指向测试数据副本并有恢复步骤；
8. 由 C0 生成的 `S0` 已冻结，记录构建目录、构建物哈希和测试数据隔离信息。

在 C0 入口门范围内，任一项无法确认，计划只能记录 `🟡待补前置`，停止创建可执行测试计划和业务实测。不得用代码猜测、历史截图或 GLM+DS 自测替代核对。

### 4.1 C0 之后的测试计划门

- `C0` 只在开发阶段进入功能实测时执行一次；它不是每个 `R<N>-<n>`、Fix 或 Review 的重复门锁。
- 同一版本的后续测试计划不要求重新提交 Git，也不要求工作树重新变干净；已有未提交修复不得被忽略、清理或伪装成已提交。
- 每次实际 GUI 测试必须绑定一个冻结的 `S` 快照。代码、依赖或构建输入改变时，必须形成新的 `QA` 候选和新的 `S`；构建输入完全相同可以复用原快照。
- `S` 必须记录来源（C0/QA、提交号或完整工作树指纹）、构建目录、构建物哈希、版本字段和测试数据目录。GPT 与用户使用同一被测构建物，不得各自从不同工作树启动。
- 无法冻结或复核 `S` 时，计划只能保持 `🟡待补前置`，不得启动业务实测。

### 4.1.1 当前 B1 入口两层门

`E0` 是静态入口前置：S1 部署、B1 当前批次入口、四角色目录、前缀映射、真实数据边界和无残留进程由 `B1实测入口预检.ps1` 或同等只读证据核对。E0 通过只证明允许进入入口取证阶段；本轮两份计划状态按当前决定仍保留 `🟡待补前置`，不在本规则中代替后续独立复核。

`T01` 是第一个动态测试点：实际验证 GUI 前缀、同角色关闭重进和角色切换隔离。T01 不是阻止 T01 启动的前置条件；T01 通过后才继续 T02 及其依赖链，T01 失败时停止依赖它的后续业务测试。T01 未执行只能记录“未测试/待取证”，不能写成通过，也不能反过来称为 T01 启动阻塞。

### 4.2 测试计划创建责任

- 测试计划由 `用户prompt/14-生成用户实测计划.md` 创建，不由 `13` 创建。
- R 的首次功能实测计划只在开发阶段关闭并形成 `C0/S0` 后创建；R 的后续计划只在对应问题完成 `Fix → Review` 并形成新的 `QA/S` 后创建。
- `13` 在测试完成后只合并已有计划的 GPT 报告、用户 06 回传、双方证据、问题诊断和轮次分流。发现全新问题时，`13` 可以新建下一轮唯一 R 闭环文档，但不得同时创建该轮测试计划。
- 新 R 闭环文档没有计划是合法中间状态；待该轮问题完成 `Fix → Review → 15A → QA/S` 后，再由 `14` 创建其首份 `R<N>-1` 计划。

### 4.3 R 初始化、事项处置和统一 Fix 门

- `13` 的 R 初始化只在 C0/S0 已形成后建立唯一 R 骨架，状态为 `🟡待实测`，修复计划填“**不适用，首次实测尚未产生问题**”；初始化不要求测试计划、GPT 报告或用户 06。
- 测试完成后，`13` 在原 R 追加双方事实和“事项处置总表”。原 R 保留全部来源事实；独立新增问题、独立覆盖缺口或独立处置事项才建立下一 R，下一 R 不自动拥有测试计划。
- 事项处置类型包括代码 Fix、覆盖补充计划、环境处置决策、替代、删除、补证/待核实和待用户确认。覆盖缺口进入 14 的覆盖补充计划，不进入代码 Fix；环境/产品事项由 16 记录用户选择。
- 只有本 R 每一项都有终态处置，且没有待核实、环境阻塞、待用户确认，所有代码/替代/删除计划的范围和验收条件完整时，才能生成一个统一 `FixN`。不能拆成多个小 Fix 绕过阻塞。
- `07` 执行统一 Fix，`05` 复审整个批次，`15A` 保存完整最终候选源包并受控同步开发树，`15` 在同步凭证 verified 后冻结 QA/S，`14` 才能创建修复后或覆盖补充计划。
- `05` 复审未通过或因环境阻断时，相关复审项只能标记为“待环境补证/复审阻断”，R3-1 等用户实测计划和用户实测状态保持未开始；只有 `05 → 15A → 15 → 14` 依次完成后，才进入用户实测阶段。

## 五、用户实测轮次门禁

### 编号定义

- `R1/R2`：实测处置来源轮次；可承接独立产品问题、覆盖缺口和环境/产品处置事项。
- `R1-1/R1-2`：同一轮内的具体测试计划；仅在 `C0/S0` 首次进入实测或 `Fix → Review → 15A → QA/S` 后由 `14` 创建下一份计划。
- `C0`：当前目标版本全部开发单元闭环后的唯一实测基线提交。
- `S0/S1/S2`：实际被测的不可变构建快照；`S0` 绑定 C0，后续 S 绑定对应 QA 候选。
- `QA1/QA2`：实测阶段候选代码状态，按当前目标版本全局递增，不是正式版本，也不是每次测试的强制 Git 提交。
- `Fix1/Fix2`：GLM+DS 修复批次，回写触发它的 `R` 文档；每批必须记录实际执行者。
- `Review1/Review2`：GPT 复审批次，回写同一 `R` 文档。
- `G1`：所有活跃轮次关闭后的版本级整合回归，不创建新问题轮次。
- `C1`：当前版本所有活跃功能/问题轮次关闭、G1 通过且用户完成最终验收后的当前目标版本正式节点。
- `R1-1-T01`：测试点稳定 ID，贯穿计划、报告、回传和证据。
- `G1-T01`：G1 计划内稳定测试点 ID，不创建 `R` 编号。

### 文档落点

```text
用户实测阶段\vX-功能名\第N轮\vX第N轮用户实测计划（n）.md
用户实测阶段\vX-功能名\第N轮\vX-第N轮-问题概述-全流程闭环记录.md
GPT实测记录\vX实测内容\第N轮\vX-R1-1-GPT实测.md
```

版本级 `G1` 使用独立落点，不归入任何 `R` 轮次：

```text
用户实测阶段\vX-版本级整合\G1\vX-G1版本级整合测试计划.md
用户实测阶段\vX-版本级整合\G1\用户证据\G1-T<NN>-<场景>.<扩展名>
GPT实测记录\vX实测内容\G1\vX-G1-GPT实测.md
GPT实测记录\vX实测内容\G1\证据\G1-T<NN>-<场景>.png
```

同一 `R<N>` 只能有一份全流程闭环文档。GPT 报告单独写入 `GPT实测记录/`；用户不建立独立实测报告，通过 06 回传。`发现问题` 可以只列问题用例；未列出的用例记为“本次暂未发现问题”，不补写通过事实。13 先完成事项处置总表；即使单个问题证据齐全，也必须等待本 R 其他事项有终态处置且无阻塞，才能生成统一 Fix。

### 双方共同核心链路

测试计划必须把核心链路同时分给 GPT 和用户。GPT 负责客观状态、回归、数据一致性、错误降级、隔离和安全；用户必须亲自执行核心链路并反馈理解、自然性、文案、信任和确认/取消体验。双方证据互不替代。

### 轮次分流

| 本轮结果 | 处理 | 门禁影响 |
|---|---|---|
| 无回归、无新增且无其他事项 | 当前 `R` 标记 `✅当前轮次闭环`，等待所有活跃轮次与 G1 | 不直接宣布功能闭环 |
| 仅回归 | 回写当前 `R`；事项处置完成后 `07 Fix → 05 Review → 15A → 15 QA/S → 14` 同 R 下一计划 | 当前轮保持活跃 |
| 仅新增 | 原 R 保留无回归事实；`13` 新建 `R+1` 唯一闭环，不创建 `R+1-1` 计划 | 新 R 先处置，再按合法节点推进 |
| 回归 + 新增 | 回归续写当前 `R`；`13` 另建 `R+1` 承接独立新增；两轮可并行，代码修改串行 | 任一活跃轮未关闭都不能完成版本 |
| 覆盖缺口 | 登记并分流到覆盖补充 R/14 计划，不成为自动产品缺陷 | 不进入代码 Fix |
| 证据不足/环境阻塞/用户决策未完成 | `📝待补证据/待核实` 或 `⏸️待环境/产品决策` | 不得写通过或生成 Fix |

问题分类由 GPT 根据双方证据完成；用户可以报告客观缺陷，但不需要先判断“回归/新增”。`用户补充问题 1/2/3…` 只是来源标签，不是测试点或子用例；能对应计划时沿用原 ID，不能对应时记录为计划覆盖缺口。对能客观复核的补充问题，13 必须在同一 `S` 和同一测试副本中触发独立 GUI/只读核验，并与用户事实分栏。

### 5.1 统一 Fix 门

部分问题回传时，不要求用户为未列用例补交详细通过证据。单个代码问题仍必须具备计划预期、用户原始事实/证据（如由用户提出）、GPT 正式或独立补充核验证据、同一 `S`/测试副本可复核结果、明确分类和验收条件；但它不能脱离本 R 的事项处置总表单独生成 Fix。只有本 R 每项都有终态处置，代码 Fix/批准替代/批准删除的范围完整，覆盖缺口已转计划，且没有待核实、环境阻塞或待用户确认时，才可生成统一 `FixN`。用户事实与 GPT 回放冲突时保持待核实，不得强行进入 Fix。

### 5.2 环境事项门

每个环境事项必须在同一 S/测试副本按正式入口重复启动，核对进程参数、环境变量、实际数据目录和 GUI 结果；存在候选替代入口时至少验证一个。还必须登记排障责任人、独立排障期限、用户/PM 复评点和“继续排障/替代/删除”选项。没有逐项期限和复评点时持续阻塞；由 16 记录用户决定，GPT 不替用户决定。

## 六、G1 版本级整合回归

### 触发条件

所有活跃 `R` 轮次均已关闭，且每轮的 GPT 客观测试和用户核心链路证据齐全。

### 执行范围

- 所有活跃轮次的核心链路和已修复问题；
- 跨功能数据流、刷新/重进、错误降级、取消保护、数据一致性；
- 测试数据隔离、安全边界、版本/构建一致性；
- GPT 客观验证与用户核心链路确认。

### 裁决

`G1` 通过才可以把功能标记为 `✅功能用户实测闭环`，并具备形成当前目标版本 `C1` 的条件。G1 发现问题时按证据判断是现有轮次回归还是全新问题，回写相应轮次或创建下一轮；G1 本身不成为 `R` 轮次。

## 七、功能用户实测闭环与维护期

功能用户实测闭环必须同时满足：

1. 所有活跃 `R` 轮次关闭；
2. GPT 客观实测有正式报告和证据；
3. 用户亲自完成共同核心链路和用户范围，并通过 06 回传；
4. 双方证据已由 13 合并到轮次唯一文档；
5. `G1` 版本级整合回归通过；
6. 用户作出最终验收裁决。

满足上述条件只关闭该功能的用户实测；当前目标版本还必须完成所有活跃功能/问题轮次、版本级 `G1` 和 `C1` 归档，不能称“项目进入维护期”。只有全部功能和阶段 6 用户 E2E 完成，才按 `规范类/变更闭环规则.md` 进入维护期、CR 和项目级版本发布。

## 八、历史兼容和文档纪律

- 旧 v0.3 测试计划、旧 GPT 记录和旧全流程文件保持原样，作为历史审计证据。
- 新规则只向前生效，不迁移、不重写历史审计线。
- 新复审结论追加到对应全流程文档，不再使用 `审查日志/` 文件夹。
- 历史章节的 `🔴/🟡` 是审计事实；当前门禁只看最新正式结论，不做历史徽标全文计数。

## 九、同一批次多 R 并行复审与合并冻结

当多个 R 的统一 Fix 已完成且用户将其归入同一批次时，批次使用 `B<N>` 标识，R 文档仍分别保留各自的 `FixN` 和 `ReviewN`。批次的共同基线只能是同一 `C0/S0`，执行顺序为：

```text
C0/S0
 ├─ B1-R1：C0 + R1 Fix1       ─┐
 ├─ B1-R2：C0 + R2 Fix1       ─┼─ 各自 05 复审，可并行
 └─ B1-merge：R1-only + R2-only ┘   第三次集成复审
                                  → 15A 源代码同步 verified
                                  → 15 冻结 QA1/S1
                                  → 覆盖部署正式测试入口
                                  → 14 创建后续计划
```

门禁和记录要求：

1. 初始复审次数为本批次 R 数加一。R-only 候选必须从 C0 独立重建，只能包含对应 R 的获准 Fix、替代和删除；当前混合工作树、另一个 R 的候选或直接读取代码不能替代来源核对。
2. 单 R 复审使用各自 R 的统一 Fix 编号和下一可用 `ReviewN`。已有前置停止的 Review 保留，不能覆盖；例如 B1 的 R2-only 使用 `Review2`，不重新写 `Review1`。
3. 每个 R-only 使用独立程序副本、启动包装、测试数据目录和隔离前缀。并行只改变候选准备/复审的目录隔离，不放宽真实 GUI、页面稳定态、刷新/重进、只读持久化、错误反馈、数据一致性、安全和技术栈证据要求。
4. 合并阶段使用唯一批次文档 `B<N>-merge的全流程闭环.md`。B1-merge 失败、修复、重建和再次复审全部追加到该文档，修复命名为 `B1-merge 修复记录N`，不得回流 R1/R2、拆批绕过或创建新的 R `FixN`。
5. 只有所有 R-only 复审和最终 B1-merge 复审均为 `✅通过（修复复审）`，且无阻断、决策缺口、越界或隔离风险，才具备调用 `15A` 的资格。`15A` 必须保存完整源包、批准差异并将最终候选受控同步到 `E:\workspace\workbuddy`；`sourceSyncStatus` 不是 `verified` 时不得调用 `15`。15 只冻结最终合并包，不能冻结 R-only 中间包。
6. `15A` 成功后必须核对同步前后工作树指纹、逐文件 applied/preserved 结果、源包只读状态、清单哈希、批准差异指纹和 `current-development-pointer.json`。任一冲突、回滚失败、未批准文件变化或开发指针不匹配，都保持阻断并记录残留，不能覆盖无关改动。
7. 15 冻结后的 S 才能覆盖部署正式入口；部署前后必须核对完整清单、哈希和 `userData` 不迁移/不清空。随后由 14 创建绑定同一 S 的各 R 后续计划；冻结本身不等于用户验收、G1、C1 或维护期。

### 9.1 Review 到冻结之间的 15A 源代码同步门

`15A` 是独立的机器交接门，固定顺序为：

```text
05 Review 通过
→ 15A 保存完整源包并受控同步 E:\workspace\workbuddy
→ GPT 核对 source-sync-result.json
→ 15 冻结 QA/S
→ 14 创建后续计划
```

- 单 R 使用 `candidateStrategy=direct`，该 R 的最终 R-only 候选就是 B 候选；多 R 使用 `candidateStrategy=merge`，只有最终 `merge` 候选可以进入 `15`。R-only 中间候选不得冻结 QA/S，也不得作为多 R B 的最终同步对象。
- 固定机器入口为 `python E:\workspace\tools\r_fix_review.py sync-final-candidate --batch-id B<N> --candidate-strategy direct|merge --candidate-dir <最终候选目录> --review-status <Review 状态文件> --code-root E:\workspace\workbuddy --review-root "E:\workbuddy 复审" --snapshot-root E:\workbuddy-snapshots`。
- 旧候选缺少新式源树/批准差异时，只能先由 `recover-history-source-package` 依据同一 R/Fix 的已验证 begin 快照、候选源清单和可审计来源生成独立只读 `source-recovery` 包；重建差异必须匹配候选已冻结的 `approvedDiffFingerprint`，不得改写历史候选。标准 `sync-final-candidate` 只自动采用身份、哈希、完整性和只读状态全部通过的恢复包；显式声明的候选源工件缺失时不得静默回退。
- 机器唯一事实是 `E:\workbuddy 复审\<B>\control\source-sync-result.json`。成功必须为 `sourceSyncStatus=verified`，并同时更新 `E:\workbuddy 复审\current-development-pointer.json`；失败只能为 `blocked` 或 `failed`，不得写 QA/S 已冻结、用户通过或 `🟢等待下一轮测试`。
- 同步只写批准差异文件，保留无关改动；新增、删除、文件/目录类型变化、Git index 冲突和同一批准文件的并发改动均需单独核对。写入失败必须回滚，回滚失败则保持阻断并记录残留文件。
- B 的 `operationalClosureStatus` 在缺少同步结果、同步状态不是 `verified`、开发指针不匹配最终候选、源包不完整/清单哈希不一致、同步冲突、回滚失败或存在未批准文件变化时保持未关闭；该字段不得被文档声明或旧 QA/S 快照替代。
- `15A` 不负责代码审查、用户实测、QA/S 编号或测试计划；成功后只在唯一权威 B/R 全流程文档追加同步记录，并引用机器结果，不重复维护另一套哈希。
## 十、长期实测版本、运行归档与入口门禁

### 10.1 版本身份与运行身份

- `C0` 是开发基线，`QA` 是 Fix/Review 后的候选代码状态，`S` 是由 15 冻结的不可变被测程序包，`G1` 是版本级整合测试门；它们不能由目录名称互相推断。
- 每次实际运行另有唯一 `runId`。`runId` 绑定一个计划集合、一个冻结 `S` 和一组运行归档目录；每个计划/角色通过 `roleDataMap` 绑定自己的可写工作数据目录和数据库。重试、新计划或需要干净前置时必须创建新的 `runId`。
- 同一计划、同一角色的一组连续步骤复用同一 `runId` 和数据库；GPT 与 USER 必须使用不同工作数据目录/数据库，不能通过前缀代替数据库隔离；同一 `runId` 可以包含多个计划/角色映射。

### 10.2 不可变 S 与可替换 current

- S 主档永久保留在 `E:\workbuddy-snapshots\<S-ID>\out`，并同时保留快照记录、全量清单和清单哈希。普通实测只能引用 S 主档，不能从 `E:\workspace\workbuddy`、当前开发目录或复审工作目录直接启动。
- `E:\workbuddy-test\current\active-run.json` 是当前运行指针，`selected-run.json` 是当前角色选择指针；只允许原子替换这两个清单，不允许覆盖历史 S、数据库、运行归档或证据。
- 可写的运行 `userData` 放在 `E:\workbuddy-test\work\v版本\B批次\计划\角色\<runId>\userData`；归档目录只保存封存数据库、必要状态、日志和证据索引，工作目录不是历史证据源。
- B1 完成后的长期入口必须核对计划 ID、角色、`runId`、S-ID、完整清单哈希、数据库路径和测试前缀，并拒绝命令行替代入口。B1 当前批次运行期间，B1 当前批次的 `启动实测.bat`、`选择B1实测角色.bat` 和 `B1实测入口预检.ps1` 继续承担当前操作职责；长期入口当前已预建但未启用，只能在 B1 完成并满足明确切换条件后使用，不能覆盖同名 B1 设施。
- 默认启动 `snapshot-direct`。只有预检证明 S 目录不可执行、程序必须写安装目录或需要离线/可搬运部署时，才允许 `app-current` 受控投影。投影要停进程、复制到临时目录、全量校验、保留旧投影、原子切换并在失败时恢复；`app-current` 不是 S 身份。

### 10.3 数据库、状态和证据封存

- 运行结束、阻断、取消或未实际执行都必须关闭 WorkBuddy 后封存；状态只能为 `completed`、`blocked`、`aborted` 或 `not-tested`，不得把已启动但未完成写成通过。
- 封存至少包含 `workbuddy.db` 以及存在的 `workbuddy.db-wal`、`workbuddy.db-shm`，必要应用状态、入口/环境清单、日志和证据索引，并计算逐文件哈希。缓存、Cookies、密钥和锁文件不进入普通最小复现集。
- workspace 中的实测计划、截图、GPT 报告和用户回传仍是事实真相源；运行归档只保存相对路径、绝对路径和哈希索引。关键、偶现、环境、数据损坏、安全边界或双方冲突问题，按记录的 S-ID 复制完整 S 主档到增强复现目录。
- 旧数据库永不覆盖、迁移或删除。禁止用删除数据库的脚本“重置”测试；需要干净前置时创建新的 `runId` 和新数据库。

### 10.4 归档与备份门

- E 盘是主档，运行归档按 `E:\workbuddy-test\archive\v版本\B批次\计划\角色\<runId>\` 保存；D 盘 `D:\workbuddy-test-archive` 是逐文件校验后的备份根。
- 备份成功前状态为 `backup-pending`；只有源/备份逐文件哈希一致并写入备份清单，才可记录 `backup-complete`。备份包含运行归档及清单引用的 workspace 证据副本，并注明副本不是第二真相源。
- B1 完成后的长期计划必须在启动前记录 `runId`、运行归档根、当前清单、数据库归档位置、证据索引、封存状态和备份状态。B1 当前批次计划不登记长期 `runId`，不使用 `E:\workbuddy-test\work\...\runId\userData`，而按 B1 数据根和角色日期目录登记；缺少适用的长期字段不能反向阻止本次 B1 的 T01。

### 10.5 长期入口阶段切换开关

- 长期入口除检查 `active-run.json`、`selected-run.json`、S 快照、入口、角色和数据隔离外，还必须检查 `E:\workbuddy-test\current\phase-switch.json`。开关文件缺失、字段缺失或值不一致时，长期入口默认拒绝启动。
- 开关文件是机器可读的阶段切换指针，最少包含：`schemaVersion=1`、`state=disabled|enabled`、`stage=B1|long-term`、`b1Status=in-progress|closed`、`currentPointer=E:\workspace\当前审查状态.md`、`enabledAt`、`enabledBy` 和 `planIds`。
- 只有同时满足 `state=enabled`、`stage=long-term`、`b1Status=closed`、`currentPointer` 指向当前审查状态快照，且该快照的“长期入口切换状态（机器闸门）”也为 `enabled`，才允许使用长期入口。`active-run.status=sealed` 不能单独授权长期入口。
- 当前 B1 批次必须保持 `state=disabled`、`stage=B1`、`b1Status=in-progress`；当前 B1 的一次性入口不读取或写入长期阶段开关。B1 关闭后，先由 GPT/PM 更新当前指针和开关，再由后续计划使用长期入口。

## 十一、R Fix 自动候选、恢复与批次整合门

用户实测 R 的 Fix 不是手工复制构建物的例外流程，而是一个必须可重复执行的机器交接。07 在统一 Fix 开始前调用 E:\workspace\tools\r_fix_review.py begin-fix，保存 E:\workspace\workbuddy 的 tracked/non-ignored 文件、Git index、HEAD、状态、文件树指纹和工作区指纹；Fix 完成并构建后调用 complete-fix。

complete-fix 只有在候选源 baseCommit 等于 begin-fix 基线、候选和开发区变化都完全落在批准文件集合内时，才创建 E:\workbuddy 复审\<B<N>>\R<N>-Fix<M>-only。候选目录必须拥有独立 app、启动包装、userData、evidence、review-meta.json、完整构建清单和 SHA-256。发现未归属变化、并发变化、重复目标或哈希不一致时停止，不覆盖既有候选。

候选复制完成后，工具可恢复 Fix 前代码开发区，但只能删除本次 begin-fix 之后新增且已归属的 non-ignored 文件，并逐文件恢复快照和 Git index。恢复后必须重新计算文件树、Git 状态、index SHA-256 和工作区指纹；restoreStatus 不是 verified 或指纹不一致时，不得进入 05。该条是 07 机器交接流程的明确授权，不构成 GPT、GLM+DS 或其他阶段对用户既有改动的擅自清理；node_modules、dist、out 和真实用户数据不属于恢复范围。

批次冻结后，finalize-batch 记录预期 R/Fix 集合，但每次 merge 前必须 scan-batch 动态枚举 E:\workbuddy 复审\<B<N>>。未登记 R、重复 R、孤立目录、缺失 Review、非 passed Review、恢复未验证、构建清单或哈希异常均阻断 merge。只有所有登记 R-only Review 通过，prepare-merge 才能向 GLM+DS 发出整合交接。

GLM+DS 在 E:\workspace\workbuddy 中整合并调用 complete-merge。工具只允许批准 R-only 变更并集及显式记录的冲突解决文件，生成同批次 merge 候选、独立 userData/evidence、全量清单和哈希；merge 的 restoreStatus 固定为 not-applicable-after-merge，开发区必须保留整合版本。随后 13 创建或验证唯一 B<N>-merge 全流程闭环文档，05 在该文档追加集成 Review；失败只追加批次级修复记录，不回流或拆分 R。最终 merge Review 通过后必须经过 `15A → 15`，才可交 `14`。

上述工具状态是机器门禁和证据索引，不替代 GPT 的 GUI 复审、用户 06、15 的 QA/S 冻结或 14 的计划创建。所有自动动作必须幂等；已有终态不可覆盖，真实用户数据不得读取、复制、清空或删除。
