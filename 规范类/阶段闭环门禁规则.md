# 阶段闭环门禁规则

> **制定**：2026-08-12
> **维护方**：GPT
> **作用**：定义开发单元、功能实测和项目维护期的门禁。新规则使用 `C0 / S / R / Fix / Review / QA / G1 / C1`；现有 v0.3 历史文件保持原样，不迁移、不重写。完整代称见 `规范类/项目代称.md`。

---

## 一、门禁总表

| 层级 | 进入条件 | 通过条件 | 主要裁决方 | 状态 |
|---|---|---|---|---|
| 开发单元闭环 | 开发单元实现完成并提交审查 | GPT 审查/复审通过、验收点全通过、无未关闭高风险项 | GPT | `🟡实现中 → 🟡待审 → ✅开发闭环` |
| `C0` 实测基线 | 当前目标版本全部开发单元闭环，变更归属明确 | 基线提交、Tag、版本/构建标识、程序入口和测试隔离均可核对 | GPT | `✅开发闭环 → C0` |
| 功能实测前置 | 已存在适用的 `C0` 或正在复用已批准版本基线 | 首份计划绑定 `C0/S0`；后续计划绑定冻结的 `S` 快照 | GPT | `C0 → 🔜待实测` |
| `QA/S` 候选快照 | Fix/Review 形成新的可测代码状态 | 候选来源、工作树/提交指纹、构建物哈希和独立目录均可复核 | GPT | `Fix/Review → QA → S` |
| 问题来源轮次 | 某次 `R<N>-<n>` 双方实测产生结果 | 回归/新增问题已分流，或本轮无回归无新增 | GPT 编排 + 用户事实 | `📝待证据 / 🟡待修复 / ✅当前轮次闭环` |
| 功能用户实测闭环 | 所有活跃问题来源轮次均关闭 | GPT 客观实测、用户核心链路/主观实测均有证据，且 G1 通过 | 用户最终验收，GPT 记录门禁 | `🔜待实测 → ✅功能用户实测闭环` |
| `C1` 正式版本 | 当前版本所有活跃功能/问题轮次关闭且 G1 通过 | 双方证据齐全、用户完成最终验收、正式版本和 Tag 已锁定 | GPT 记录 + 用户验收 | `G1 → C1` |
| 项目维护期 | 全部功能闭环且阶段 6 用户 E2E 完成 | 项目级验收闭环，按变更闭环规则进入 CR | 项目治理规则 + 用户验收 | `✅项目闭环 → 维护期` |

“功能实测前置”不是用户验收；“GPT 自主实测通过”不是用户验收；单个功能达到“功能用户实测闭环”也不等于项目进入维护期。

## 二、角色与状态看板权限

| 文档 | 唯一维护方 | 其他角色 |
|---|---|---|
| `当前代码状态.md` | DeepSeek | GPT 只读，核对实现真实性 |
| `当前审查状态.md` | GPT | DeepSeek 只读，读取审查要求 |
| 开发单元全流程记录 | GPT/DeepSeek 按环节追加 | 不删除、不覆盖历史 |
| 用户实测轮次全流程记录 | GPT 通过 13 创建/续写；DeepSeek 通过 07 写 Fix | 用户原始回传和双方证据只引用，不改写事实 |

GPT 不得修改产品代码、数据库或 `当前代码状态.md`；DeepSeek 不得修改 `当前审查状态.md`。状态看板的当前结论必须与对应全流程文档最新正式结论一致。

## 三、开发单元闭环

### 判定条件

- 规格、实现、审查、修复（如有）和复审记录齐全；
- 所有开发单元验收点有实际证据通过；
- 无未关闭的 `HIGH/CRITICAL`、技术栈红线或越界改动；
- GPT 复审明确写出 `✅通过（开发单元闭环）`。

### 状态流转

```text
🟡实现中 → 🟡待审 → 03 审查 → 04 修复（如有）→ 05 复审 → ✅开发闭环
```

`当前代码状态.md` 中“待 GPT 审查/待 GPT 复审”是 DeepSeek 交审前置状态，不覆盖 GPT 已有的正式通过；但实现/修复失败或事实与证据矛盾时，必须重新处理。

## 四、进入功能实测的硬门：C0

GPT 创建当前目标版本第一份 `R<N>-1` 测试计划前，只读核对并形成 `C0`：

1. 所有开发单元均为 `✅开发闭环`；
2. 整个 `E:\workspace` 工作区内所有非忽略变更均已明确归属；无法归属的变更必须停止，不能擅自提交、删除或还原；
3. C0 基线已提交 Git，能锁定提交号、构建标识和对应版本字段；
4. C0 Tag 已创建，且提交内容与待测代码一致；
5. 程序入口、启动方式、操作系统和窗口环境明确；
6. 测试专用目录、测试数据目录和真实用户数据隔离边界明确；
7. 需要重置时，命令只指向测试数据副本并有恢复步骤；
8. 由 C0 生成的 `S0` 已冻结，记录构建目录、构建物哈希和测试数据隔离信息。

任一项无法确认，计划只能记录 `🟡待补前置`，停止创建可执行测试计划和业务实测。不得用代码猜测、历史截图或 DeepSeek 自测替代核对。

### 4.1 C0 之后的测试计划门

- `C0` 只在开发阶段进入功能实测时执行一次；它不是每个 `R<N>-<n>`、Fix 或 Review 的重复门锁。
- 同一版本的后续测试计划不要求重新提交 Git，也不要求工作树重新变干净；已有未提交修复不得被忽略、清理或伪装成已提交。
- 每次实际 GUI 测试必须绑定一个冻结的 `S` 快照。代码、依赖或构建输入改变时，必须形成新的 `QA` 候选和新的 `S`；构建输入完全相同可以复用原快照。
- `S` 必须记录来源（C0/QA、提交号或完整工作树指纹）、构建目录、构建物哈希、版本字段和测试数据目录。GPT 与用户使用同一被测构建物，不得各自从不同工作树启动。
- 无法冻结或复核 `S` 时，计划只能保持 `🟡待补前置`，不得启动业务实测。

## 五、用户实测轮次门禁

### 编号定义

- `R1/R2`：问题来源轮次；仅发现新增独立问题时开启下一轮。
- `R1-1/R1-2`：同一轮内的具体测试计划；每次实际测试都新建计划。
- `C0`：当前目标版本全部开发单元闭环后的唯一实测基线提交。
- `S0/S1/S2`：实际被测的不可变构建快照；`S0` 绑定 C0，后续 S 绑定对应 QA 候选。
- `QA1/QA2`：实测阶段候选代码状态，按当前目标版本全局递增，不是正式版本，也不是每次测试的强制 Git 提交。
- `Fix1/Fix2`：DeepSeek 修复批次，回写触发它的 `R` 文档。
- `Review1/Review2`：GPT 复审批次，回写同一 `R` 文档。
- `G1`：所有活跃轮次关闭后的版本级整合回归，不创建新问题轮次。
- `C1`：当前版本所有活跃功能/问题轮次关闭、G1 通过且用户完成最终验收后的当前目标版本正式节点。
- `R1-1-T01`：测试点稳定 ID，贯穿计划、报告、回传和证据。
- `G1-T01`：G1 计划内稳定测试点 ID，不创建 `R` 编号。

### 文档落点

```text
用户实测阶段\vX-功能名\第N轮\vX第N轮用户实测计划（n）.md
用户实测阶段\vX-功能名\第N轮\vX-第N轮-问题概述-全流程闭环记录.md
GPT实测记录\vX实测内容\第N轮\vX-R1-1-GPT实测.md
```

版本级 `G1` 使用独立落点，不归入任何 `R` 轮次：

```text
用户实测阶段\vX-版本级整合\G1\vX-G1版本级整合测试计划.md
用户实测阶段\vX-版本级整合\G1\用户证据\G1-T<NN>-<场景>.<扩展名>
GPT实测记录\vX实测内容\G1\vX-G1-GPT实测.md
GPT实测记录\vX实测内容\G1\证据\G1-T<NN>-<场景>.png
```

同一 `R<N>` 只能有一份全流程闭环文档。GPT 报告单独写入 `GPT实测记录/`；用户不建立独立实测报告，通过 06 回传。缺少 GPT 或用户正式证据时，13 只能停止或创建明确的 `📝待补证据草稿`。

### 双方共同核心链路

测试计划必须把核心链路同时分给 GPT 和用户。GPT 负责客观状态、回归、数据一致性、错误降级、隔离和安全；用户必须亲自执行核心链路并反馈理解、自然性、文案、信任和确认/取消体验。双方证据互不替代。

### 轮次分流

| 本轮结果 | 处理 | 门禁影响 |
|---|---|---|
| 无回归、无新增 | 当前 `R` 标记 `✅当前轮次闭环`，等待所有活跃轮次与 G1 | 不直接宣布功能闭环 |
| 仅回归 | 回写当前 `R`，`Fix → Review →` 同轮下一测试计划 | 当前轮保持活跃 |
| 仅新增 | 当前轮按“无回归”事实收束；新建 `R+1` 和 `R+1-1` | 新轮保持活跃 |
| 回归 + 新增 | 回归留当前 `R`；新增新建 `R+1`，可并行 | 任一活跃轮未关闭都不能完成版本 |
| 证据不足/环境阻塞 | 待补证据或待用户实测，不进入 Fix | 不得写通过 |

问题分类由 GPT 根据双方证据完成；用户可以报告客观缺陷，但不需要先判断“回归/新增”。

## 六、G1 版本级整合回归

### 触发条件

所有活跃 `R` 轮次均已关闭，且每轮的 GPT 客观测试和用户核心链路证据齐全。

### 执行范围

- 所有活跃轮次的核心链路和已修复问题；
- 跨功能数据流、刷新/重进、错误降级、取消保护、数据一致性；
- 测试数据隔离、安全边界、版本/构建一致性；
- GPT 客观验证与用户核心链路确认。

### 裁决

`G1` 通过才可以把功能标记为 `✅功能用户实测闭环`，并具备形成当前目标版本 `C1` 的条件。G1 发现问题时按证据判断是现有轮次回归还是全新问题，回写相应轮次或创建下一轮；G1 本身不成为 `R` 轮次。

## 七、功能用户实测闭环与维护期

功能用户实测闭环必须同时满足：

1. 所有活跃 `R` 轮次关闭；
2. GPT 客观实测有正式报告和证据；
3. 用户亲自完成共同核心链路和用户范围，并通过 06 回传；
4. 双方证据已由 13 合并到轮次唯一文档；
5. `G1` 版本级整合回归通过；
6. 用户作出最终验收裁决。

满足上述条件只关闭该功能的用户实测；当前目标版本还必须完成所有活跃功能/问题轮次、版本级 `G1` 和 `C1` 归档，不能称“项目进入维护期”。只有全部功能和阶段 6 用户 E2E 完成，才按 `规范类/变更闭环规则.md` 进入维护期、CR 和项目级版本发布。

## 八、历史兼容和文档纪律

- 旧 v0.3 测试计划、旧 GPT 记录和旧全流程文件保持原样，作为历史审计证据。
- 新规则只向前生效，不迁移、不重写历史审计线。
- 新复审结论追加到对应全流程文档，不再使用 `审查日志/` 文件夹。
- 历史章节的 `🔴/🟡` 是审计事实；当前门禁只看最新正式结论，不做历史徽标全文计数。
