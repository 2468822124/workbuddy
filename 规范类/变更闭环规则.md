> **版本**：v1.0.0

> **影响范围**：维护期（C1 后）  
> **向后兼容**：N/A

> **维护方**：GPT（项目经理）。本文件是**维护期（阶段 6 关闭后）** 代码变更闭环的操作手册。
> **上位文件**：`规范类/文档治理总纲.md`。**配套**：`用户prompt/08`（GLM+DS 执行）、`用户prompt/09-维护期CR-gpt审查.md`、`模板/04_反馈部分/变更请求部分编写模板.md`、`模板/02_日志部分/变更日志部分编写模板.md`。
> **建立日期**：2026-08-07。

## 0. 核心承诺（用户硬要求）

> 「后续每次对代码的编辑都应当**记录、审查、修复/成功、复审**；出现的所有问题都应当有**记录**与**修复指导**。」

本规则把上面这句话制度化。维护期的任何代码改动，**没有 CR（或用户反馈）编号、未经 GPT 审查通过，不得视为完成**。

---

## 1. 两种闭环总览

| 闭环 | 适用期 | 单位 | 链路 | 操作 |
|---|---|---|---|---|
| **构建期**（已存在） | 阶段 0–6 | 阶段 N | `规格-阶段N` → 对应开发单元全流程闭环记录 | `用户prompt/01–05`、`项目计划.md §7` |
| **维护期**（本文件） | 阶段 6 关闭后 | CR-NNN | CR 全流程记录（变更请求 → 实现日志 → 审查/复审 → 闭环）→ `CHANGELOG` | `用户prompt/08–09` + 本规则 |

**判定当前用哪套**：看 `当前代码状态.md` 与 `当前审查状态.md` —— 若阶段 6 标记"✅ 全部关闭（含用户实跑 E2E）"，则进入维护期，一律用 CR 闭环；否则仍属构建期，用阶段闭环。

---

## 2. CR 触发条件（何时开 CR）

阶段 6 关闭后，**凡涉及代码改动**，必须先开 CR-NNN：

1. **用户实测 bug**（post-GA）：用户在 `用户最终测试反馈/用户反馈N.md` 报问题 → GPT 诊断后开 CR 并链接反馈号。
2. **滚动改进项转工单**：`当前代码状态.md §7 已知后续改进项`（如"今日总览已完成 x/y 须随勾选动态更新"）→ GPT 将其转为 CR-NNN 动工。
3. **GPT/GLM+DS 发现的内部缺陷**：直接开 CR。
4. **新增小功能 / 重构 / 依赖升级 / 打包配置调整**：开 CR。

> **不开 CR 的例外**：纯文档改动（GPT 域内的规格/治理/说明文档）由 GPT 直接维护并在对应治理文档的决策/变更记录中留痕，无需 CR；新文档改动不创建 `审查日志/`。若文档改动伴随代码改动，则代码部分仍需 CR。

## 3. CR 全闭环（5 步，每步标角色）

```
① GPT 起 CR  →  ② GLM+DS 修复  →  ③ GPT 审查  →  ④ 🟡? 回到 ②(04/05)  →  ⑤ ✅ 关闭
```

**① GPT 起草 CR**（用 `模板/04_反馈部分/变更请求部分编写模板.md`）
- 产物：`变更开发/vX-{功能名}/CR-{NNN}-{简述}-全流程闭环记录.md` 的「变更请求」环节
- 必含：现象/复现 · 根因诊断(概率排序+代码位置+证据) · 范围(含/不含) · **修复计划(file:line，具体改什么)** · **验收点(可勾选可验证)** · 严重度(🔴/🟡/🔵) · 禁止边界&降级核查 · 版本影响(目标版本号)
- 源自用户反馈 → 在 CR 元信息填"起源：用户反馈N"并链接；源自 §7 滚动项 → 填"起源：滚动项"。
- 完成后告知用户「CR-NNN 规格已就绪」，用户转 GLM+DS（用 `08` prompt）。

**② GLM+DS 执行修复**（用 `用户prompt/08-维护期CR-DeepSeek执行.md`）
- 约束：**只修 CR §修复计划指出的问题**，不扩大范围、不擅自重构；偏差在 `当前代码状态.md` 记录原因。
- **强制复跑 CR §复现步骤 / 失败场景**（吸取教训：动态 `require` 因 headless 未实跑而潜伏 6 阶段）——不能只查代码。
- 记录义务（缺一不可）：
  - 在同一 CR 全流程记录的「变更日志」环节追加 `Fix` 小节（用 `模板/02_日志部分/变更日志部分编写模板.md`）。
  - 更新 CR 全流程记录的 `§闭环记录` 表（GLM+DS 行：真实执行者、改了什么 + 日期）。
  - 更新 `当前代码状态.md`（修复摘要、影响范围、复审所需信息）。
- 完成后报告「CR-NNN 修复完成，待 GPT 审查」，用户用 `09` 启动审查。

**③ GPT 审查**（用 `用户prompt/09-维护期CR-gpt审查.md`）
- 依据：CR `§验收点`（权威基准）+ `当前代码状态.md`（先核对真实性）+ 项目计划 §7-B/§7-C。
- **必须实地运行验证，不只看 diff**；逐条核 §验收点 + 禁止边界 + 降级（构造失败场景）。
- 产物：在同一 CR 全流程闭环记录内追加「审查/复审」环节（用 `模板/03_审查部分/审查部分编写模板.md`，结论三态）；不新建 `审查日志/`。
- 结论：
  - ✅ 通过 → 进 ⑤ 关闭。
  - 🟡 需修复 → 列剩余项，回 ②（用 `04` 修复 + `05` 复审，引用 CR-NNN）。
  - 🔴 驳回 → 说明重大原因（如严重越界、破坏禁止边界）。

**④ 🟡 修复循环**（复用现有 `04`/`05` prompt）
- GLM+DS 用 `08` 按同一 CR 全流程记录的修复要求逐条修；GPT 用 `09` 复审；直至 ✅ 或 🔴。每次循环追加同一 CR 全流程记录的修复/复审小节。

**⑤ ✅ 关闭**（GPT 执行）
- 版本 bump（见 §5）：按 CR 严重度定 `0.X.Y`。
- `变更记录/CHANGELOG.md` 追加一行（版本 + CR 号 + 一句话 + 日期）。
- 更新 `当前代码状态.md`（如涉及 §7 滚动项，勾除或更新）。
- 若源自用户反馈 → 回链对应 `用户实测阶段/` 轮次唯一全流程记录，记录 CR 号、终态和日期；历史 `用户最终测试反馈/` 只保留原样。
- CR `§闭环记录` 终态行 + CR 元信息状态改 ✅ 已关闭。

## 4. 问题 → 记录 → 修复指导（成文硬要求）

> 对应用户硬要求「出现的所有问题都应当有记录、修复指导」。

1. **任何问题必落档**：用户/GPT/GLM+DS 发现的任何 bug、异常、偏差，**必须**落成用户实测轮次唯一全流程记录或 `CR-NNN` 全流程记录，**不准只在聊天/口头里解决**。聊天里的结论若不改代码可不落档；一旦要改代码，必须先补 CR/反馈编号。
2. **落档必含六要素**：① 现象 ② 复现步骤 ③ 预期 vs 实际 ④ 根因诊断(概率排序 + 代码位置 + 判断证据) ⑤ **修复计划(file:line，具体改什么)** ⑥ 验收点 + 严重度。
3. **信息不足不准瞎猜**：诊断证据不足时，列「需补充」清单（要谁做什么检查/截图/命令输出），不要下无据结论（参考用户反馈1 的三轮收敛过程，是正例）。
4. **修复指导要可执行**：修复计划写到 GLM+DS 无需再问即可动手（file:line + 改什么 + 为什么 + 验收点）。

## 5. 版本与 changelog 策略

**语义化版本 `MAJOR.MINOR.PATCH`**（Day-1 起 = `0.1.0`）：

| 改动类型 | bump | 示例 |
|---|---|---|
| 🔵 小修/打磨/LOW 收敛 | PATCH（末位 +1） | `0.1.0` → `0.1.1` |
| 🟡 需修缺陷、行为变更、依赖升级、**0.x 期新增功能** | MINOR（中位 +1，末位归 0） | `0.1.0` → `0.2.0`（计划与复盘体系） |
| 🔴 阻断修复（大）、**破坏性改动** | MAJOR（首位 +1，后归 0） | `0.2.0` → `1.0.0` |

> **0.x 期新功能例外（2026-08-07 增补）**：项目未到 `1.0.0` 前，**新增功能模块**按 **MINOR** bump；MAJOR 留待 `1.0.0` 正式发布或真正的破坏性改动。裁决来源：计划与复盘体系立项（`计划与复盘体系实现项目计划/项目计划.md §13`）。

- **bump 时机**：CR 在 ⑤ 关闭时 bump；连续多个 CR 可合并到一个版本号发布（在 CHANGELOG 列多条）。
- **CHANGELOG 格式**（Keep a Changelog 风格，倒序）：
  ```
  ## [0.1.1] — 2026-08-XX
  - 修复：今日总览「已完成 x/y」不随勾选更新 (CR-001, 🟡)
  ```
- `package.json` 的 `version` 由 GLM+DS 在 CR 修复时同步（属代码改动）。

## 6. 闭环硬门（不可破）

| 门 | 规则 | 违反后果 |
|---|---|---|
| **H1 编号门** | 维护期任何代码改动必有 CR-NNN 或 用户反馈N 编号 | GPT 审查直接驳回，不进细节 |
| **H2 审查门** | 每个改动必经 GPT 审查（实地验证），GLM+DS 不得自判通过 | 视为未完成 |
| **H3 复跑门** | GLM+DS 必须复跑 CR/反馈的失败场景，不能只查代码 | 审查不通过（吸取动态 require 教训） |
| **H4 边界门** | 承袭项目计划 §7-B 禁止边界、§7-C 降级，任何 CR 不得破红线 | 🔴 驳回 |
| **H5 记录门** | 每个 CR 必有一份全流程记录，且其中的变更请求、实现日志、审查/复审和闭环环节齐全；GLM+DS 的实现事实同步到 `当前代码状态.md` 并标真实执行者 | 视为流程缺失，补齐才关闭 |

> 这五道门即用户硬要求"记录/审查/修复/复审"的强制实现。

---

## 7. 制度演进

本规则修订须在本文件或对应治理文档的决策/变更记录中留痕（修订项 + 原因 + 影响），并同步 `文档治理总纲.md` 与 `文档索引.md`；不得为新修订创建 `审查日志/`。
