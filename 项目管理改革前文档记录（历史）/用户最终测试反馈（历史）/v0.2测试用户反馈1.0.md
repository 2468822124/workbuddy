## 1. 问题背景：输入文档 vs v0.2 真实架构（根本错位）

| 维度 | 输入文档设想（网页 LLM） | v0.2 真实架构（代码核实） | 矛盾 |
|---|---|---|---|
| 真相源 | `base_task`/`plan_schedule` 规范化表 + 外键树 | `plans.content` 的 **Markdown 原文**为真相源，靠解析 `- [ ]` 行 + 文本匹配串联月/周/日 | 文档抛弃手帐灵魂 |
| 层级关联 | `parent_schedule_id` 外键引用 | 无外键树；`sourcePlanId` + `labelTodoSource` 五规则**推断**出处 | 文档凭空建树 |
| 删除 | 物理级联 `ON DELETE CASCADE` 递归删下游 | **全软删除铁律**；方案B：删日任务行→open 软删/**done 留历史** | **文档级联会销毁 done 历史，推翻方案B** |
| 溯源 | `plan_schedule` 自带层级 | `todos.sourcePlanId` + 五规则 tag（反馈3.2 刚加） | 文档不知 3.2 已做 |

**关键**：文档的"源头删除→递归级联删全部下游"会直接销毁用户 5 天前亲自定稿要保留的 done 历史 → **推翻方案B**。网页 LLM 不知道这些决策的存在。

## 2. GLM 诊断：4 个「参照完整性」缺口（代码级核实，全部实测真问题）

用户实测反馈3.2 后仍觉"没解决根本问题"。经代码级核实，确诊 4 缺口（3.2 只做了出处 tag + 日级删行分流，**未碰这 4 个**）：

- **① 反向不同步** 🟡：选取周任务进日计划、后删/放弃，weekly 那条卡在「已下沉 `[x]`」回不到可选，须手改。代码：`pickTask` 不再 eager 标记（方案C）；weekly 的 `[x]` 仅在 `TODOS_TOGGLE` 完成/取消时改（`todos.ipc.ts:32-81`）；删日任务行走 `syncPlanTodos` orphan 分流，**不触发 weekly 回退**。规格 §5.4/§11 刻意"不做反向同步"（YAGNI）。
- **② 文本匹配脆弱** 🟡：所有级联靠任务文字**精确匹配**（`m[2].trim() === content.trim()`）。改名 / 同名多行 / 空白差异 → 下沉与勾选匹配错或不上。代码：`todos.ipc.ts:47/63`、`plans.ipc.ts` markTaskConsumed。
- **③ 出处链断裂** 🟡：todo 最多追溯到「日规划·{date}」，**追不到周任务、更追不到月任务**；选过的周任务出处**根本没存**（todo.sourcePlanId 指向日计划，非周计划）。代码：`todoSource.ts` labelTodoSource 仅到日规划级。
- **④ 删除不传播** 🟡：删周/月任务 → 日待办不消失（runSync 门控：`plans.ipc.ts` 周/月跳过 syncPlanTodos，不生成/不维护 todo）；删日任务 → weekly 不回退（同①）。

## 3. 方向抉择：重做 vs 增量（光谱 + 决策轨迹）

稳定身份是根治②的前提（用户锁定），故对比围绕"稳定身份加多少"展开为一条光谱：

- **L1 极轻增量**：任务行内联隐藏 ID + todos 加 `parentTaskRef` 列；Markdown 仍唯一真相，零新表。
- **L2 半规范化**（✅ 定稿）：新增轻量 `tasks` 表（planId/tid/content/parentTaskId/consumed），`plans.content` 保留为手帐真相，保存时双向 sync；todos 加 `parentTaskRef`。
- **L3 全重做**：`base_task` 实体 + `plan_schedule` 外键树（输入文档方案）；真相源移到 `base_task`。

**冲击半径**（核实）：L2 冲击圈死在「规划/级联」子系统（项目管理/模板/AI复盘/提醒/晨间热点/复盘 CRUD 全不动，✅）；L3 横扫全平台（项目管理/模板/计划编辑/导入导出/存量迁移/5 轮反馈全重验，🔴）。

**关键否决**：
- **L3 否决**：代价（横扫全平台 + 推翻方案B/手帐灵魂 + 5 轮全重验 + 存量迁移）远超收益；且文档的物理级联 `ON DELETE CASCADE` 是**红鲱鱼**——任何方案都得用应用层 open/done 分流（全软删铁律 + 方案B 禁物理级联），L3 在"删除语义"上**无任何优势**。L3 唯一正当理由是"任务即一等实体"愿景（跨期复用/任务库/知识库任务化），用户经多轮验证**未触及**。
- **混合/双模型否决**：dual-model 反模式——维护两套全栈 + 桥接，成本逼近 L3 而复杂度更高；"每次创建问是否独立"=UX 税；"项目任务自动独立"=触发项目管理重写。集两端之短。

**用户未来功能压力测试（均验证 L2 够用，作为 L2 充分性证据）**：
1. 交接流转（今日未完成→交接→次日/任意日选取完成/删除）：顺延机制已具雏形，L2 不动 todo 核心模型。✅
2. AI 多轮问答生成复盘/计划（子阶段4 引导式提问升级版，AI 读现有数据，与数据模型无关）。✅ ⚠️约束：弹窗与项目"禁模态弹窗"规则冲突（需改侧抽屉/内联，或推翻规则）；"运动"模块未建（规格 §2 不含）。
3. AI 识别一周内低完成率任务并提问：按任务文字聚合统计即可（孤立亮点，非整条"任务分析/循环任务"方向——后者才是 L3 正当理由，用户确认无此方向）。✅
4. 项目任务池→今日总览新模块 + 月/周/日计划 rail 选取：项目任务池=查 `todos WHERE projectId 非空 AND status='todo'`（数据已在，零新表）；选进今日=设 `planDate` 复用同一 todo（无重复）；选进日计划=插行 + `syncPlanTodos` 按 id 复用已链接项目 todo（非新建）；选进周/月=引用文本（runSync 门控不生 todo）。靠 L2 的"稳定身份+链接"层（同 ②③①④）延伸覆盖，无新分散复杂度。✅ ⚠️实现点：`syncPlanTodos` 须优先复用已链接项目 todo（按 id，非文字）而非新建，否则缺口②复发 + 重复 todo。L3 仅在"同任务同时排多天独立完成（循环/多实例）"占优——用户确认无此需求。

> 反直觉技术真相（记入防反复）：即便 L3，对"每天重新输入的同名任务"也只能靠名字匹配识别（除非显式复用同一任务实体，需额外建循环任务功能）；故功能3 在 L2/L3 实际效果接近。

## 4. 定稿：L2 半规范化（用户锁定 2026-08-10）

**载体定义**：
- `plans.content`（Markdown）**仍为手帐真相源**，手帐灵魂与"写计划"体验不变。
- 新增轻量 `tasks` 表：`(tid PK, planId FK→plans, content, parentTaskId nullable, consumed, order)`；`plans` 保存时 `content ↔ tasks` 双向 sync（解析 `- [ ]`/`- [x]` 行 ↔ tasks 行）。
- `todos` 加列 `parentTaskRef`（= `parentPlanId + parentTaskId`，nullable）。

**4 缺口修法（L2 下）**：
- **② 稳定身份**：`tasks.tid` 给每条任务稳定编号；级联匹配键由"文字"改为"tid" → 改名不影响关联。
- **③ 出处链**：`todo.parentTaskRef` 指向上级 task → 逐级溯源（todo→周任务→月任务→源头）；UI 每任务标**直接上级**（非源头），可点击跳转到上级 plan + 定位任务行。
- **①④ 删除语义**：扩展 `syncPlanTodos` 的方案B open/done 分流到**跨级**——检测上级 task 被删 → 按 `parentTaskRef` 查下游 todo → open 软删 / done 保留并标"来源失效"。自洽扩展方案B，不违背。

**约束（一律不变）**：方案B、全软删除铁律、Markdown-as-truth、离线优先；存量 27 todo `parentTaskRef=null` 降级显示（不丢失、不强行回填出处）。

**工作量与范围**：约 1–2 个子阶段；migration `0005`（todos 加列 + tasks 新表）；改动圈在「规划/级联」子系统（planParser/planRepo/syncPlanTodos/CascadeRail/usePlanning/pickTask/TODOS_TOGGLE 同步/labelTodoSource→出处链/TodayView+PlanningView UI/导入导出 +tasks 表）。**不碰**：项目管理、模板、AI 复盘、自动提醒、晨间热点、对话搜索、复盘 CRUD。

## 5. 解决途径（实现路径概要；细则留子阶段规格）

1. migration `0005`：建 `tasks` 表 + `todos` 加 `parentTaskRef`（`addColumnIfMissing` 幂等，事务包裹，同 0003/0004 范式）。
2. `planParser`/`planRepo.syncPlanTodos`：复用键 content→tid；保存时 content↔tasks 双向 sync（含稳定标识生成与保持策略）。**此 id 复用机制亦为未来"项目任务选入计划"奠基（避免重复 todo）**。
3. `pickTask`/`markTaskConsumed`/`TODOS_TOGGLE`：匹配键 text→tid；写 `parentTaskRef`。
4. `labelTodoSource` → 出处链：读 `parentTaskRef`，显示直接上级，可点击跳转。
5. 新增"上级任务删除 → 下游 open 软删 / done 标失效"应用层逻辑（扩方案B 分流）。
6. UI：TodayView/PlanningView 出处链 tag + 点击跳转；CascadeRail 依 tid。
7. 存量：27 todo `parentTaskRef=null` → 降级（手动/顺延/日规划·date），不回填。
8. 自测：vitest（tid 匹配纯函数 + 出处链 + 删除分流）+ build 绿 + GUI 复跑 + 记 `当前状态.md` 偏差（migration 0005 触「无 migration」边界，同 0004 先例）。

**待子阶段规格细化（非本反馈记录范围）**：`tasks` 表 DDL 细则、content↔tasks 双向 sync 的冲突解决算法、稳定标识生成与保持（隐形编号 vs 段位/位置启发）、出处链点击跳转的 UI 定位方式、上级删除→下游分流的触发时机（保存时 vs 实时）。
