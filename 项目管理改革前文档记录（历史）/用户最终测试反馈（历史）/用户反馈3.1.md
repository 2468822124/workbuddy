## F3-1.1 日规划「本周周任务」rail 仍空 — 🔴 真实缺陷（HIGH，未闭环）

### 用户报告
- **现象**：日规划中按要求显示了**日规划模板**（模板串档已修 ✓），但在**已制定好本周任务**的前提下，「本周周任务」CascadeRail **依旧没有任务可选项**。
- **场景 D 同**：周统筹写的周任务未掉入日规划「本周周任务」rail。
- **是否报错**：否
- **截图**：2 张（已附）

### 用户重新讲述的级联业务逻辑（关键，逐字保留）
> 「周统筹在每周的末尾日进行（周日），包括周复盘与下周计划两部分，**下周计划制定完后，任务自动掉入下周的日规划的"本周周任务"中**。
> 如 W31 最后一天：8.2 制定完成 W32 的周任务（任务1、任务2、任务3），在未完成任何一项的前提下观看 W32：**8.3-8.9 任何一日都会在"本周周任务"中显示：任务1、任务2、任务3**。
> 若 8.3 选取"任务1"进入日规划，并完成，则 **W32 周统筹中的任务1 显示完成（划掉），且该周内后续天数的日规划的"本周周任务"中不再看到"任务1"。**」

**提炼的业务规则**：
1. 「本周周任务」= **当前查看日所在周**的 weekly_plan 任务（用户看 W32 任一日，rail 都是 W32 的任务）。
2. 在某日选取一个任务下沉 → 上级 weekly_plan 该任务 `[ ]→[x]`（划掉）。
3. 该周后续天数再看 rail，已下沉任务不再显示（消耗态）。

### GLM 诊断（代码逐行核实）
**裁定：🐛 真实缺陷。双重根因（期基准错 + 规划下周语义冲突）。**

**根因 A — CascadeRail 的「本周」基准用了明日（nextStart），而非今天（curStart）：**
- `usePlanning.loadParentTasks(planStart)`（`composables/usePlanning.ts:195-216`）的 `planStart` 由 PlanningView 传入，**当前传的是 `nextStart`（明日）**（`PlanningView.vue` load 末尾 `plan.loadParentTasks(nextStart.value)` + pickTask 亦传 nextStart）。
- 内部 `parentStart = periodStartFor('weekly', 明日)` → 取**明日所在周**的 weekly_plan。
- 用户业务规则 1：「本周周任务」= **当前查看日（curStart/今天）所在周**。两者在**跨周边界不一致**（如周日看日规划，明日已是下周一 → rail 取到下一周，空）；且语义上 rail 标题写的是「本周」，应指今天所在周。

**根因 B — 周统筹页固定「规划下周」，与「制定本周任务」心智冲突：**
- 周统筹页 PlanPanel 固定引用 `nextStart`（规划下期，规格 §5.3）。用户在**非周日**（如实测日 8.8 周六）进周统筹写周任务 → `nextStart('weekly', 8.8)` = 下周一 8.10（W33）→ 保存的 weekly_plan `date = 8.10`。
- 用户心智是「制定本周 W32 任务」，实际存到了 **W33**。回日规划取本周 W32（8.3）→ 空。
- 即便修了根因 A，若用户在周中/非周日制定任务仍会存到下周，rail 仍可能对不上。

**叠加效果**：用户实测（8.8）在周统筹制定任务（存到 W33 8.10）→ 日规划 rail 取本周（按 nextStart 8.9→W32 8.3，或按 curStart 8.8→W32 8.3）→ W32 无 weekly_plan → rail 空。

### 推荐修复方向（供 DeepSeek 04 参考，**DS 须用真实 DB 数据复现后定最终方案**）
> DS 第一步：查用户实际 DB（`%APPDATA%/workbuddy/workbuddy.db` 的 plans 表）——用户在周统筹存的 weekly_plan，`date` 字段实际是哪天？确认是根因 A、B 还是两者。再定修法。

- **方向 1（对应根因 A，必做）**：CascadeRail 的 parentStart 改基于 **curStart（当前查看期/今天）所在周**，而非 nextStart（明日）。
  - `usePlanning.loadParentTasks(curStart)` + `pickTask(..., curStart)`；PlanningView 调用处改传 `curStart`。
  - 效果：用户看 W32 任一日（8.3-8.9），curStart 所在周恒为 W32 → rail 稳定显示 W32 weekly_plan 任务 ✓（满足业务规则 1）。
  - 注意：下沉动作是把任务插入「明日」日计划（PlanPanel 仍引用 nextStart 编辑明日内容），但**任务来源是今天所在周**——两者解耦，语义自洽。
- **方向 2（对应根因 B，需产品决策）**：周统筹页是否应支持「本周/下周」切换，或默认显示本周？
  - 规格 §5.3 原设计 = 规划下期。若改默认本周是**规格变更**，需用户确认。
  - 备选：保持「规划下周」语义，但在 UI 明确标注「你正在规划 W33（下周）」，避免用户误以为是本周。
  - DS 评估后若需改默认本周，请在当前状态.md 记录规格偏差原因，等用户确认。

**验证点（DS 修后 GLM 复审 + 用户复测，严格按用户业务规则）：**
- [ ] 周日（或模拟）在周统筹制定下周周任务 → 下周任一日看日规划，rail 显示这些任务（业务规则 1）。
- [ ] 某日选取一个任务 → 编辑器插入 + 上级 weekly_plan 该任务 `[ ]→[x]` 持久化（业务规则 2）。
- [ ] 该周后续天数再看 rail，已下沉任务不再显示（业务规则 3，consumed 态）。
- [ ] 跨周边界（周日看日规划）rail 不串到下一周。

### 严重度
🔴 **HIGH** —— 核心级联功能不可用，阻断场景 D。**必须修**（方向 1 必做；方向 2 待产品决策）。

## 测试4-E 日规划保存的待办出现在今日总览 — ❓ 待 DS 核实（MED）

### 用户报告
- **现象**：日规划（**规划明日**）保存后显示「生成 N 条待办」，**但这些待办出现在今日总览**。
- **用户隐含预期**：日规划规划的是明日，生成的待办应归属**明日**（planDate=明日），今日总览（今天）不应显示，要等到次日。

### GLM 诊断
**裁定：❓ 待 DS 核实 planDate 归期语义。**
- 日规划 PlanPanel 编辑明日内容，保存时 `date = nextStart`（明日）。
- `runSync` → `planRepo.syncPlanTodos(planId)` 生成待办。**待办的 `planDate` 赋的是什么？** 若 = `plan.date`（明日）→ 正确，今日总览（按 planDate=今天 过滤）不应显示，用户次日才看到；若 = 今天 或其他 → bug。
- 需 DS 核 `planRepo.syncPlanTodos` 生成 todo 时的 `planDate` 取值 + 今日总览 `useToday`/`todoRepo.findByPlanDate(today)` 的过滤是否正确。

**结论分支**：
- 若 planDate=明日 且今日总览正确不显示 → ✅ 符合预期，向用户解释（待办次日才进今日总览）。
- 若 planDate=今天（错）或今日总览错显明日 → 🐛 bug，DS 修。

### 严重度
🟡 **MED** —— 若为 bug 则影响待办归期正确性（明日任务污染今日）。

## 测试3 未保存输入翻期后消失 — ✅ 非缺陷（符合用户期望）

### 用户报告
- **现象**：日规划编辑器输入字符（未保存）→ 点 ‹（上一天）→ 再点 ›（下一天）回到原日 → 输入字符消失。
- **用户态度**：「这个是用户想要的，未保存情况下切换页面则自动重置。如果你设计的代码是未保存切换页面不重置，则需要更改为会重置。」

### GLM 诊断
**裁定：✅ 非缺陷——当前行为就是「未保存切换自动重置」，符合用户期望，无需改。**
- 翻期走 `watch(curStart)` → `router.replace({query:{date}}) + load()`（`PlanningView.vue:137-140`）。`load()` 重新拉 savedPlan 并覆盖 `planDraft`（未保存的草稿被覆盖）→ 草稿消失 = 既有行为。
- 本次反馈3 修复未动 `load()`，行为未变。
- **澄清 GLM 05 复审的一处误判**：复审曾说「翻期不丢草稿（key=path 保证）」——不准确。`key=route.path` 只保证**切 level 不重建组件**；翻期（同 level、date query 变）本就不重建，但 `load()` 仍重置 planDraft。故草稿丢失是 `load()` 行为，非 key 行为。

### 处置
- **不改代码**。DS 仅需在修复说明里确认 `load()` 仍重置 planDraft（本次未动，应仍是），向用户回一句「当前就是未保存切换自动重置，符合你的期望」。

### 严重度
— （非缺陷，澄清）
