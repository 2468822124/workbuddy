## 逐项详情

### 1. 根因 C — periodStartFor 非法 date 兜底未归一化（🔴，DS 新发现，GLM 未诊断）

- **现象链**：侧栏「规划→周统筹」`router.push('/planning/weekly')` **无 date query** → `curStart = periodStartFor('weekly', '')`。原实现非法 date 兜底 `return todayStr()`——**未按 level 归一化** → 用户 8.8（周六）打开，curStart = **8.8 周六**（非周一 8.3）→ 保存 `nextStart('weekly', 8.8)` = 8.8+7 = **8.15 周六**。
- **DB 实锤**（用户真实库只读核查，`%APPDATA%/workbuddy/workbuddy.db` plans 表）：weekly_plan `date = 2026-08-15`（周六），正是 8.8+7 的产物；而 rail 按 `periodStartFor('weekly', 查看日)` = 周一键（8.3/8.10）查询，**永远取不到 8.15** → rail 空。GLM 的根因 A 无法解释此数据（8.15 不是任何查看日的「下周一」）。
- **修复**：`periodStartFor` 非法 date 兜底改为**递归调用自身**（按 level 归一化）：daily→今天、weekly→本周一、monthly→本月 1 号。
- **测试**：`tests/period.spec.ts` 新增 1 例（`'非法 date 兜底今天且按 level 归一化（用户反馈3.1 根因 C）'`，覆盖 空串/非 ISO 串 三 level）。

### 2. 根因 A — 级联基准用 nextStart 而非 curStart（🔴，GLM 方向1 必做）

- `loadParentTasks` / `pickTask` 原传 `nextStart`（明日）→ 跨周边界（周日看日规划）rail 取「明日所在周」= 下周，空/串周。
- **修复**：PlanningView `load()` 与 `onPickTask()` 均改传 `curStart`（当前查看期）——业务规则 1「本周周任务 = 查看日所在周」；下沉动作仍插入「明日」计划（PlanPanel 引用 nextStart），来源与去处解耦，语义自洽。
- usePlanning JSDoc 同步更新（记录 planStart 语义为「当前查看期」，附用户反馈3.1 出处）。

### 3. 业务规则 3 — consumed 任务从 rail 隐藏（🔴，GLM §5 验证点 + 用户原话）

- 用户原话：「该周内后续天数的日规划的"本周周任务"中**不再看到**"任务1"」。
- 原实现：consumed 任务显示「已下沉」标签（GUI 实测暴露，R3 失败）→ 与用户期望不符。
- **修复**：CascadeRail 增加 `activeTasks = tasks.filter(t => !t.consumed)`——rail 计数、空态、列表全部基于 activeTasks；移除 consumed class（line-through）/已下沉标签/pick-btn 条件。业务规则 3 达成：选取后该周后续天数 rail 不再看到该任务。

### 4. 根因 B（方向2）— 不改规格默认，记取舍

- **不改**：周统筹页仍固定「规划下期」（规格 §5.3 原设计）。原因：
  - 用户业务规则 = 「周日（每周末尾）制定**下周**计划」→ 与「规划下周」语义一致；8.8 周六制定存到 8.15/W34 属**操作时点非语义错误**；
  - 方向 1 + 根因 C 修复后语义已闭环：用户周日制定下周任务 → 下周任一日 rail 显示（R1 验证）；
  - 改默认本周 = 规格变更，需用户确认；现 UI 已标注「规划下周/下月」标题 + period-label 周次（第 N 周 · 日期范围），用户可见。
- **备选（若用户仍困惑，另行 CR）**：周统筹页加「本周/下周」切换按钮。

### 5. 测试4-E — 核实为非 bug（🟡）

- 代码核实：`planRepo.syncPlanTodos` 生成 todo 的 `planDate = plan.date`（= 明日 nextStart）；今日总览 `todoRepo.findByPlanDate(today)` 精确匹配 → **明日待办不显示在今日总览**。
- **结论：符合用户隐含预期**（「次日才进今日总览」）。向用户解释：日规划保存后生成的待办 planDate=明日，今日总览（按今天过滤）不显示，**次日才出现**。
- 若用户复测仍见明日任务出现在今日总览，请截图定位具体行（可能为 QuickAdd 手动添加或旧数据，非日规划生成）。

### 6. 测试3 — 确认非缺陷（不改代码）

- `load()` 未动（本轮零改动），翻期走 `watch(curStart)` → `load()` 仍覆盖 planDraft →「未保存切换自动重置」= 用户期望行为。向用户回一句确认即可。

### 7. 出处标注 — 方案（🔵，不实现，待 GLM 复审 + 用户确认粒度）

**推断链（渲染层纯函数，零迁移、零新列）**——按优先级：
1. `content` 以 `📌` 开头 → 「周期提醒」（周统筹/月指导提醒，reminders 生成）
2. `projectId` 非空 → 「项目任务」
3. `templateId` 非空 → 「日规划任务」（日规划模板生成）
4. 其余 → 「手动添加」

**交接事项区**（findOverdue：planDate < 今天 && todo）：统一标注「顺延自 {planDate}」——天然已知出处，无需推断。

**UI**：TodayView 的 todo-row / hand-row 行尾加 tag（复用 `.tag` token 样式，无新视觉系统）。

**粒度待确认**：与用户确认「日规划任务/项目任务/周期提醒/手动添加/顺延」5 类是否够，或需「日规划·8.9」级细粒度。若日后需精确追溯来源 plan（非仅类型），todo 无 planId 列——可通过 `plans.generatedTodoIds` JSON 反查（只读 join，仍无迁移）；需加列属规格边界，届时另行 CR。
