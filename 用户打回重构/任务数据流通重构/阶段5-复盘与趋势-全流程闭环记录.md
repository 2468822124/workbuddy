### 5. 核心设计

#### 5.1 唯一统计口径与时间边界

阶段5 所有统计必须以**结构化 id 关系**和 active 凭据为准，不按标题、来源文案或 Markdown 文本关联。

**周范围**：

- `weekStart` 使用 `getWeekStart(input.weekStart)` 归一化；周范围为 `getWeekRange(weekStart)` 返回的周一至周日
- 当前周的 `asOf` 为本地今天；历史周的 `asOf` 为该周周日。当前周周日之后的未来日期不进入当前周完成率分母
- 只接受本周及历史周。服务端收到未来周时返回 `err('INVALID_INPUT', '复盘仅支持本周及历史周')`；不能靠前端隐藏按钮代替服务端校验
- 所有跨年、闰年、周一/周日计算复用 `@shared/period.ts` 的 `getWeekStart`、`getWeekRange`、`addDays`；禁止在新代码里使用本地时区 `Date` 直接做天数加减

**周任务统计范围**：

- 周任务实例来自 `flow_week_instances.weekStart = weekStart AND isDeleted=0`
- 日计划 occurrence 来自 `flow_day_entries.weekInstanceId -> flow_week_instances.id`，且 `date` 位于目标周并不晚于 `asOf`
- `skippedAt` 非空的安排行不进入计划完成率分母；`skippedAt` 非空的周实例不进入未完成清单
- `manual` / `extra` 凭据用于周任务/场次完成度，但没有对应日安排行时不伪造一个日计划 occurrence，因此不增加日计划完成率分子或分母
- `project` / `reminder` 行没有周实例归属，永不进入阶段5周统计；不得通过标题匹配或 `source` 猜测把它们塞入周任务口径

**日计划完成率**：

```text
plannedCount(day)
  = 目标周内、截至 asOf 的 active day_entry 数量
  ∩ weekInstanceId 指向目标周实例
  ∩ 实例未跳过
  ∩ 安排行未跳过

completedPlannedCount(day)
  = 上述 planned day_entry 中存在 active kind='check' 凭据的数量

completionRate(day)
  = plannedCount(day) == 0 ? null : completedPlannedCount(day) / plannedCount(day)
```

周摘要的 `plannedCount` / `completedPlannedCount` 是 7 天明细求和；前端只格式化 `0..1` 比例，不重新计算分母。没有计划的日子显示 `—`，不能显示一个误导性的 `0%`。

#### 5.2 复盘派生 DTO 与计算算法

在 `src/shared/flowTypes.ts` 增加以下完整的只读类型。字段只能来自查询结果或纯计算，禁止作为 DDL 字段落库。

```typescript
export type FlowReviewTaskStatus = 'done' | 'unfinished' | 'skipped'

export interface FlowReviewSummary {
  plannedCount: number
  completedPlannedCount: number
  completionRate: number | null
  deferredCount: number
  unfinishedCount: number
  unarrangedCount: number
  skippedCount: number
}

export interface FlowReviewDay {
  date: string
  plannedCount: number
  completedPlannedCount: number
  completionRate: number | null
}

export interface FlowReviewTask extends FlowWeekInstance {
  completion: InstanceCompletion
  status: FlowReviewTaskStatus
  /** 目标周内是否至少存在一条未跳过 active 日安排行；展示字段，不是数据库状态 */
  arranged: boolean
  /** status='unfinished' 且 arranged=false；未安排清单的服务端判定结果 */
  unarranged: boolean
  /** 仅历史周未完成项为 true；UI 可据此显示「转下周」 */
  carryable: boolean
}

export interface FlowReviewDeferredEntry {
  entryId: number
  title: string
  source: FlowEntrySource
  originalDate: string
  deferredDays: number
  status: 'open' | 'done'
  resolvedAt: string | null
  note: string | null
}

export interface FlowReviewTrendPoint {
  weekStart: string
  weekEnd: string
  asOf: string
  plannedCount: number
  completedPlannedCount: number
  completionRate: number | null
  deferredCount: number
  unarrangedCount: number
}

export interface FlowReviewBoard {
  weekStart: string
  weekEnd: string
  asOf: string
  isClosed: boolean
  summary: FlowReviewSummary
  days: FlowReviewDay[]
  tasks: FlowReviewTask[]
  deferred: FlowReviewDeferredEntry[]
  trend: FlowReviewTrendPoint[]
}
```

服务端实现建议按以下顺序计算，确保每一层只有一个真相出口：

1. 一次性读取趋势窗口涉及的周实例、目标周日期范围内的 active day entries、以及顺延候选；按 id 建 `Map`，不得在循环内按标题查询
2. 批量读取相关 `week_instance` 和 `day_entry` 的 active 凭据；`kind='check'` 归到 day entry，`kind='manual'/'extra'` 归到 week instance。软删凭据不参与任何集合
3. 对每个目标周实例复用现有 `getWeekBoard` 的 completion 语义：一次性任务有 manual 凭据或任一已勾选安排行即 done；多次性任务 `manual + extra + check` 达到 `targetCount` 即 done；超额照计；实例跳过优先为 `skipped`
4. 给每个实例标注 `status`、`arranged`、`unarranged`、`carryable`。`arranged` 只看该实例目标周内未跳过 active 安排行；`unarranged` 只对 `unfinished` 实例成立；当前周 `carryable=false`
5. 按日期生成 7 个 `FlowReviewDay`；日计划 occurrence 只计目标周实例的安排行；项目、提醒、手动、模板自由行不进入周完成率
6. 生成 `summary`：日明细求和得到计划数/完成数/完成率；`unfinishedCount`、`unarrangedCount` 来自服务端任务状态；`skippedCount` 只数周任务域的跳过实例或跳过 occurrence，不能把同一跳过实例下的多条安排行重复计数
7. 生成 `deferred`：
   - 候选必须是 active、`locked=false`、`weekInstanceId=null`、`source!='reminder'`、`skippedAt=null` 的自由行；project 投影因 locked=true 天然排除
   - 以 active check 凭据的 `occurredAt` 作为完成日；没有 active check 时以 `asOf` 作为观察日
   - 只有 `观察日 > originalDate` 且该行在所选周期间仍 open 或在该期间完成，才算该周顺延；从更早周滚入的自由行也必须能在本周顺延清单出现
   - `deferredDays = 观察日 - originalDate`，按 `@shared/period` 的 UTC 日期算法计算；完成后仍保留为 `status='done'` 的顺延历史项，未完成为 `status='open'`
   - 按 `deferredDays` 降序、`originalDate` 升序、`entryId` 升序稳定排序；`deferredCount` 是清单行数，不是重复渲染天数
8. 对过去 8 个周一至选定周（共 8 个点）重复相同的纯计算口径；趋势点顺序从最早到最晚。当前周点只统计到 `asOf`，未来天数不提前计入

> **实现约束**：可以把复盘聚合拆成 `flowReviewDerived.ts`，但它必须落在 `src/main/services/`、只调用 repository、不能绕过 `flowDerived` 的完成态规则；若继续放在 `flowDerived.ts`，必须保持文件小于技术栈规范 §5.2 的 800 行上限。无论文件如何拆分，`getStats(): null` 预留实现必须被真正替换，不能留下空实现。

#### 5.3 封账语义与历史可编辑性

- `isClosed = weekStart < getWeekStart(todayStr())`，只是返回 DTO 的只读展示字段
- 历史周复盘显示「已封账」；当前周显示「进行中」。不得向数据库写 `isClosed`、封账时间或统计快照
- 历史周仍遵守立项 #5：用户在 `/flow/day` 翻回历史日补勾/收勾、在 `/flow/week` 编辑凭据后，重新进入复盘必须实时改变周完成态、日完成率、场次和趋势
- 固定型任务下周由既有 `materializeWeek(nextWeekStart)` 生成全新实例，凭据计数自然从零开始；复盘不能把本周实例的凭据、安排行或标题快照复制到下周
- 复盘页不提供直接改名、删除、跳过、勾选入口；需要修改时通过已有 `/flow/week` 或 `/flow/day` 入口完成，避免做出第三套写路径

#### 5.4 「转下周」显式清债与幂等

既有 `flow:instance:carryNext` 继续作为唯一写通道，阶段5只把服务端契约补完整：

1. `carryInstance(id, nextWeekStart)` 读取源实例；不存在返回 `NOT_FOUND`
2. `nextWeekStart` 必须是合法日期并归一化为周一；源实例必须属于历史周且当前状态为 `unfinished`，否则返回 `INVALID_ACTION`，不得靠 UI 条件保护
3. 目标周必须是源周之后的下一周；不接受跨两周或更远的任意目标，避免把按钮变成任意复制器
4. 先按 `carriedFrom = source.id AND weekStart = normalizedNextWeek AND isDeleted=0` 查 active 实例；已有则直接返回该实例，不插入重复行
5. 没有既有实例时只创建：
   - `origin='temp'`
   - `kind='once'`
   - `targetCount=1`
   - `fixedDefId=null`
   - `skippedAt=null`
   - `carriedFrom=source.id`

2. `FlowReviewView.vue`：`.grid { grid-template-columns: 1fr }`（@980 单列规则）的 auto 轨道在 390×844 下被 `.summary` 撑至 396px（容器轨道仅 235px），被 `.main { overflow-x: hidden }` 裁切。修复 = 双列/单列均改 `minmax(0, 1fr)`。机制说明：390 下对 `.summary` 各叶子（.top/.days/.rate-num/.stat…）逐一 fit-content 实测，全部 ≤220px，确认 396px 非内容 min-content，而是 Chrome grid auto 轨道对 flex 容器子项的保守计算（实测现象）；minmax(0,1fr) 修复后 summary 精确落回轨道 235px。
