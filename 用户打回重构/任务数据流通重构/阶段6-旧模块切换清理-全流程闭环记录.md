### 1. 单元目标

交付旧模块到新 flow 模块的最终切换：侧边栏和全部规划、复盘入口统一指向 /flow/week、/flow/month、/flow/day、/flow/review；旧规划/复盘页面、解析同步链和旧 IPC 不再被运行时加载；项目任务与周期提醒保留阶段4约定的兼容能力，但改由明确的项目任务适配仓储和专用 IPC 承载；用户主动触发旧表归档时先生成本地 JSON 备份，再事务性删除 plans、tasks、templates、reviews 四张旧表；正常数据导入导出覆盖 flow 数据和保留表；最后完成 3.2 六轮场景全量回归。

一句话可演示价值：**从侧边栏打开四个 flow 页面时不再经过旧规划壳；项目任务仍可创建、改名、加入今日、勾选回写；提醒仍按日生成且不重复；用户点击设置中的旧数据清理后能拿到包含计数和原始数据的 JSON，备份失败或删除失败都不损坏原库。**

本阶段的清理不是把旧数据偷偷迁移到 flow 表，也不是启动时自动 DROP 表。旧表数据只在用户明确确认并完成本地备份后清理；flow_* 数据、项目任务、设置、热点和其它保留基础表永不因该动作被删除。

### 5. 核心设计

#### 5.1 路由切换与兼容重定向

**设计逻辑**：

- 新 flow 页面已经在阶段2-5交付，阶段6只收口入口，不重复实现页面业务。
- 旧路径保留一层无 UI 的兼容别名，帮助已有书签和提醒链接平滑进入新页面；别名不能再加载 PlanningView.vue 或旧 composable。
- 旧 /planning/:level 路由改为 redirect 函数。daily→/flow/day，weekly→/flow/week，monthly→/flow/month；未知 level→/flow/day。
- /plan→/flow/day；/review→/flow/review。
- 查询参数转换必须是显式的：旧 daily 的 date 传给新 date；旧 weekly 的 date 转为 week；旧 monthly 的 date 转为 month；旧 review 的 week 保留，若只有 date 则归一化为 week。除日期参数外不把旧 focus、模板或 Markdown 参数传给新页面。

**实现细节**：

- router/index.ts 不得再出现 PlanningView.vue 的 import。
- 重定向函数必须是纯的可测试逻辑，不能读取 DB，不能在 renderer 直接调用旧 API。
- 新 flow 路由的 name 保持 flow-week、flow-month、flow-day、flow-review，避免修改阶段2-5已有页面内部导航。
- AppSidebar.vue 的规划组可以保留折叠视觉，但 children 的 path 只能是 /flow/week、/flow/month、/flow/day、/flow/review；active 判定必须覆盖 query 变化但不能把旧 /planning 路径标为 active。

**交互与边界**：

- 用户点击侧边栏四入口，目标页直接加载；错误由目标 flow 页面已有反馈条处理。
- 旧 URL 访问只发生一次导航替换，不显示旧页面闪烁，不出现“规划页面不存在”空白。
- 旧路径参数非法时落到对应 flow 页面默认期；未知规划级别落日规划。

#### 5.3 项目任务兼容适配层

**职责边界**：

- projectTaskRepo.ts 是 todos 表在阶段6后的唯一项目/提醒兼容读写入口。
- 仓储只做 SQL 和行映射；项目任务完成态是 projects/todos 旧项目模块既有状态，不复制到 flow 表，不写 flow_vouchers。
- flowActions.ts 负责投影动作编排：project 行的加入、勾选回写、移出今日；reminder 行的打卡回写和当日有效语义。
- flowDerived.ts 负责批量读取 project 源任务、实时标题和完成态，并在源缺失时返回已有行快照和 sourceHref=null。
- reminders.ts 负责周期触发和幂等种入；失败只能影响提醒渠道，不阻断应用启动或其它三个渠道。

**仓储最小 API**：

    listByProject(projectId: string): ProjectTask[]
    findById(id: string): ProjectTask | undefined
    findByIds(ids: string[]): ProjectTask[]
    findByDate(date: string): ProjectTask[]
    findReminderTask(date: string, key: 'weekly' | 'monthly'): ProjectTask | undefined
    createProjectTask(input: CreateProjectTaskInput): ProjectTask
    ensureReminderTask(input: ReminderTaskInput): ProjectTask
    updateProjectTask(id: string, patch: UpdateProjectTaskInput): ProjectTask | undefined
    toggleDone(id: string): ProjectTask | undefined
    softDelete(id: string): boolean

- createProjectTask 只能由 projectTasks IPC 使用，并强制 projectId 非空、内容长度沿用现有 200 字符限制。
- updateProjectTask 只能允许 content、planDate；禁止 renderer 修改 projectId、来源字段或删除标志。
- ensureReminderTask 只接受 weekly/monthly 和合法日期，必须幂等；不得让任意 renderer 输入创建提醒源。
- findByIds 必须批量查询，flowDerived 不得恢复 N 次 IPC/SQL。
- 现有 todos 表没有 reminderKey 列，本阶段不得为此新增列；因此 projectTaskRepo 必须集中封装一个兼容定位规则：由 date + weekly/monthly 计算唯一的预期提醒文案，优先读取阶段6新建的确定性提醒 id，再对阶段6前的随机 UUID 存量执行一次精确的 date + 预期文案 + 非项目归属 + 非旧规划来源约束查询，并按 createdAt、id 稳定排序取一行。该兼容查询只能存在 projectTaskRepo.findReminderTask 内，不能在 flowActions、flowDerived、reminders 或 renderer 重新按任意正文匹配。
- reminders.ts 创建新提醒源时使用同一 date/key 计算确定性 id，重复调用幂等；不得回填旧行、不得迁移旧数据。flow 域只使用 flow_day_entries 已保存的 reminderKey，不读取或解析 sourcePlanId、parentTaskRef、sourceTaskTid。

**项目详情 API 迁移**：

- useProjectDetail.ts 改为 api.projectTasks.listByProject/create/update/delete/toggle。
- TaskRow.vue、ProjectDetailView.vue 的事件命名可继续使用 task 语义，但类型必须是 ProjectTask；删除继续是行内确认和软删，不使用阻断式模态框。
- projectRepo.ts 的项目统计可以继续直接查询 todos 表，因为 SQL 仍只在 repository；不得再 import todoRepo.ts。

**提醒语义**：

- 周日生成 weekly，月末生成 monthly；同一日期、同一 key 只有一条 active flow 投影。
- 当日移出提醒后，启动再次执行不得把 tombstone 拉回；写入旧提醒源失败时记录脱敏警告并继续启动。
- reminder 行不可挪动、不可跳过、不顺延；勾选只影响当日提醒源状态，仍保持阶段4可见行为。

#### 5.4 旧表归档与物理清理

**用户流程**：

1. 设置页提供“归档并清理旧规划数据”的显式入口。
2. 用户先点击入口，再通过行内确认条确认；不使用自定义阻断模态框。
3. archive:legacy handler 打开用户选择的本地 JSON 保存路径；取消直接返回 CANCELLED。
4. IPC 将路径传给 legacyArchive 服务；服务读取旧表快照、生成归档 payload，写入临时文件并原子改名到用户路径。
5. 文件写入成功后，服务在一个 better-sqlite3 transaction 中按固定顺序 DROP plans、tasks、templates、reviews。
6. 事务成功才返回 ok；任何异常返回 ARCHIVE_FAILED/ARCHIVE_ROLLBACK，原库必须仍可打开，用户可看到错误反馈。

**归档 payload**：

    {
      version: 1,
      kind: "workbuddy-legacy-archive",
      exportedAt: "ISO timestamp",
      tables: {
        plans: [],
        tasks: [],
        templates: [],
        reviews: []
      },
      counts: {
        plans: 0,
        tasks: 0,
        templates: 0,
        reviews: 0
      }
    }

- tables 的行对象按数据库原始列名写出，不解析 Markdown，不改写任务内容，不上传网络。
- 文件写入必须先写 path.tmp 或等价临时文件，成功后 rename；失败时删除临时文件但不碰数据库。
- 日志只记录操作结果和各表计数，不记录任务/复盘/模板正文、API Key 或用户文件完整路径。
- 四张旧表不存在时返回 NO_LEGACY_TABLES，不报内部错误，不影响启动；实现可以生成“无旧数据”的归档文件，但不得 DROP 保留表。
- DROP 不是普通业务删除；它只能出现在 legacyArchive.ts 的用户触发事务中，不能出现在迁移、启动、data.ts 正常导入或页面 mounted 逻辑中。

**事务与失败保证**：

- 读快照失败：不创建最终归档文件，不执行 DROP。
- JSON 序列化或临时文件写失败：不执行 DROP，返回错误条。
- 任一 DROP 失败：transaction 回滚四张旧表，已写好的归档文件保留并明确提示“备份已生成，但旧表未清理”。
- 清理成功后，再次点击只返回 NO_LEGACY_TABLES；不得重建旧表、不得重新跑 0001-0009。
